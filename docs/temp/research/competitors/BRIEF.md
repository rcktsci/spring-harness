# БРИФ: Конкурентный анализ для проекта spring-harness

> Общий файл для всех субагентов-исследователей. Читай целиком, затем работай по своему объекту из индивидуального задания.

## Контекст: что мы строим

Клиент-серверная платформа оркестрации AI-агентов на Java 25 / Spring Boot 4.1 / Spring AI 2.0 (репозиторий: `D:\RocketScience\AI\spring-harness-gh`).

**Сервер:**
- Все сессии агентов хранятся в PostgreSQL.
- Вытесняющий планировщик на ShedLock: сканирование таблицы сессий раз в 1–5 секунд; распределённый лок по ключу сессии; сессия запускается только если есть новые сообщения (от пользователя, от оркестратора или от асинхронных инструментов) и лок свободен.
- Workflow-движок: таблица workflow (кастомные состояния + разрешённые переходы, граф). Задача находится ровно в одном состоянии. У состояния — своя сессия и назначенный агент. Переход задачи в следующее состояние агент выполняет инструментом (tool call). Есть терминальные состояния (Done/Cancelled/Error).
- Системные состояния без сессии агента: ожидание внешнего вебхука (с таймаутом), вызов bash-скрипта. Успех → переход дальше; ошибка (падение скрипта / таймаут / кривой payload) → переход в сессию-разборщик ошибки.
- Агент = роль (описание) + набор инструментов + разрешения + навыки (skills).
- Агент-оркестратор («CEO», элемент из Paperclip): инструментами создаёт/редактирует workflow, назначает задачи, настраивает триггеры.
- Внешние триггеры: вебхуки (GitHub/GitLab и др.) создают задачи по конкретному workflow. Отдельный тип — постоянные сессии, получающие входящие события через вебхуки.

**Клиент:**
- Удалённые клиенты attach-стиля (аналог `opencode attach`): подключение к сессии с любого ПК, роуминг офис/дом.
- REST API клиент↔сервер по OpenAPI, contract-first.

**Инфраструктура пользователя:**
- LLM через корпоративный LiteLLM-подобный провайдер (OpenAI-совместимый API, свой SSO).
- 12+ MCP-серверов за корпоративным OAuth2-прокси (SSO, токены на 24 часа).

## Цель исследования

Дать фактуру для проектирования нашей платформы: как устроены аналоги, что брать, чего избегать. Проект один; результаты пойдут в дизайн-документы и OpenSpec-изменения.

## Единый список вопросов (ответить по каждому пункту)

1. **Архитектура**: клиент/сервер, где хранится состояние, транспорт, изоляция процессов.
2. **Модель сессий**: хранение (файлы/БД), персистентность, удалённый доступ/роуминг, attach/resume, совместный доступ, форки/ветвления сессии.
3. **Модель агента**: роли, субагенты, навыки (skills), разрешения, промпт-структура.
4. **Инструменты**: список встроенных, синхронные/асинхронные паттерны, фоновые задачи с отложенным возвратом результата.
5. **Оркестрация/воркфлоу**: задачи, планирование, plan mode, многоагентные сценарии, найм/распределение работ (если есть).
6. **API-поверхность**: REST/HTTP/RPC/SDK/CLI — конкретные эндпоинты/методы/протоколы, авторизация, стриминг (SSE/WebSocket).
7. **MCP**: поддержка клиента/сервера, OAuth, известные проблемы.
8. **Расширения/плагины**: механизмы, API, ограничения.
9. **Сильные и слабые стороны** с точки зрения наших целей (см. Контекст).
10. **Выводы**: что нам перенять; чего избегать.

## Формат результата

- Язык: русский, Markdown.
- Каждый факт — со ссылкой на источник (URL). Для GitHub-репозиториев указывай конкретные пакеты/модули/файлы.
- Если факт не найден — честно пиши «не найдено/не подтверждено». Не выдумывай.
- Ориентир объёма: 300–800 строк.
- Результат записать в назначенный тебе целевой файл (см. индивидуальное задание).
- В ответе верни только краткую сводку (10–15 строк): ключевые находки и проблемы.
