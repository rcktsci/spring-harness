## CRITICAL

### C-1: design.md:130 + tasks.md:2.3 — «первый `<version>`» в pom.xml не работает, parent уже есть

**Место:** `design.md` D-CI13 (строка 130): "первый `<version>` в файле — версия проекта; допущение: у pom нет `<parent>`"; `tasks.md` 2.3 (строка 12): "версии извлекаются из первого `<version>` в `pom.xml`".

**Почему это дефект:** Допущение в D-CI13 неверно для текущего `pom.xml`. Реальное состояние файла (проверено):
- `pom.xml:7-12` — `<parent>` блок присутствует: `org.springframework.boot:spring-boot-starter-parent:4.1.1`.
- `pom.xml:10` — первый `<version>` в файле: `4.1.1` (версия parent'а).
- `pom.xml:16` — второй `<version>`: `1.0.0-SNAPSHOT` (версия проекта).

Если шаг 2.3 реализуется буквально (`grep -m1 '<version>' pom.xml` или `sed -n '/<version>/{p;q}'`), он извлечёт `4.1.1`, а не `1.0.0-SNAPSHOT`. На теговом прогоне `v0.1.0` сверка сравнит `4.1.1` ≠ `0.1.0` → CI упадёт на шаге проверки версии. **Задача 4.4 (первый релиз v0.1.0) при буквальной реализации шага 2.3 не сможет пройти CI-гейт ни на одном теге** — релиз v0.1.0, заявленный как стартовая версия продукта (proposal.md:10, spec release-policy сценарий "первый релиз"), не состоится через CI.

Дизайн сам частично признаёт проблему (design.md:134, design.md Risks строка 161): "Хрупкость «первого `<version>`» документируется в задаче; появление `<parent>` в pom сразу делает проверку неверной, но это заметно на ревью и чинится одной строкой". Однако parent не "появится" — он уже есть в закоммиченном `pom.xml:7-12`, и design.md:8 сверено с этим же `pom.xml` (см. ссылки на строки 290, 347, 376), но parent-блок пропущен при анализе допущения.

Сценарий release-policy "версии в репо разошлись с тегом" (spec release-policy:17-20) не покрывает этот случай: версии не расходятся, а тег просто никогда не совпадёт с тем, что извлекает шаг 2.3.

**Как исправить (любой из вариантов):**

(a) Извлекать версию проекта явно через контекст `<project>` → `<version>`, игнорируя `<parent>`. На ubuntu-latest без Maven доступны:
- `xmllint --xpath '/*[local-name()="project"]/*[local-name()="version"]/text()' pom.xml` (xmllint обычно есть; проверить перед использованием).
- `python3 -c "import re; xml=open('pom.xml').read(); m=re.search(r'<project[\s\S]*?<version>([^<]+)</version>', xml); print(m.group(1) if m else '')"` (python3 есть на ubuntu-latest).
- `awk '/<parent>/,/<\/parent>/{next} /<version>/{gsub(/.*<version>|<\/version>.*/, ""); print; exit}' pom.xml` — вырезает блок parent и берёт первое оставшееся `<version>`.

(b) В design.md D-CI13 явно описать инвариант "пропустить блок `<parent>...</parent>` при поиске первого `<version>` после закрытия parent-блока".

(c) Допустить, что на теге версия проекта — всегда третий `<version>` (после `<modelVersion>` и `<parent>/<version>`), и формализовать это в задаче 2.3 (хрупко, не рекомендуется).

Рекомендую (a) с использованием python3 или xmllint + явная правка design.md и tasks.md. Также добавить локальную проверку в tasks 2.3: "повторить логику на pom с `<parent>` (текущий main) — получить именно `X.Y.Z`, а не `4.1.1`".

## MINOR

### m-1: proposal.md:9 + spec release-policy scenario — неполный список тегов на релизе

**Место:** `proposal.md:9` ("на теге `vX.Y.Z` — теги `vX.Y.Z`, `X.Y.Z`, `sha-<short>`"); `specs/release-policy/spec.md` scenario "тег запускает релизный прогон" (строка 29: "теги `v0.1.0`, `0.1.0`, `sha-<short>`"); `tasks.md:2.2` использует `type=semver` без явного `pattern`.

**Почему это дефект:** `docker/metadata-action@v6` с `type=semver` без явного `pattern` по умолчанию генерирует не только `{{raw}}` (= `v0.1.0`) и `{{version}}` (= `0.1.0`), но и `{{major}}.{{minor}}` (= `0.1`) и `{{major}}` (= `0`). Иначе говоря, на теге `v0.1.0` GHCR получит пять тегов: `v0.1.0`, `0.1.0`, `0.1`, `0`, `sha-<short>`. Proposal/спека перечисляют только три — это не противоречие (дополнительные теги не нарушают заявленные), но расхождение с реальностью может удивить владельца, когда он увидит лишние теги в GHCR UI.

**Как исправить:** Либо в proposal/spec явно указать "также публикуются `X.Y` и `X`", либо в tasks 2.2 добавить `pattern={{raw}},{{version}}` (и при необходимости `{{major}}.{{minor}},{{major}}` — но не нужно для MVP).

### m-2: spec release-policy scenario "узнать, что крутится на VM" — не работает для :latest до первого релиза

**Место:** `specs/release-policy/spec.md` scenario "узнать, что крутится на VM" (строки 72-75): "docker inspect label'а `org.opencontainers.image.version` контейнера даёт версию semver".

**Почему это дефект:** На веточном прогоне (push в main) `docker/metadata-action@v6` не имеет semver-тега → label `org.opencontainers.image.version` будет пустым (metadata-action заполняет его только при наличии semver-тега). До выполнения задачи 4.4 (первый релиз v0.1.0) и при работе VM на `:latest`-образе команда `docker inspect ... -f '{{index .Config.Labels "org.opencontainers.image.version"}}'` вернёт пустую строку, а не версию. Сценарий спеки формально проходит только для релизных образов; для latest — нет.

Дизайн D-CI15 и tasks 4.3 это не оговаривают. После 4.4 рассогласование уходит (если VM катается на semver-теге), но tasks 3.1 (README) описывает `docker pull ...:latest` как основной путь доставки — то есть сценарий спеки и инструкция README расходятся до первого релиза.

**Как исправить:** В scenario добавить оговорку "для релизного образа; на :latest label версии пуст, трассировка через `org.opencontainers.image.revision`". Либо в tasks 4.3 / README рекомендовать после релиза использовать semver-тег вместо latest.

### m-3: перезапись существующего semver-тега в GHCR не покрыта

**Место:** `specs/backend-image-ci/spec.md:39`: "Один и тот же тег SHALL всегда указывать на образ, собранный из соответствующего коммита". Ни Risks, ни requirements не покрывают случай force-push существующего semver-тега.

**Почему это дефект:** GHCR (как и любой OCI registry) по умолчанию разрешает перезапись тега: `docker push` с тем же тегом перезаписывает манифест. Если владелец случайно переместит `v0.1.0` на другой коммит (force-push, ошибка при локальной правке тега) — тег будет указывать на новый коммит, что нарушит требование "один и тот же тег SHALL всегда указывать на образ, собранный из соответствующего коммита". Risks (design.md:152-164) не упоминают этот сценарий.

**Как исправить:** В Risks добавить пункт "Force-push существующего semver-тега → митигация: релиз только через `git push origin vX.Y.Z` (без force), на стороне GitHub защита тегов через Settings → Rules → Tags (опционально для MVP)". Для MVP достаточно пункта в Risks + упоминания в README.
