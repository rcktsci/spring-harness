## CRITICAL

### C-1. Модель авторизации для задач не определена
- **Severity:** CRITICAL
- **Место:** §3 «Задачи» — права `PARTICIPANT-уровень задачи` (subtasks, dependencies, comments, stop); `GET /api/v1/tasks` — «по видимости».
- **Описание:** В глоссарии уровни `VIEW`/`PARTICIPATE` определены **только для сессий** (раздел 1, Share). У задач в data-model нет ни поля `visibility`, ни механизма share — только `owner_user_id`/`author_user_id`. При этом глоссарий (§3 Task) упоминает `visibility` задачи, которого нет в таблице `task`. Термин «PARTICIPANT-уровень задачи» не определён нигде: непонятно, кто может создавать подзадачи, ставить зависимости между **произвольными** задачами (инвариант TaskDependency — «между любыми двумя»), комментировать и останавливать. Это дыра в безопасности: проверка прав неформализуема.
- **Предложение:** Определить в API-спеке (и синхронизировать glossary/data-model): (а) есть ли у задач share-модель или доступ = owner + участники родительской задачи; (б) кто такой PARTICIPANT задачи; (в) правила для кросс-деревных зависимостей. До этого эндпоинты задач нельзя реализовать без ad-hoc проверок, что запрещено инвариантом «доступ только через AccessPolicy».

### C-2. Нет способа получить подписанный URL вебхука WAIT_WEBHOOK
- **Severity:** CRITICAL
- **Место:** §3 «Входящие вебхуки задач»; отсутствие поля/эндпоинта в TaskDto.
- **Описание:** Глоссарий §7 и workflow-domain §7: «URL выдаётся через API/агента, регистрацию во внешней системе делает агент предыдущего состояния или человек». Подпись = `HMAC(server_secret, taskId)`, где `server_secret` известен только серверу. Человек не может вычислить подпись; в API-спеке **ни один эндпоинт и ни одно поле TaskDto не возвращают готовый URL**. Сценарий WAIT_WEBHOOK через публичный контракт нереализуем.
- **Предложение:** Добавить в `GET /api/v1/tasks/{id}` (или отдельный `GET /api/v1/tasks/{id}/webhook-url`, право — owner/участник) поле `webhookUrl` для задач в WAIT_WEBHOOK; описать, когда URL выдаётся и логируется ли secret в ответах.

### C-3. Обязательная идемпотентность не имеет хранилища (противоречит data-model)
- **Severity:** CRITICAL
- **Место:** §0.3 (`Idempotency-Key` обязателен на `POST .../messages` и вебхуках), §5 `idempotency-conflict`; data-model §6 «Отдельных таблиц нет».
- **Описание:** Детекция `idempotency-conflict` («тот же ключ, другое тело») и возврат результата повторного запроса требуют **хранения** ключей (минимум — сессионного/временного). Data-model явно фиксирует: для интеграций таблиц нет, история попыток не хранится; таблицы идемпотентности в модели нет вообще. Контракт требует невозможного.
- **Предложение:** Либо ввести хранилище идемпотентности в data-model (таблица с TTL-очисткой), либо ослабить контракт (идемпотентность только «наилучшим усилием» для вебхуков, конфликты не детектируются). Заодно зафиксировать семантику повтора «тот же ключ + то же тело» (см. MIN-8).

## MAJOR

### M-1. Пагинация сообщений противоречит общим правилам
- **Место:** §1 `GET /sessions/{id}/messages` (возвращает голый `MessageDto[]`) vs §0.4 («ответ содержит `nextCursor`»).
- **Описание:** Основная стриминговая коллекция не отдаёт курсор — клиент не может продолжить чтение без оффбай-эвристики. Противоречие внутри самой спеки.
- **Предложение:** `{ items: MessageDto[], nextCursor? }` как в `GET /sessions`.

### M-2. Не существует способа узнать `agentKey` — нет каталога агентов
- **Место:** §1 `POST /sessions` (обязательное `agentKey`).
- **Описание:** Нет `GET /api/v1/agents` или аналога. Attach-CLI не может показать список агентов при создании сессии; ревизии агентов тоже не раскрываются (SessionDto отдаёт `agent {key, rev}`, но выбрать нельзя).
- **Предложение:** Добавить `GET /api/v1/agents` → `{ key, name?, latestRev }` (права — аутентифицированный). Управление ревизиями — явно вынести за рамки MVP или описать.

### M-3. Folder — субъект шаринга, но API папок не существует
- **Место:** §1 (`folderId` в сессиях); глоссарий §1 (Folder — «субъект шаринга»); data-model `share.resource_type = SESSION | FOLDER`.
- **Описание:** Нет CRUD папок и нет управления share на папку (`/folders/{id}/shares`). FOLDER-шаринг заложен в модель данных и глоссарий, но публичным контрактом недостижим. Также неясно, как считается видимость сессии, лежащей в расшаренной папке.
- **Предложение:** Добавить `GET/POST/PATCH/DELETE /api/v1/folders`, `GET/POST/DELETE /api/v1/folders/{id}/shares`; описать наследование доступа папка → сессии в правилах AccessPolicy (или явно отложить, указав в спеке out-of-scope и убрав FOLDER из обещаний).

### M-4. `/compact` не ограничен FREE-сессиями
- **Место:** §1 `POST /sessions/{id}/compact`.
- **Описание:** Глоссарий §4: «`/compact` — та же механика по команде для **свободных** сессий». В API нет ограничения kind (в отличие от fork/rewind, где `409 wrong-session-kind` описан). Принудительная компакция задачной сессии извне ломает аудит workflow.
- **Предложение:** Ограничить FREE (`409 wrong-session-kind` иначе) — и внести compact в описание `wrong-session-kind` в каталоге.

### M-5. «Архивация» сессии не существует в модели данных
- **Место:** §1 `DELETE /sessions/{id}` → «архивация → 204».
- **Описание:** Ни в data-model (`session`), ни в глоссарии нет поля `archived`. SessionDto не содержит признака архивации; `GET /sessions` не фильтрует по нему; нет unarchive. Клиент не отличит архивную сессию, поведение списков не определено. DELETE, который не удаляет — вводит в заблуждение.
- **Предложение:** Либо добавить `archived_at` в data-model + фильтр в список + `POST .../restore`, либо переименовать метод/семантику (например, оставить только visibility-механику). Указать каскад для поддерева субагентов и shares.

### M-6. runtimeStatus не отражает исход Turn'а; в SSE нет ошибок
- **Место:** §1 SessionDto, §2 события SSE.
- **Описание:** Enum `IDLE|TURN_RUNNING|PARKED_ASYNC` не покрывает исходы из execution-model §3: Turn может завершиться `FAILED` (ошибка LLM) или `CANCELLED`. Событий типа `turn.failed`/`turn.cancelled`/`session.error` в SSE нет — attach-клиент не узнает, почему поток замолчал. Также неясен runtimeStatus для «Turn паркуется, ждёт клиента CLIENT_EXEC» (это не PARKED_ASYNC в смысле async-тулов).
- **Предложение:** Дополнить enum (или добавить отдельное поле lastTurnOutcome), добавить событие `session.error`/`turn.finished { status }` в SSE; определить значение статуса для ожидания клиента.

### M-7. Каталог ошибок неполон и не согласован с текстом
- **Место:** §5.
- **Описание:** В тексте спеки используются коды, отсутствующие в каталоге: `executor-already-connected` (§4). Нет кодов для `404 task-not-found`, `workflow-not-found`, `trigger-not-found`, `400 validation` (тела запросов, JSON-Schema params), `409 task-already-terminal` (suspend/resume/stop по финальной задаче). Для RFC 9457 заявлен «машиночитаемый каталог» — он должен быть исчерпывающим.
- **Предложение:** Дополнить каталог всеми используемыми и ожидаемыми кодами; добавить правило: любой `code` вне каталога — дефект реализации.

### M-8. Триггер: сущность и secret отсутствуют в data-model
- **Место:** §3 «Триггеры» (`TriggerDto { id, url }`, HMAC по secret); data-model §6; спека §6 (открытый вопрос 3).
- **Описание:** API уже обязуется выдавать `TriggerDto` и stateless-URL с per-trigger secret, но таблицы `trigger` в data-model нет (спека сама признаёт это «открытым вопросом»). Где хранится secret, как отзывается триггер (DELETE → URL умирает?), не определено. Нельзя релизить контракт, висящий на неутверждённой сущности.
- **Предположение:** Утвердить вопрос 3: добавить `trigger (id, name, workflow_revision_id?/workflow_key, params_jsonb, secret_encrypted, owner_user_id, created_at)` в data-model в этой же итерации; описать семантику DELETE (мгновенная инвалидация подписи).

### M-9. Не определена авторизация на workflow и trigger-эндпоинтах
- **Место:** §3 «Workflow» (таблица вообще без колонки прав), `DELETE /api/v1/triggers/{id}` и scope `GET /api/v1/triggers`.
- **Описание:** Кто может создавать/править workflow (любой аутентифицированный? только владелец key?), кто видит список, кто удаляет чужой триггер — не определено. Требование «на каждом эндпоинте явно определена авторизация» нарушено. В data-model у `workflow` есть `owner_user_id`, но прав нет.
- **Предложение:** Проставить колонку прав во все таблицы §3: создание/ревизии — владелец key (или админ), чтение — по видимости (ввести её) или «все аутентифицированные» явно; триггеры — только владелец.

### M-10. Комментарии задачи нельзя прочитать
- **Место:** §3 `POST /tasks/{id}/comments`.
- **Описание:** Есть только создание (append-only); `GET /tasks/{id}/comments` отсутствует — данные записываются, но недоступны ни CLI, ни WebUI, ни оркестратору через публичный контракт.
- **Предложение:** Добавить `GET /api/v1/tasks/{id}/comments?cursor=&limit=` → `{ items, nextCursor }`.

### M-11. Надёжность WebSocket-релея не специфицирована
- **Место:** §4.
- **Описание:** (а) `tool.result` «идемпотентен по callId», но в WS нет ack/нумерации/ретраев — сценарий потери результата (обрыв после выполнения до доставки) не определён: Turn паркуется до таймаута состояния? (б) «вторая регистрация → `409 executor-already-connected`» — HTTP-статус неприменим к WS-фрейму: нужен тип ошибки в сообщении или close-code (например, 4409). (в) Направление heartbeat `{"type":"ping"}` (клиент→сервер или сервер→клиент) и критерий «разрыва» не указаны. (г) Поведение при регистрации, когда задача не в CLIENT_EXEC-состоянии, не описано.
- **Предложение:** Дописать протокол: типы ошибок `{ type: "error", code }` + WS close-codes; направление и таймауты ping; поведение при обрыве (результат потерян → синтетический TIMEOUT/ERROR-переход?); валидация register по состоянию задачи.

### M-12. HMAC-подпись в query-параметре: утечка через логи и бесконечный replay
- **Место:** §3 оба вебхука (`?signature=...`).
- **Описание:** Подпись в URL попадает в access-логи прокси/балансировщиков и внешних систем (регистрирующих webhook URL). Отсутствуют timestamp/nonce — перехваченный запрос можно реплеить вечно; ротация secret невозможна по построению (stateless, без БД). Схема продиктована глоссарием — это междокументная проблема, но публичная спека безопасности обязана её зафиксировать или осознанно принять риск.
- **Предложение:** Минимум — задокументировать угрозы и компенсации (TLS-only, короткий secret-слуг, идемпотентность вебхуков). Лучше — `Authorization: HMAC` в заголовке + `X-Timestamp` с окном допуска (stateless-проверка сохраняется: подпись от taskId+timestamp).

### M-13. Видимость STATE-сессий и список задач неформализованы
- **Место:** §1 `GET /sessions` («по видимости»), §3 `GET /tasks` («по видимости»).
- **Описание:** К STATE-сессиям (владелец — владелец задачи) непонятно, как применяется visibility/share: может ли участник родительской FREE-сессии оркестратора «провалиться» в STATE-сессии подзадач (ключевой сценарий «следить вместе с оркестратором» из глоссария §3)? Какие поля TaskDto видны не-владельцу (`params` может содержать секреты)? Спека отвечает «по видимости», не определив её.
- **Предложение:** Описать матрицу доступа в терминах AccessPolicy: FREE (owner/share/visibility), STATE (наследование от задачи — а доступ к задаче = C-1), состав TaskDto для не-владельца.

## MINOR

### MIN-1. Разнобой имён поля отсечки: `atSeq` (fork) vs `toSeq` (rewind)
- **Место:** §1. **Предложение:** унифицировать (`atSeq` в обоих) — семантически это одна точка отсечки.

### MIN-2. Двойной механизм переподключения SSE
- **Место:** §2 (`?since=` и `Last-Event-ID = seq` одновременно). **Предложение:** указать приоритет: при наличии `Last-Event-ID` он главнее `?since=`; `?since=` — только для первичного attach.

### MIN-3. `suspend` → 202, `resume` → 204
- **Место:** §3. Обе операции асинхронны по духу (каскад дорабатывает). **Предложение:** единообразно 202 (или оба 204, если операции синхронны — тогда сказать это явно).

### MIN-4. `history`: `?since=&cursor=` — два курсора на одном эндпоинте
- **Место:** §3 `GET /tasks/{id}/history`. **Предложение:** оставить один стиль (`cursor=&limit=`); `since` определить как filter по created_at, если нужен.

### MIN-5. `includeHidden` — значение по умолчанию и права не определены
- **Место:** §1 `GET /sessions/{id}/messages`. Может ли VIEW-пользователь запросить скрытые COMPACT-ом оригиналы? **Предложение:** default `false`; `true` — только владелец (и описать, что это инструмент аудита).

### MIN-6. Формы TreeNode/TransitionDto не определены
- **Место:** §1 `/sessions/{id}/tree` (поля перечислены в скобках — ок, но не глубина: прямые дети или всё поддерево?), §3 `/tasks/{id}/tree` и `history` (DTO вообще не описаны). **Предложение:** задать полные формы DTO и глубину деревьев (вся ветка рекурсивно / плоский список с parent).

### MIN-7. Нет соглашения о `Location` для 201
- **Место:** все `201` (sessions, fork, tasks, subtasks, workflows, revisions, triggers, comments). **Предложение:** добавить в §0: «201 всегда содержит `Location: <resource url>`».

### MIN-8. Семантика повтора идемпотентного запроса не определена
- **Место:** §0.3. «Тот же ключ + то же тело» → вернуть сохранённый результат или пересчитать? **Предложение:** зафиксировать: повтор с тем же ключом и телом возвращает исходный ответ (в т.ч. 202 c тем же messageId/seq); TTL ключа.

### MIN-9. `lockedBy` — внутренний идентификатор инстанса, утекает наружу
- **Место:** §2 `session.status { runtimeStatus, lockedBy? }`. **Предложение:** не отдавать наружу или заменить на булев `locked`.

### MIN-10. Расхождение с глоссарием по вебхукам
- **Место:** глоссарий §7: путь `POST /api/webhooks/{taskId}` и «Тело запроса → SYSTEM-сообщение в сессию состояния»; API/workflow-domain: `POST /api/webhooks/tasks/{taskId}`, payload → `reason` (WAIT_WEBHOOK — состояние без сессии). **Предложение:** синхронизировать глоссарий с API (путь + «payload → reason, опционально доступен следующему состоянию»); опциональный `&source=` из глоссария отразить в API.

### MIN-11. Export как POST; 401 без challenge
- **Место:** §1 `POST .../export { format } → 200 file` — безопасная операция через POST теряет кэшируемость; лучше `GET /export?format=`. §5 `signature-invalid → 401` — по RFC 9457/7235 стоило бы указать `WWW-Authenticate` (или использовать 403, раз challenge невозможен). **Предложение:** `GET`-форма; для 401 вебхуков зафиксировать отсутствие challenge явно.

### MIN-12. Bulk-зависимости: частичный отказ не определён
- **Место:** §3 `POST /tasks/{id}/dependencies { blockedBy: [taskId] }` — если один из id невалиден/циклическая зависимость: 204 без него? 422 целиком? **Предложение:** атомарно: 422 со списком невалидных, либо 207/частичный ответ. Указать запрет self-dependency и циклов.

### MIN-13. Скачивание артефактов workspace не покрыто даже как out-of-scope
- **Место:** глоссарий §8 (WebUI: «кнопка скачать»). В API нет ни эндпоинта, ни пометки out-of-scope. **Предложение:** добавить явный раздел «Не входит в v1» с этим пунктом, чтобы отсутствие не считалось дырой.

### MIN-14. Публичные вебхуки: нет указаний по rate limiting; `source` потерян
- **Место:** §3. Неаутентифицированные эндпоинты — кандидат на абьюз (перебор подписи по известным taskId дёшев не является, но спам запросами реален). Глоссарийный `&source=...` для task-вебхука в API не упомянут. **Предложение:** зафиксировать базовый rate-limit на `/api/webhooks/**`; включить `source` в контракт (параметр reason'а).

### MIN-15. runtimeStatus для «ждёт клиента CLIENT_EXEC»
- **Место:** §1/§4. «Turn паркуется, задача WAITING» — но PARKED_ASYNC зарезервирован для async-тулов. **Предложение:** отдельное значение `WAITING_CLIENT` или отдельное поле; иначе клиенты не отличат ожидание инструмента от ожидания исполнителя.

### MIN-16. `GET /sessions`: недоопределены параметры
- **Место:** §1: тип `mine` (bool?), сортировка списка (expected: lastActivityAt desc), поведение `q` (по title only?), фильтр архивных (см. M-5). **Предложение:** специфицировать типы, дефолтную сортировку и семантику поиска.

## 2. Новые проблемы v2

### N-1. `webhookUrl` выдаётся TASK-VIEW — read-only уровень получает capability записи
- **Severity:** MAJOR
- **Место:** §4.4 («полем TaskDto (WAIT_WEBHOOK, TASK-VIEW)»), §4.1 TaskDto.
- **Описание:** VIEW определён как «видеть и attach-иться на чтение», но держатель TASK-VIEW получает в TaskDto готовый capability-URL, POST по которому **переводит задачу** (переход NEXT). Read-only грант, декорированный правом записи, — нарушение семантики уровней (и потенциальная эскалация: участник-наблюдатель может подделать payload перехода).
- **Предложение:** Отдавать `webhookUrl` только владельцу и TASK-PARTICIPATE (поле опускается для VIEW) либо вынести в отдельный эндпоинт с правом PARTICIPATE.

### N-2. Курсор потоков задачи не определён
- **Severity:** MAJOR
- **Место:** §3.2 `GET /tasks/{id}/events?since=`, §4.1 `history?since=&limit=`; §0.4 («events, history — `?since=<seq>` … `nextCursor` = max seq»).
- **Описание:** У `task_transition_history` нет `seq`: PK — uuid (`id`), индекс по `created_at`. Что такое `since` для history и task-events (uuid v7 id? created_at? отдельный монотонный номер?) — не определено; гарантия монотонности курсора не зафиксирована. Новый task-SSE без определённого курсора нереализуем корректно (пропуски/дубли при реконнекте).
- **Предложение:** Определить: либо монотонный `event_seq`/`history_seq` (bigint per task), либо курсор = uuid v7 `id` с явным правилом сортировки и обработкой коллизий в пределах миллисекунды.

### N-3. Черновой остаток в нормативной матрице прав + видимость `params` не отражена в TaskDto
- **Severity:** MAJOR
- **Место:** §7 («TaskDto (без params при PRIVATE-владельце? — нет: params скрыт не-владельцу)»), §4.1 TaskDto (`params` без оговорки).
- **Описание:** В матрице прав остался мусорный текст внутреннего диалога («…? — нет: …»). Правило «params скрыт не-владельцу» — security-релевантное, но (а) сформулировано двояко, (б) не отражено в TaskDto §4.1, из которого генерируется SDK (поле присутствует без условной видимости).
- **Предложение:** Переписать строку матрицы («params — только владельцу»), в §4.1 пометить поле `params` условием видимости.

### N-4. Иероглифы в нормативном тексте
- **Severity:** MINOR
- **Место:** §0.4 «полуг开放的 интервалом».
- **Описание:** Порча текста при редактировании («полуоткрытым»). В нормальном правиле пагинации.
- **Предложение:** «полуоткрытым интервалом».

### N-5. `workspace/files`: нет листинга и containment-инварианта
- **Severity:** MINOR
- **Место:** §2 `GET /sessions/{id}/workspace/files?path=<rel>`.
- **Описание:** (а) Клиент не может узнать, какие файлы есть (листинга нет) — «кнопка скачать» WebUI требует хотя бы `GET .../files?path=` → листинг директории. (б) Не зафиксировано требование containment: `path` строго внутри корня workspace, запрет `..`/symlink-выход — стоит прописать инвариантом спеки, а не надеждой на реализацию.
- **Предложение:** Определить режим листинга (например, `?path=` на директорию → JSON-список) и инвариант containment с `400 path-invalid`.

### N-6. Остатки синхронизации вебхучных схем
- **Severity:** MINOR
- **Место:** `workflow-domain.md` §3 (строка WAIT_WEBHOOK: старый `POST /api/webhooks/{taskId}?signature=HMAC(secret, taskId)`); `decisions.md` D-05.
- **Описание:** §7 workflow-domain синхронизирован, §3 — нет (старая схема в таблице состояний). D-05 формально противоречит D-26 и не помечен superseded.
- **Предложение:** Поправить строку §3; в D-05 добавить пометку «superseded by D-26».

### N-7. `TransitionDto` не определён
- **Severity:** MINOR
- **Место:** §3.2 (`task.transition (TransitionDto)`), §4.1 history.
- **Описание:** SDK генерируется из спеки, но форма TransitionDto (fromState, toState, kind, reason, createdAt?) не задана — выводится из data-model по умолчанию.
- **Предложение:** Описать DTO явно (включая усечение `reason` в SSE-событии, если планируется).

### N-8. Владелец/автор задач, создаваемых агентом и триггером
- **Severity:** MINOR
- **Место:** §4.1 POST /tasks (user-создание описано), инструменты оркестратора, §4.3 триггер.
- **Описание:** Не определено: кто становится `owner`/`author` задачи, созданной агентом-оркестратором из сессии (owner = владелец сессии? author = NULL?), и задачи, созданной триггером (owner = владелец триггера?). Наследуется ли owner подзадачам? Влияет на все проверки видимости.
- **Предложение:** Зафиксировать правила владения для agent-created и trigger-created задач.

### N-9. Гигиена схемы данных
- **Severity:** MINOR
- **Место:** data-model §6.
- **Описание:** `idempotency_key` — нет PK/UNIQUE `(key, scope)`, нет индекса по `expires_at` (чистка/поиск); `trigger` — нет индекса по `revoked_at`/`workflow_key`.
- **Предложение:** Дописать ключи и индексы.

### N-10. `attachments` молча удалены из POST /messages
- **Severity:** MINOR
- **Место:** §2 `POST /messages` — v1: `{ text, attachments? }`, v2: `{ text }`.
- **Описание:** Изменение контракта не отмечено ни в спеке, ни в §8 (out-of-scope), ни в ADR.
- **Предложение:** Либо вернуть поле, либо зафиксировать удаление (в §8 или changelog v2).

### N-11. `lastTurnOutcome` без источника в data-model
- **Severity:** MINOR
- **Место:** §1 SessionDto vs data-model §5 `session`.
- **Описание:** Таблицы Turn нет (D-04), в `session` поля исхода последнего Turn'а тоже нет. Проекция из `cancel_requested`/локов `FAILED` не выводит — нужен источник (колонка в `session` или явное признание ephemeral-поведения после рестарта).
- **Предложение:** Добавить `last_turn_outcome` в `session` (или указать правило реконструкции).

### N-12. Мелкие несостыковки
- **Severity:** MINOR
- **Место/описание:**
  - нумерация §1: подразделы 1.4–1.6 без 1.1–1.3;
  - `GET /api/v1/workflows` — графы и метаданные **чужих** шаблонов видны всем аутентифицированным (модель «публичная библиотека шаблонов» не заявлена явно — подтвердить);
  - `POST /api/v1/triggers { workflowKey }` — можно создать триггер на чужой workflow (связать с предыдущим пунктом);
  - `GET /api/v1/folders` — без `cursor/limit` вопреки §0.4;
  - выбор NEXT vs ERROR при приёме task-вебхука: workflow-domain §3 допускает «ERROR по семантике workflow», но контракт вебхука не определяет, чем определяется исход;
  - `POST /api/v1/auth/ticket → 201` — §0.7 требует `Location` для всех 201 (билет — не ресурс; оговорка или 200).
- **Предложение:** Точечные правки текста.
