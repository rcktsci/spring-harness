# Ре-аппрув: `silent-refresh-single-flight` (закрытие F1–F4)

Рецензент: субагент-ревьюер (DeepSeek-V4.1-Flash). Дата: 2026-09-25.
Вход: текущее рабочее дерево (`web-desktop/src/main/auth.ts`, `index.ts`, `tests/unit/auth-refresh.test.ts`), delta-спека `desktop-shell`, design, отчёт `docs/temp/silent-refresh-single-flight-glm.md`.
Мой прежний вердикт: reject (F1 major — logout во время in-flight refresh «воскрешал» сессию; F2 429; F3 тело 2xx; F4 гигиена теста). Сборка/тесты/docker не запускались; проверял по коду.

## F1 (major): инвалидация in-flight при смене сессии — ЗАКРЫТО

- **Эпоха сессии:** `auth.ts:256-257` (`refreshInFlight` + `sessionEpoch`). `invalidateSession()` (`:264-266`) инкрементит эпоху; `terminateSession()` (`:268-271`) инкрементит и чистит токены.
- **Все пути явной смены сессии покрыты:** `logout()` вызывает `invalidateSession()` + `clearTokens()` (`:379-388`, инвалид на `:382`); смена issuer в конфиге — `main/index.ts:210-213` (`clearTokens` + `invalidateSession`); терминальные очистки (нечитаемое хранилище `:300-302`, нет refresh-токена `:311-314`, отказ гранта `:339-341`) идут через `terminateSession()`. Других `clearTokens`/`saveTokens` в main нет (grep: только logout, issuer-change, terminateSession, login-exchange `:224`, doRefresh `:332`).
- **`doRefresh` захватывает эпоху до сети** (`:325`) и при расхождении не сохраняет и не отдаёт токен: успех — `:328-331` (return null, `saveTokens` не вызывается), ошибка — `:336-338` (выход без повторного `clearTokens` поверх logout). Ожидающие получают `null` → `requireAccessToken` кидает «Not signed in».
- **Тест ровно на регресс:** `auth-refresh.test.ts:179-200` — 3 параллельных `requireAccessToken`, refresh в полёте, `logout()` → release 200 → все реджектятся, `store.save` не вызван, `store.tokens===null`, `readLoginState=c loggedIn:false`. Детерминирован (fetch-mock выставляет `release` синхронно до `await`).
- baseUrl-без-issuer смена токены не чистит и token-endpoint не меняет — инвалидация ей не требуется; «воскрешения» там нет.

## Легитимный single-flight не сломан — ЗАКРЫТО

Проверка эпохи — только внутри `doRefresh`, эпоха в пределах пачки неизменна: тест `:59-72` (5 параллельных → 1 fetch, все `'fresh'`, 1 save), `:122-137` (новая пачка после транзиентной ошибки), `:139-150` (свежий токен → 0 fetch). После logout `loadTokens()` пуст → ранний `null` (`:304-306`), повторный join стухшего обещания не происходит; после нового логина свежие токены короткозамыкают refresh (`:307-310`). Висящего обещания нет: `doRefresh` не реджектит, `.finally` (`:317-319`) сбрасывает.

## F2/F3/F4 — ЗАКРЫТЫ

- **F2:** `auth.ts:124` — терминальный только 4xx **кроме 408/429**; тест `auth-refresh.test.ts:152-162` (`it.each([408,429])` → `clear`/`save` не вызваны). Delta-спека (`desktop-shell/spec.md:11,53-56`) и D-2 (`design.md:26-28`) синхронизированы.
- **F3:** аномальный 2xx несёт тело: JSON-parse-fail (`auth.ts:133`) и parseTokenResponse-fail (`:136-141`) оборачиваются в `RefreshTransientError` с телом; тест `:164-177`.
- **F4:** `afterEach(() => vi.unstubAllGlobals())` (`auth-refresh.test.ts:55-57`); тесты используют `vi.resetModules()` + динамический импорт — модульное состояние (`refreshInFlight`/`sessionEpoch`) изолировано по тестам, флейка не вижу.
- Delta-спека дополнена двумя сценариями: «logout во время обновления» (`:48-51`) и «rate limit не логинит заново» (`:53-56`); поведение соответствует коду.

## Остаточные замечания (не блокируют)

1. **(minor, hardening) Тело 2xx-ответа token endpoint уходит в текст ошибки/лог.** `auth.ts:133,140` включают сырой `text` для аномального 2xx. 2xx-ответ token endpoint по природе — место, где живут токены; если тело окажется «успешным» JSON с `refresh_token`, но без `access_token` (или усечённым), refresh-токен попадёт в plain-text `main.log` в обход требования «plain-text хранение токенов запрещено». На целевом корпоративном Keycloak сценарий аномальный, поэтому minor. Рекомендация: для 2xx не эхоть сырое тело (достаточно перечня ключей/длины), тело оставить только для `!res.ok` (там токенов нет).
2. **(minor, док) `design.md:9` (Goals) всё ещё говорит «4xx» без исключения 408/429** — D-2 (`:26-28`) и спека точны; привести Goals к той же формулировке.
3. **(minor) Пути «нет refresh-токена» (`:311-314`) и «нечитаемое хранилище» (`:300-302`) вызывают `terminateSession()` на каждого параллельного вызывающего** → на пачку возможно несколько `clearTokens` (идемпотентно, эпоха просто растёт). Спека обещает «не более одного раза на пачку»; для refresh-пачки так и есть, для этих двух веток — буквальная мелочь (унаследовано).
4. **(observation) `invalidateSession()` не обнуляет `refreshInFlight`.** После logout повторный вызов всё равно короткозамыкается на пустом хранилище/свежих токенах, поэтому практической гонки нет; обнуление `refreshInFlight` в `invalidateSession` сделало бы инвариант жёстче.
5. **(observation, вне scope) login-путь `saveTokens` (`auth.ts:224`) эпохой не защищён** — теоретический race «logout во время code exchange». Недостижимо: окно логина модальное, main-окно заблокировано, logout в этот момент не нажать.

## Итог

F1 закрыт по существу и с регрессионным тестом: logout/смена issuer/терминальные очистки инвалидируют in-flight refresh, результат отбрасывается без `saveTokens` и без выдачи access-токена ожидающим, сессия остаётся завершённой. Single-flight и «следующая пачка» не сломаны; 408/429 транзиентны; аномальный 2xx диагностируется телом; тесты детерминированы и гигиеничны. Остаток — hardening-мелочи (эхо 2xx-тела, формулировка Goals), не нарушающие требования.

# Дополнение: проверка hardening-фикса маскирования тела (2026-09-25)

Запрос: закрыт ли отмеченный мной риск «сырое тело token endpoint в тексте ошибки/лог». Заявлено: `sanitizeBody()` во всех четырёх местах refresh-ошибок, маскирование полей по имени (`token`/`secret`/`password`/`credential`, регистронезависимо, с вложенностью), `BODY_LOG_LIMIT_CHARS`, два теста.

## Что подтверждено

- **Маскирование на refresh-пути есть во всех четырёх точках**: `auth.ts:152` (grant), `:154` (transient !ok), `:160` (non-JSON), `:167` (аномальный 2xx). Сетевой `unreachable` (`:120`) тела не несёт.
- **`maskSecrets`** (`:110-123`): регистронезависимо (`key.toLowerCase().includes(part)`), массив/объект рекурсивно, имена полей сохраняются, значения секретных полей → `[masked]`. `sanitizeBody` (`:125-131`) клампится `BODY_LOG_LIMIT_CHARS=512` (`:106`).
- **Успешный путь не затронут**: `parseTokenResponse(parsedBody)` (`:158,164`) работает с исходным телом; `sanitizeBody` вызывается только при построении строк ошибок — разбор ответа не ломается.
- **Диагностика не ослепла**: имена полей и `scope` видны (`test:190`), тело причины остаётся.
- **Тесты**: `auth-refresh.test.ts:179-193` (mask `refresh_token`/`id_token`, `SECRET-RT`/`SECRET-IDT` отсутствуют, `scope` виден), `:195-207` (обрезка oversized-тела). Тест `:164-177` обновлён под маскирование.

## Остаточные замечания (не блокируют)

1. **(minor) Не все места вывода тела token endpoint санитизированы.** `exchangeCode` (`auth.ts:96-97`) по-прежнему бросает `token endpoint ${res.status}: ${text}` с сырым телом; далее оно логируется `log.error('code exchange failed', err)` и уходит в `LoginResult.message` (`:250-258`). Токен-утечки нет — это ветка `!res.ok` (тело Keycloak-ошибки, без токенов), и аномальный 2xx там не логируется вовсе, поэтому исходный риск закрыт. Но чек «нигде не осталось несанитизированного вывода тела token endpoint» формально не выполнен. Требование: применить `sanitizeBody` и там (или явно задокументировать исключение login-exchange).
2. **(minor) `maskSecrets` не маскирует потомков секретного ключа-контейнера.** Проверка имени срабатывает только на примитивах (`:119`), а ветки массива/объекта (`:111,114`) ключ игнорируют: `{"tokens":["<jwt>"]}` и `{"token":{"value":"<jwt>"}}` остаются немаскированными. Для реальных форм Keycloak (токены — строковые поля `access_token`/`refresh_token`/`id_token`) утечки нет; «с вложенностью» выполнено для вложенных *полей*, но не для поддерева под секретным ключом. Рекомендация: при совпадении ключа маскировать всё поддерево.
3. **(minor) Fallback для не-JSON тела (`:129`) только обрезает, но не маскирует.** Если прокси вернёт токен как plain-text (не Keycloak-кейс), первые 512 символов уйдут в лог. Рекомендация: редactить JWT-подобные подстроки и в fallback.

## Итог дополнения

Исходный hardening-риск закрыт: тела-ответы (включая аномальный 2xx) на refresh-пути санитизируются, успех не задет, диагностика сохранена, тесты есть. Остаток — согласованность (`exchangeCode:97`) и теоретические формы вложенности — minor.

# Дополнение 2: закрытие minor-остатков маскирования (2026-09-25)

Проверка заявленного: (1) проверка ключа перенесена в начало `maskSecrets` → маскируется всё поддерево; (2) `exchangeCode` `!res.ok` через `sanitizeBody`; (3) `JWT_LIKE_PATTERN` для не-JSON.

## Что подтверждено

- **(1) Поддеревья закрыты.** `auth.ts:111-124`: проверка `SECRET_KEY_PARTS` теперь **до** веток массива/объекта (`:112-114`), поэтому значение под секретным ключом маскируется целиком (объект/массив/скаляр, любая глубина) → `[masked]`; несекретные поля и имена сохраняются. Прежний обход (`{"tokens":[…]}`, `{"token":{…}}`) закрыт. Тест `auth-refresh.test.ts:195-215` (`credentials`-объект и `tokens`-массив → `"[masked]"`, `scope`/окружение видно, внутренние ключи отсутствуют). Успешный путь не задет: `parseTokenResponse(parsedBody)` (`auth.ts:169`) работает с исходным телом, `sanitizeBody` — только в текстах ошибок (`:157,159,165,172`).
- **(2) Сырого тела token endpoint нет нигде.** `exchangeCode` теперь `token endpoint ${res.status}: ${sanitizeBody(text)}` (`auth.ts:96-97`); grep по `.text()` даёт только `:96` и `:154`, оба пути санитизированы; `unreachable` (`:152`) тела не несёт. Ранее мой единственный leftover закрыт.
- **(3) JWT-подобные в не-JSON.** `JWT_LIKE_PATTERN = /[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}/g` (`:109`), `maskJwtLike` (`:126-128`) в fallback `sanitizeBody` (`:134`) до обрезки. Тест `:217-230` (`AccessToken: eyJ…‥.…` → `[jwt-like]`, окружающий текст сохранён, сегменты отсутствуют). Ложные срабатывания маловероятны: нужны три base64url-сегмента по 8+ через точки (хосты/версии/UUID без точек не матчатся); сохранены имена и форма ошибки — диагностика не ослепла.
- **Артефакты синхронизированы.** `design.md:35` (D-3) описывает маскирование поддерева, JWT-паттерн, санитизацию `exchangeCode`, `BODY_LOG_LIMIT_CHARS`; `tasks.md:34-45` (6.1-6.4, 7.1-7.5).

## Остаточные наблюдения (не блокируют)

- `maskJwtLike` применяется только к не-JSON fallback: JWT-подобная строка внутри **JSON** под несекретным ключом (напр. `error_description`) не маскируется — для Keycloak JSON-ошибок токены там не встречаются, риск теоретический. Также top-level JSON-массив строк и `[jwt]` под несекретным ключом вне маскирования. Рекомендация (опционально): прогнать `maskJwtLike` и по сериализованному JSON-результату.
- Delta-спека `desktop-shell/spec.md:11` формулирует «текст ошибки SHALL содержать тело ответа», но не упоминает санитизацию; инвариант «без секретов» живёт в design D-3/tasks. Желательно добавить клаузулу в требование спеки.

## Итог дополнения 2

Оба моих minor закрыты по существу: `exchangeCode` санитизирован, поддеревья под секретными ключами маскируются целиком, не-JSON JWT-подобные вырезаются; успешный разбор не задет, диагностика сохранена, тесты ловят регресс, артефакты синхронизированы. Остаток — теоретические формы в JSON-ветке и формулировка спеки — minor.
