## Находки

### CRITICAL-1: Гейт неизменяемости проверяет несуществующий тег `vv<версия>`

- Место: `.github/workflows/backend-image.yml:52`
- Код: `IMAGE="ghcr.io/${{ github.repository_owner }}/spring-harness-orchestrator:v${GITHUB_REF_NAME}"`
- Почему дефект: на теговом прогоне `GITHUB_REF_NAME` равен полному имени тега **с** префиксом, т.е. `v0.1.0`. Конкатенация даёт `...:vv0.1.0` — тег, который никогда не публикуется (metadata-action публикует `v0.1.0` через `{{raw}}` и `0.1.0` через `{{version}}`). `docker buildx imagetools inspect` на такой тег стабильно отвечает «not found», условие на строке 53 всегда ложно, ветка fail (строки 54–56) недостижима.
- Последствие: повторный пуш того же релизного тега (в т.ч. `git tag -f` + force-push) проходит гейт и **перезаписывает** опубликованный релизный образ в GHCR. Нарушены: задача 2.3 (пункт 2), D-CI13/D-CI16, требование спеки release-policy «Релизные теги неизменяемы» (оба сценария). Согласуется с тем, что в прогоне разработчика негативно проверялся только гейт version-mismatch; иммутабельность негативом не накрывалась (для неё нужен реально опубликованный тег).
- Исправление: убрать лишний префикс — либо
  `IMAGE="ghcr.io/${{ github.repository_owner }}/spring-harness-orchestrator:${GITHUB_REF_NAME}"` (имя тега уже с `v`),
  либо `IMAGE="ghcr.io/${{ github.repository_owner }}/spring-harness-orchestrator:v${TAG}"` (используя переменную без префикса со строки 42). Любой из вариантов проверяет реально публикуемый тег `v0.1.0`.

### MINOR-1: Ошибка registry неотличима от «тега нет» в гейте неизменяемости

- Место: `.github/workflows/backend-image.yml:53`
- Код: `if docker buildx imagetools inspect "$IMAGE" >/dev/null 2>&1; then`
- Почему дефект (мягкий): любой ненулевой код выхода — сетевая ошибка, отказ авторизации, rate-limit — трактуется как «тег отсутствует», и гейт пропускает прогон дальше. После исправления CRITICAL-1 остаётся окно: транзиентный сбой `inspect` при живой публикации может пропустить перезапись релизного тега. Устойчивость при «недоступном registry» — явно запрошенный сценарием проверки.
- Исправление: различать исходы — захватить вывод/код (`out=$(docker buildx imagetools inspect "$IMAGE" 2>&1)`), при успехе — fail (тег есть), при ошибке типа manifest/unknown — пропуск (тега нет), при любой иной ошибке — `::error::` + `exit 1` (fail-safe). Достаточно одного дополнительного ветвления, без новых зависимостей.

## Фикс MINOR-1 (fail-safe при недоступном registry) — принят

- Место: `backend-image.yml:62-79`
- Логика корректна: успешный `inspect` → `::error::` + `exit 1` (тег есть, публикация запрещена); вывод с `not found|no such manifest|manifest unknown` → `exit 0` (тег отсутствует); нераспознанная ошибка → `::warning::` + `sleep 5` + retry, после 3 попыток `::error::` с последним выводом + `exit 1`. Публикация при неопределённости не происходит — fail-safe в безопасную сторону.
- Бонус: блоки `VAR="$(python3 ... 2>&1)" || { ::error::...; exit 1; }` (строки 44-54) дают внятные сообщения вместо сырого traceback; сообщение version-mismatch дополнено ожидаемой формой `v${TAG}` (строка 57). `VAR="$(...)" || {...}` при `set -e` корректен (часть составной команды, errexit не срабатывает).
