# Кросс-чек: `desktop-ui-robustness` — DeepSeek (reject) vs Mercury (approve)

Рецензент: субагент-ревьюер (DeepSeek-V4.1-Flash). Дата: 2026-09-25.
Мой отчёт: `docs/temp/review/desktop-ui-robustness-deepseek.md` (reject, F1 major).
Отчёт коллеги: `docs/temp/review/desktop-ui-robustness-mercury.md` (approve).

Суть расхождения одно: я счёл отсутствие at-most-once на consent-диалоге major-дефектом (второй клик → второй IPC → `pendingConsent` → тихий обход согласия); Mercury этот путь вообще не разбирал. Ниже — проверка достижимости по коду, а не по описанию.

---

## 1. Ключевой пункт: достижим ли «второй клик → второй IPC → тихий обход consent»?

**Вердикт по пункту: не достижим на практике; моя квалификация major была завышена. Соглашаюсь с Mercury (approve) по этому пункту.**

Механика, как я её описал, в коде есть (ни одного явного guard'а at-most-once нет):

- `web-desktop/src/renderer/src/components/RelayDialogs.vue:44-59` (consent approve/deny) и `:77-92` (tool-confirm) — кнопки без `:disabled`/in-flight флага.
- `web-desktop/src/renderer/src/composables/useRelay.ts:87-98` — `respondConsent`/`respondToolConfirm` читают текущий prompt, `await`-ят IPC, очищают только после успеха; синхронной очистки (как в `9976660`) больше нет.
- `web-desktop/src/main/relay-client.ts:725-737` — `resolveRegistrationConsent` на повторный вызов без резолвера безусловно кладёт ответ в `pendingConsent` (`:735`), а `requestRegistrationConsent` (`:707-710`) затем потребляет его без диалога.

Но **достижимость второго IPC детерминированно не следует**. Второй `click` обработается только если кнопка ещё в DOM. Кнопка исчезает, потому что `consent.value = null` (`useRelay.ts:91`) снимает весь `<div v-if="relay.consent.value" class="overlay">` (`RelayDialogs.vue:26-30`). Vue 3 планирует патч DOM в microtask (`nextTick`), а второй `click` — это отдельная macrotask; microtasks вычерпываются до следующей macrotask. Значит, DOM-патч выполняется раньше второго клика, если только ответ IPC не придёт позже второго клика. Первый IPC — это `ipcRenderer.invoke` в main, где `RELAY_CONFIRM_REGISTRATION` (`web-desktop/src/main/index.ts:382-385`) синхронный и возвращается немедленно (не блокируется очередью длинных синхронных handler'ов — остальные обработчики async). Типовая задержка ответа ~1-5 мс, а человеческий второй клик — ~50-200 мс. То есть в нормальном режиме ответ и Vue-патч «выигрывают» у второго клика, и он попадает в уже удалённый элемент (или подложку), а не в кнопку.

Требуемое для бага условие — блокировка event loop main-процесса дольше интервала между кликами (>~50-200 мс) в момент ответа. Это редкий стук (нет длительных синхронных handler'ов, сокет/сеть в main асинхронны), а не штатный путь. Программного/клавиатурного пути ускоренного повторного ответа нет (обе кнопки — обычный `@click`, авто-repeat с клавиатуры медленнее IPC и упирается в тот же unmount).

Доводы против «protected path» — тоже не в пользу бага: guard'а нет, инвариант держится на тайминге Vue/IPC. Но именно потому, что он держится, и потому что **blast radius ограничен той же сессией, по которой пользователь первый клик уже отправил**, назвать это live-багом и блокером нельзя. Даже в редком срабатывании последствие — пропуск повторного диалога при *следующей* регистрации той же сессии, уже однажды одобренной этим же пользователем в этом же запуске; это не «не-согласованное исполнение».

Также delta-спека `desktop-ui-robustness/specs/desktop-relay-client/spec.md:23-35` («Устойчивость ответов диалогов») требует ровно: при сбое доставки состояние сохраняется и ответ можно повторить (`useRelay.ts:87-98` — выполнено), при успехе очищается (`:91,97` — выполнено). Требования at-most-once в спеке нет. D-93 требует per-session consent при первой регистрации — он выдаётся; редкий пропуск повторного диалога для той же сессии не отменяет уже выданное согласие.

**Вывод:** мой F1 — **minor defensive hardening**, не major и не блокер. Рекомендую (необязательно) добавить at-most-once (флаг «ответ в полёте» по объекту prompt и/или `:disabled`) и/или в main не буферизовать ответ при `openConsent === null`; тест на два вызова. Вердикт reject на этом основании не держится.

## 2. Точность отчёта Mercury

- **Согласен по существу вердикта** (A/B/C1/C2 исправлены) — совпадает с моим разбором кода.
- **Несогласен с таблицей «Сверка с delta-спеками»** (`mercury:63-74`): сопоставления перепутаны. Строка «A: disconnect терминалирует регистрацию» сопоставлена с текстом «При отказе согласования клиент SHALL эмитить статус с причиной отказа» — это требование **предыдущего** change'а, а не новое «Очистка регистрации при разрыве»; C1 сопоставлен с ADDED «Очистка регистрации при разрыве» (тоже неверно); строка про каталог агентов (`desktop-chat`) сопоставлена с фразой «Причина последней неудачи регистрации…», которая к каталогу агентов не относится. Сама реализация от этого не страдает (я сверил delta-спеки напрямую: `desktop-ui-robustness/specs/desktop-relay-client/spec.md:9-35` и `.../desktop-chat/spec.md:9-31` — соответствуют коду), но таблица Mercury не является доказательством.
- **Находка #1 Mercury** (`mercury:118`: «Эмита статуса при отказе согласия нет») — неверна/запутана: статус при decline эмитится (`relay-client.ts:284-294`, это уже вошло в `9976660`), а не «принято, disconnect эмитит status». На итог не влияет.

## 3. Мои неблокирующие замечания — включать ли в фикс-раунд?

1. **`disconnect()` не чистит `confirmWaiters`/`cancelledCalls`** (`relay-client.ts:210-230`). Достижимость через UI ~нулевая: tool-confirm-оверлей (`RelayDialogs.vue:64-95`, `inset:0;z-index:100`) блокирует кнопку «Отключить», пока висит подтверждение; программный `disconnect()` (quit/config-change) не оставляет живого сокета, и ответ по висящему диалогу уходит в no-op. **В фикс-раунд не обязательно** — это отдельная косметика жизненного цикла, вне scope change'а.
2. **`electron-smoke.spec.ts:175` `rmSync(userData, …)` без `maxRetries`** (в отличие от `stub-server.ts:811` с `maxRetries:5`). Это потенциальный Windows-флейк (EBUSY/EPERM сразу после `app.close()`). Дешёвая симметричная правка — **стоит включить, но не блокер**: прогоны у разработчика зелёные, electron-smoke в CI — отдельный ручной шаг.

## 4. Итог

Расхождение снято: путь «второй клик → второй IPC → тихий обход per-session consent» детерминированно недостижим (Vue-патч DOM в microtask опережает второй `click`; IPC-хендлер синхронный и быстрый), а последствие даже при редком срабатывании ограничено уже одобренной пользователем сессией. Delta-спека at-most-once не требует. Мой F1 переквалифицирую в **minor** (defensive hardening, необязательно); неблокирующие замечания — тоже не блокеры. Реализация A/B/C1/C2 корректна, тесты ловят регресс, спеки соответствуют коду.

## ВЕРДИКТ по артефакту: `approve`
