## Класс 2 — противоречия между доками / внутри дока

### 2.1 roadmap M1 — билеты, AccessPolicy-каркас, users/groups-синхронизация
- **Док+раздел**: `roadmap.md` M1 vs нота под M1, D-41/D-42, api §8, security §1.
- **Дефект**: тройное: (а) M1 включает «билеты», а нота прямо под M1 и api §8 относят их к WebUI-фазе; (б) «AccessPolicy-каркас» — контракт выброшен; (в) «Keycloak-синхронизация users/**groups**» — группы в БД не моделируются, гейт читает claim из JWT.
- **Предложение**: объём M1: «identity (SSO-гейт groups-claim + синхронизация users)» без AccessPolicy и билетов.

### 2.2 workflow-domain §7 — threat-model обещает rate-limit и Idempotency-Key
- **Док+раздел**: `workflow-domain.md` §7, строка 75: «…опциональный `Idempotency-Key`, TLS-only, **rate-limit**» (со ссылкой на D-26).
- **Дефект**: противоречит security §4 («rate-limit — не делаем», D-41), api §0.3 («хранилища нет») и api §4.4 (в threat-model уже без rate-limit). D-41 сузил D-26, живой раздел не обновлён.
- **Предложение**: привести к формуле api §4.4: «идемпотентность по построению (`409` вне WAIT_WEBHOOK), TLS-only, логирование».

### 2.3 execution-model §6 + glossary §5 — «recovery добивает поддерево» = докатка отмен
- **Док+раздел**: `execution-model.md` §6 (строка 94), `glossary.md` §5 «CancellationToken-дерево» (строка 77) vs D-41 («докатка отмен — выброшено»).
- **Дефект**: оба живых раздела обещают recovery-спуск по БД, добивающий выжившее поддерево после падения — это и есть выброшенная докатка отмен. Семантика восстановления после crash в дереве субагентов теперь не определена.
- **Предложение**: зафиксировать фактическое поведение без отдельного механизма: «выжившие Turn'ы поднимаются POLL'ом после истечения TTL лока и немедленно гасятся по сохранённому `cancel_requested`/`pending_tool_calls`-скану». Обновить формулировки в обоих доках.

### 2.4 execution-model §1 vs §2 — один `lockAtMostFor` на два разных TTL
- **Док+раздел**: `execution-model.md` §1 («POLL… `lockAtMostFor` ~10 сек») vs §2 («TTL **сессионного** лока = `lockAtMostFor`… заведомо больше максимальной длины Turn'а»).
- **Дефект**: одна конфигурационная имя-константа описана с двумя несовместимыми семантиками (~10 сек для джобы vs >> длины Turn'а для сессии). Несущий механизм локов (класс 3) — риск неверной реализации.
- **Предложение**: развести параметры: `harness.poll.lockAtMostFor` (джоба) и `harness.session.lockTtl` (сессия), heartbeat-интервал отдельно.

### 2.5 decisions — superseded-строки без пометок
- **Док+раздел**: `decisions.md` D-16, D-18, D-27, D-28, D-29, D-32, D-34, D-36, D-37, D-38 vs D-41.
- **Дефект**: D-41 выбрасывает их части, но сами строки читаются как действующие решения. Особенно: D-29 («идемпотентность POST — хранилище `idempotency_key` TTL 24ч»), D-34 («message_count/tokens_total», «share/group_member lookups»), D-37 («stop_grace_period 45s»), D-36 («докатка отмен») — читатель следует им мимо D-41.
- **Предложение**: в superseded-строки добавить суффикс «частично отменено D-41 (см. список)» — журнал append-only, правка = пометка, не переписывание.

### 2.6 api SessionDto/TaskDto `workspaceBinding(s)` — нет источника в модели
- **Док+раздел**: `api-contracts.md` §2 SessionDto, §4.1 TaskDto vs `data-model.md` §5 (`session` без полей биндинга).
- **Дефект**: API обещает `workspaceBinding { type, pathTemplate?, logicalKey? }` / `workspaceBindings: [{ stateCode, logicalKey }]`, но в схеме биндинг нигде не хранится и не описан как вычисляемый.
- **Предложение**: пометить в api/data-model как проекцию: FREE — `SERVER_DIR auto` из `{sessionId}`; STATE — из `workspace`-декларации состояния пиннутой ревизии.

### 2.7 glossary §8 — «первый/второй клиент, позже» vs D-42
- **Док+раздел**: `glossary.md` §8 («Attach-CLI… Первый клиент», «WebUI… Второй клиент, позже») vs D-42, roadmap-нота, api §8.
- **Дефект**: глоссарий фиксирует порядок, который D-42 сделал гибким.
- **Предложение**: «целевые клиенты; порядок ввода — по D-42».

### 2.8 roadmap M4 — «скачивание workspace-файлов» vs WebUI-фаза
- **Док+раздел**: `roadmap.md` M4 vs нота под M1 и api §8.
- **Дефект**: нота и api §8 относят скачивание workspace-файлов к WebUI-фазе, а M4 (CLI-фаза) включает его в объём.
- **Предложение**: либо исключить из M4, либо явно пометить «REST-эндпоинт — здесь, UI-кнопка — WebUI-фаза» (сейчас client-cli §3 склоняется ко второму — зафиксировать в api §8).

### 2.9 glossary Eligibility — «сессия не терминальна»
- **Док+раздел**: `glossary.md` §4 Eligibility (строка 63), `execution-model.md` §1 (строка 32) vs `data-model.md` §5.
- **Дефект**: у сессии в схеме нет признака терминальности (видимо, имеется в виду «задача не в TERMINAL»).
- **Предложение**: переформулировать: «задача (для STATE) не в терминальном состоянии».

### 2.10 agent-tools §2b vs §4 — статус metaTools после D-41 (низкий приоритет)
- **Док+раздел**: `agent-tools.md` §2b («Доступны только агентам, у которых `permissions_jsonb.metaTools = true`») vs §4 (в `permissions_jsonb` описаны только `allowedTools`, `workspaceScope`) и D-41 («metaTools-гейт — выброшено»).
- **Дефект**: не разведены (а) выброшенный гейт из D-38 «metaTools только при instructionSource=USER» и (б) остающийся флаг-allowlist; флаг не описан в контракте §4.
- **Предложение**: в §4 добавить `metaTools: bool` как элемент allowlist'а инструментов; в §2b снять двусмысленность слова «гейт».

1. **2.3 / 1.1** — семантика восстановления отмены: `execution-model` §6 и глоссарий обещают recovery-добивание поддерева (докатка отмен), которое D-41 выбросил; плюс в схеме остались 4 колонки fork/rewind/archive с зависимыми «не архивна»-условиями в трёх местах.
