## 0. Целевой масштаб и метод

**Масштаб (из задания):** 50+ пользователей (не все активны одновременно), десятки одновременных задач/сессий, сессии до тысяч сообщений с payload порядка MB; один инстанс на VM, Postgres рядом, LLM — корпоративный LiteLLM-подобный бэкенд (`glossary.md` §2).

**Рабочая модель ёмкости** (оценка для прикидок, не факт из доков):

| Параметр | Обозн. | Значение |
|---|---|---|
| Зарегистрированные / активно в час пик | U / Ua | 50+ / 15–30 |
| Одновременные сессии (задачи+подзадачи+субагенты) | S | 30–60 |
| Одновременные Turn'ы | T | 20–40 |
| Одновременные LLM-стримы (с учётом субагентов) | L | 50–120 |
| Сообщений в сессии | N | 10³–5·10³ |
| Размер одного payload | P | 0.2–1 MB (TOOL_RESULT-пики выше) |
| Объём `session_message` за год | M | 10⁵–10⁶ строк; десятки–сотни GB с TOAST |
| Тиков POLL | — | раз в ~5 с = 17 280/сутки — самый горячий запрос системы |

**Легенда вердиктов:**
- **OK** — по докам покрытие есть, на целевом масштабе укладывается.
- **RISK** — покрытие формально есть, но есть конкретный failure mode на целевом масштабе.
- **GAP** — ни поля, ни индекса, ни механизма в доках.

**Дисциплина:** отделяю **Факт** (ссылка на доку) от **Оценка** (моя прикидка). Риск без конкретного failure mode не засчитываю.

### Топ-3

1. **POLL-скан не проектируется «дёшево индексируемо» на текущей схеме** (A1+A2+A3+A5). Нет маркера «есть непоглощённые события» и позиции «конец последнего модельного хода», тип состояния живёт в `graph_jsonb` ревизии, дедлайнов нет. D-33 обещает «дёшево индексируемые сканы» — схема обещание не подтверждает, а тик каждые 5 с — самый горячий запрос системы.
2. **Неограниченный параллелизм к LLM-провайдеру** (D1+D2). Виртуальные потоки делают стримы «бесплатными» для JVM, но не для корпоративного LiteLLM: семафора нет, 429/5xx → `FAILED` (терминал задачи) без retry/backoff. Один утренний пик = массовый FAILED по всем задачам.
3. **Списковые API на сессиях со счётчиками и N+1** (F1+F2+F3). `SessionDto` требует `messageCount/tokensTotal/lastSeq` — агрегаты по таблице с MB-строками на каждый элемент страницы; плюс N+1 по `agent/owner/task` и сортировка по неиндексированному `last_activity_at`. Самый частый клиентский запрос деградирует первым.

Runner-up: E2+E3 — суммарная память/диск контейнеров на VM не ограничена и не квотируется; переполнение убивает весь инстанс (вместе с Postgres), а не одну задачу.

## 1. POLL: eligible-скан раз в ~5 с

### A1. Маркер «есть непоглощённые события» — **GAP**

**Факт.** Eligibility: «есть события после конца последнего модельного хода И не терминальна И не suspended И лок свободен/стух» (`execution-model.md:29`, `glossary.md` §4). POLL сканирует eligible-сессии раз в ~5 с (`execution-model.md:13`). В таблице `session` (`data-model.md:165–189`) **нет** ни поля «конец последнего модельного хода» (absorbed-позиция), ни материализованного `last_event_seq` — только `last_activity_at`, который не различает «дописали сообщение» и «сообщение поглощено Turn'ом».

**Оценка.** Без маркера предикат «есть события после X» вычислим только коррелятом с `session_message` (MAX(seq) на сессию) — на каждый тик по всем кандидатам. При тысячах сессий это 17 280 × N корреляционных подзапросов в сутки, растущих с ростом истории. D-33 («side-effects выводимы дёшево индексируемыми сканами») схемой не подтверждён.

**Предложение.** Денормализовать на `session`: `last_event_seq bigint` (обновляется транзакционно с INSERT сообщения — append-only делает это тривиальным) и `absorbed_seq bigint` (позиция конца последнего модельного хода, обновляется Turn'ом). Partial index: `ON session (...) WHERE last_event_seq > absorbed_seq AND archived_at IS NULL` — скан становится точным и пустым в спокойной системе.

### A2. Опорные индексы скана сессий — **GAP**

**Факт.** Единственный индекс в разделе `session` — `PARTIAL UNIQUE (task_id, state_code) WHERE kind='STATE'` (`data-model.md:189`). Нет индексов под фильтры скана: `archived_at IS NULL`, `locked_at` (стухшие локи), `cancel_requested`, терминальность.

**Оценка.** Даже с маркером из A1 скану нужен доступ по `archived_at IS NULL` + стухшие локи (`locked_at < now() - TTL`) без последовательного чтения таблицы сессий; при 5-секундном тике любая фулл-скан-составляющая × 17 280 в сутки — это постоянный фоновый IO и раздувание shared_buffers грязными страницами.

**Предложение.** Составной partial index под eligibility-предикат (см. A1) + отдельный дешёвый индекс `ON session (locked_at) WHERE locked_by IS NOT NULL` для TTL-освобождения стухших локов (и старт-скана №1). Заодно закрывает LRU-подозрение из `execution-model.md:19–22` на «одноразовые сканы при старте» — они тоже должны быть индексными.

### A3. «AGENT-задача без живой сессии» — **RISK**

**Факт.** POLL уровня задач: «задача в AGENT-состоянии без живой сессии → bootstrap» (`execution-model.md:15`). Тип состояния — только в `graph_jsonb` пина ревизии (`workflow-domain.md` §2); в `task` есть `current_state` (code) и `status_projection` (`data-model.md:123–124`). Индексы задачи: `(parent_task_id, status_projection)` и GIN `(tags)` (`data-model.md:132`).

**Оценка.** Предикат «current_state — AGENT-код» нельзя выразить индексируемо без денормализации: принадлежность code к AGENT-типу известна только из JSON-графа ревизии. Либо скан тащит все RUNNING-задачи + джойн ревизий + парсинг графа каждые 5 с, либо поле. Формально механизм есть (скан возможен), на масштабе десятков задач он ещё дёшев, но это единственная «дорогая» ветка POLL, и она растёт линейно с числом живых задач. Отсюда RISK, не GAP.

**Предложение.** Денормализовать `current_state_type enum(AGENT|BASH_SCRIPT|WAIT_WEBHOOK|WAIT_TASKS|TERMINAL)` на `task`, обновлять транзакционно вместе с `current_state`/`status_projection` (тот же CAS, `data-model.md` §7.2). Тогда весь уровень задач POLL — три индексных среза: `WHERE current_state_type='AGENT'` (плюс anti-join по живым сессиям), `status_projection='WAITING'`, `state_deadline_at < now()`.

### A4. WAIT_* переоценка: индекс по `status_projection` — **RISK**

**Факт.** POLL переоценивает `WAIT_TASKS / WAIT_WEBHOOK` (`execution-model.md:15`); поиск «кто ждёт» при терминалах — по `(parent_task_id, status_projection)` и `(blocked_task_id)` (`data-model.md:132,139`, `workflow-domain.md` §3). Отдельного индекса по `status_projection` нет — колонка индексируется только второй позицией составного индекса.

**Оценка.** Обратный wake (терминал подзадачи → родители) покрыт индексами — OK. Но страховочная переоценка «все WAITING-задачи» каждые 5 с без самостоятельного индекса — seq scan по растущему `task`. Сотни задач → сотни тысяч «лишних» строк в сутки на тик; терпимо, но противоречит декларации D-33 и бесплатно чинится.

**Предложение.** Partial index `ON task (id) WHERE status_projection = 'WAITING' AND suspended = false` — WAITING-множество на целевом масштабе десятки строк, индекс почти пустой.

### A5. Таймауты состояний (TIMEOUT) — **GAP**

**Факт.** WAIT_* обязаны иметь TIMEOUT-переход, для BASH_SCRIPT — обязателен, для AGENT — опциональный предохранитель (`workflow-domain.md:24,35`). В `task` нет ни `state_entered_at`, ни `deadline_at` (`data-model.md:114–132`); время входа в состояние можно вывести только из последней записи `task_transition_history` (INDEX `(task_id, created_at)`, `data-model.md:161`).

**Оценка.** Кто-то должен Period finding просроченные WAIT_*/BASH/AGENT-задачи. Вывод «вошли в состояние в T» = подзапрос последней истории на каждую задачу-кандидат — на каждый тик POLL это ровно тот корреляционный шаблон, который не масштабируется; а без A3/A4 нет даже списка кандидатов. Ни в execution-model, ни в workflow-domain механизм детекции таймаутов не описан (семантика перехода описана, детекция — нет).

**Предложение.** `task.state_deadline_at timestamptz NULL` + `state_entered_at timestamptz` (или только дедлайн, вычисленный из `timeout` графа при переводе), обновлять транзакционно с CAS перехода. POLL-ветка: `WHERE state_deadline_at IS NOT NULL AND state_deadline_at < now()` по partial index. BASH_SCRIPT закрывается тем же механизмом (запуск = переход).

## 2. Рост `session_message`

### B1. Bloat/vacuum при append-only — **OK**

**Факт.** Только INSERT, UPDATE/DELETE запрещены (`data-model.md:191–203,235`); COMPACT не мутирует строки — видимость производная от `covers` (D-17, `glossary.md` §4); fork «байты не копируются» (`glossary.md` §4); PK — UUID v7, генерация единая (`D-31`).

**Оценка.** Append-only без UPDATE → нет dead tuples от обновлений, autovacuum почти не работает на таблицу (кроме freeze); вставки в PK `(session_id, seq)` для новых сессий идут в «правый край» индекса (UUID v7 даёт временную локальность), старые сессии — в холодные диапазоны. Классический.best-case профиль для Postgres. Горячая точка одна: перезапись `session.absorbed_seq/last_event_seq` из A1 — это отдельная таблица с малыми строками, HOT справится (fillfactor — деталь реализации).

**Предложение.** Ничего. Зафиксировать в доке абзац «почему bloat не проблема» — чтобы при ревью миграций не «починили» append-only внезапным UPDATE.

### B2. Неограниченный рост: TOAST, retention, партиционирование — **RISK**

**Факт.** `payload_jsonb` с MB-payload уходит в TOAST (порог ~2 KB); retention на `session_message` отсутствует: «сессии не удаляются — резюмируемы» (`execution-model.md:86`), `archived_at` только скрывает из списков (`api-contracts.md:49`); export существует, но как канал высвобождения не описан. Рендер смягчает чтение: лёгкая проекция без payload → полные payload только видимых (`execution-model.md:76`) — это сильно.

**Оценка.** При M ≈ 10⁵–10⁶ строк с P ≈ 0.2–1 MB диск под TOAST растёт до десятков–сотен GB за год; бэкап/restore и `VACUUM FULL`-сценарии на такой таблице — уже часы. READ смещённого payload при рендере «старой» части сессии — случайные TOAST-фетчи, но компакция (~80% окна) ограничивает видимую часть — чтение под контролем. Проблема не в чтении, а в **только-растущем** объёме при отсутствии политики: retention упомянут ровно один раз и только для workspace (`glossary.md` §6 «чистится по retention»), для сообщений — ничего.

**Предложение.** (1) Зафиксировать retention-политику: архивация → N месяцев → export+cold-storage → удаление (или осознанное «не удаляем никогда» с budget на диск). (2) Заложить декларативное партиционирование по `created_at` (месяц) — пока можно просто задокументировать как точку эволюции в `architecture.md` §5. (3) Ограничить размер одного TOOL_RESULT-payload политикой усечения (например, 2 MB, хвост — в workspace-файл) — главный генератор MB-строк именно туловые выводы.

## 3. SSE

### C1. Keepalive, ticket, rate-limit — **OK**

**Факт.** `: ping` каждые 15 с + `retry: 5000` (`api-contracts.md:75`); ticket одноразовый, TTL 60 с, JWT в query запрещён (`api-contracts.md:26`); rate-limit на билеты per-user и на вебхуки (`api-contracts.md:17`); реконнект — `Last-Event-ID`/`?since=` со снапшотом статуса первым событием (`api-contracts.md:74`).

**Оценка.** Полукомплект жизненного цикла соединения продуман: прокси-таймауты держатся пингами, реконнект детерминирован курсором, аутентификация браузеров закрыта билетами. На 50+ пользователей и десятках attach-соединений — достаточно.

**Предложение.** Нет.

### C2. Лимиты соединений, backpressure, MB-фреймы — **RISK**

**Факт.** Событие `message.created` несёт **полный MessageDto** включая payload (`api-contracts.md:75,64`). Лимиты: только rate-limit на билеты (`api-contracts.md:17`); max-connections per user/instance, политика медленного потребителя, размер фрейма — не определены нигде.

**Оценка.** Failure modes: (1) клиент-зевака на MB-сессии: каждый viewer получает MB-фрейм на каждый `TOOL_RESULT` — десятки viewers × MB × частота туловых вызовов = гигабиты исходящего трафика и GC-давление на сериализацию; (2) медленный consumer: если сервер пишет в TCP-буфер без backpressure-политики, эмиттер копит очередь в heap неограниченно; (3) без капа соединений один зависший CLI-цикл реконнектов выедает лимит инстанса. Каждое — конкретный и реалистичный инцидент при заявленном MB-payload.

**Предложение.** Зафиксировать в api-contracts: (1) cap соединений (per-user ~5, per-instance ~500) с `429 rate-limited`; (2) backpressure-политика: буфер K событий/байт → при переполнении рвать соединение (клиент догоняет `Last-Event-ID` — механизм уже есть, дешёвая деградация); (3) для payload > ~64 KB слать в SSE заглушку `{id, seq, truncated: true}` + догрузку `GET /messages/{id}` — иммутабельность уже даёт ETag-кэширование (`api-contracts.md:16`), это сочетается с докой почти без изменений контракта (только документировать envelope).

### C3. Механизм fan-out — **GAP**

**Факт.** SSE-эндпоинты описаны (`api-contracts.md` §3), но откуда эмиттер берёт события — не сказано: in-memory шина после коммита? polling БД каждым соединением? Это решение определяет и латентность, и нагрузку на БД, и поведение при мульти-инстансе (последнее — осознанно за бортом MVP, `architecture.md` §5).

**Оценка.** При наивной реализации «каждое SSE-соединение поллит `session_message` раз в секунду» — 50 соединений × 1 Гц × индексный запрос — терпимо, но при MB-payload это ещё и перечитывание TOAST. Событие пишется тем же процессом, что держит соединения (один инстанс MVP) — in-memory after-commit шина очевидна, но она должна быть **документирована**, потому что от неё зависят гарантии доставки между коммитом и рассылкой (потеря события при рестарте лечится `since`-догонкой — это тоже надо зафиксировать).

**Предложение.** Дополнить `execution-model.md`/`architecture.md`: after-commit in-process pub/sub (например, Spring `ApplicationEvent` после коммита транзакции); SSE-соединения БД неPolling'ят; пропуск события при падении процесса компенсируется реконнектом с `Last-Event-ID` (уже в контракте).

## 4. Параллельные Turn'ы vs rate-limit провайдера

### D1. Семафор/лимитер конкурентных LLM-вызовов — **GAP**

**Факт.** Turn'ы — виртуальные потоки, «локи в БД делают безопасным горизонтальный запуск» (`execution-model.md:99–100`); на целевом масштабе T = 20–40 Turn'ов, с субагентами L ≈ 50–120 стримов (оценка §0). Нигде — ни в `intelligence`, ни в `execution` — нет семафора, bulkhead, очереди или лимита конкурентных вызовов на `llm_credentials`. Единственная упомянутая защита — явные `.timeout()/.maxRetries()` в `OpenAiChatOptions` из-за регрессии Spring AI (`architecture.md:49`) — это per-request HTTP-параметры, не ограничитель параллелизма.

**Оценка.** Виртуальные потоки делают запуск стрима «бесплатным» локально — значит, без ограничителя инстанс честно попытается открыть все L одновременно. Корпоративный LiteLLM с общим на компанию лимитом ответит 429 на хвосте очереди — см. D2. Плюс локальный ресурс: каждый стрим держит соединение пула БД в паузах раунда и heap под контекст. Это самый вероятный каскадный отказ системы на пике.

**Предложение.** Bulkhead на `LlmGateway` (resilience4j SemaphoreBulkhead или голый `Semaphore`) per `llm_credentials`: `maxConcurrentStreams` (конфиг, напр. 8–16) + очередь с таймаутом; при переполнении Turn не фейлится, а **паркуется** (выход из цикла без терминала; EVENT-wake от semaphore-релиза или POLL поднимет) — механика парковки `PARKED_ASYNC` переиспользуется. Добавить метрику занятости bulkhead.

### D2. 429/5xx → FAILED без retry/backoff — **RISK**

**Факт.** Цикл Turn'а: «Ошибка LLM → статус FAILED, выход» (условие 6, `execution-model.md:64`). `last_turn_outcome=FAILED` — терминальная проекция (`data-model.md:181`). Retry-политика к провайдеру не описана (только maxRetries в HTTP-опциях, `architecture.md:49`); каталог ошибок API не содержит никакого `provider-*` code — пользовательская ошибка задачи неотличима от транзиентной ошибки провайдера.

**Оценка.** 429 и 5xx LiteLLM — **транзиентные** события, а путь ведёт в терминал задачи: FAILED задача требует ручного вмешательства (resume остановленной задачи вообще `409 task-already-terminal`, `api-contracts.md:90`). Утренний пик + отсутствие bulkhead (D1) = волна 429 = пачка FAILED задач за минуты. Это design-level risk, не деталь реализации.

**Предложение.** Классификация ошибок провайдера в `LlmGateway`: 429/5xx/timeout → retry с экспоненциальным backoff+jitter (N≤3, уважая `Retry-After`); исчерпали → **парковка** сессии (не-терминальный исход), повторная попытка при следующем POLL с grow-интервалом; `FAILED` — только 4xx (кроме 429) и контентные ошибки. Заодно: задача в FAILED-по-причине-провайдера не должна съедать `ERROR`-ребро графа (семантика ERROR — «агент сигнализирует неудачу», `workflow-domain.md:52`).

## 5. Docker-память и диск

### E1. Пер-контейнерные лимиты — **OK**

**Факт.** `cpus=2, memory=2g, pids-limit=512`, сеть — только нуждающимся состояниям (`execution-model.md:70`); task-контейнеры — те же лимиты (`execution-model.md:70`); helper-образ локально на VM, pull — только backoff (`execution-model.md:26`).

**Оценка.** Изоляция одного «взбесившегося» контейнера закрыта: память/ЦП/pids ограничены, rogue-git-клон не съест канал остальным. Для find/grep/coreutils/git 2g — с запасом.

**Предложение.** Нет (дефолт можно снизить до 512m–1g — деталь конфига, не доки).

### E2. Агрегатный потолок контейнеров/памяти VM — **RISK**

**Факт.** Контейнер — per-session (D-30), создание лениво, удаление при архивации/чистке (`execution-model.md:70`); итоговый потолок числа контейнеров = число неархивированных сессий. VM не специфицирована (`architecture.md:50`: «оркестратор — контейнер на выделенной VM»); агрегатный лимит одновременных контейнеров, admission control при исчерпании — нигде.

**Оценка.** S ≈ 30–60 живых сессий → до ~60 контейнеров; worst-case память 60 × 2g = 120 GB лимитов на VM неизвестного размера. Лимит ≠ потребление, но fork-бомба в трёх сессиях при loose-oversubscription деградирует всех (по CPU — точно: 60 × 2 cpus = 120 vCPU требований на типовую 16–32-ядерную VM). Также не описан ceiling на **параллельное создание** контейнеров (docker.sock + burst стартов после рестарта — все сессии просыпаются разом от POLL).

**Предложение.** (1) Зафиксировать VM-спеку в `architecture.md` (например, 32 vCPU/64 GB как референс) и заголовок «ёмкость инстанса: ≤ N одновременных контейнеров». (2) Семафор в `ContainerWorkspaceTools` на число живых контейнеров + на burst-создание (например, ≤10/мин) — превышение = инструмент отвечает `ASYNC_ACCEPTED`/ошибкой-ретраем, не падением. (3) Метрика «контейнеров живых / лимит».

### E3. Диск: workspace-тома, git-клоны, quota/GC — **GAP**

**Факт.** Workspace — примонтированный том, git-клонирование — bash-состояние подготовки (D-11, `glossary.md` §6); `SERVER_DIR auto` — «чистится по retention» (`glossary.md:88`) — единственное упоминание, параметры/владелец очистки не определены; старт-скан чистит **осиротевшие контейнеры** (`execution-model.md:22`), но не осиротевшие тома/workspace. Postgres живёт на той же VM (`architecture.md:50`) — конкуренция за диск БД и docker-томов не рассматривается; watermark/quota не заданы.

**Оценка.** Конкретный failure mode: десятки задач × git-клоны монорепо (сотни MB–GB каждый) + MB-артефакты TOOL → том заполняется; disk-full валит и контейнеры (запись workspace), и Postgres (WAL) — то есть **весь инстанс разом**, при том что единственная близкая защита (старт-скан) про контейнеры, а не про диск. Ретеншн-фраза без параметров — не механизм.

**Предложение.** Дополнить `execution-model.md` §8: (1) retention-параметры: FREE auto-workspace — удалить через N дней после архивации; task-workspace — через N дней после терминала задачи (в обе стороны явно); (2) GC-джоба/POLL-ветка «workspace без живой сессии/терминальной задачи старше N» — симметрично осиротевшим контейнерам; (3) quota на workspace (docker `--storage-opt size` или du-джоба с alarm) + disk watermark alert (80/90%); (4) словами зафиксировать размещение PG-данных и docker-root на отдельных томах/разделах.

## 6. Списки, N+1, счётчики SessionDto

### F1. `messageCount`/`tokensTotal`/`lastSeq` — **GAP**

**Факт.** `SessionDto` содержит `lastSeq, messageCount, tokensTotal` (`api-contracts.md:62`); списковый `GET /sessions` отдаёт те же DTO (`api-contracts.md:46`). В таблице `session` денормализованных счётчиков нет (`data-model.md:165–189`); `tokens` хранится на сообщении (`data-model.md:200`).

**Оценка.** Страница из 20–50 сессий = 3 агрегата × N по `session_message` (таблица с MB-TOAST-строками; COUNT(*) по PK ещё дёшев, но SUM(tokens) — это уже индексный проход, а при росте N до тысяч элементов — десятки млн строк в агрегатах на страницу). На целевом масштабе — секунды на самый частый UI-запрос. Причём append-only делает денормализацию абсолютно безопасной: счётчики меняются только INSERT'ом.

**Предложение.** Денормализовать на `session`: `last_seq`, `message_count`, `tokens_total` — обновлять транзакционно с INSERT сообщения (та же транзакция, тривиальная инвариантность); подсветить в доке, что fork переписывает их из `seq_cutoff`-среза одним запросом. `tokensTotal` можно обновлять батчево/лениво, если INSERT-путь захочется разгрузить.

### F2. N+1 по связям и сортировка без индекса — **GAP**

**Факт.** `SessionDto` вкладывает `agent {key, rev}`, `owner`, `workspaceBinding`, `taskId?/stateCode?` (`api-contracts.md:62`); список сортируется `lastActivityAt desc` с фильтрами `folder/mine/kind/q/archived` (`api-contracts.md:46`). Индексов на `session.last_activity_at`, `folder_id`, `owner_user_id` в схеме нет (`data-model.md:165–189`).

**Оценка.** Без batch/fetch-join — классическое N+1: элементы страницы × (agent, owner, task, folder). Без индекса по `last_activity_at` сортировка на тысячах сессий — top-N sort на каждый запрос (терпимо, но зря). Совокупно самый частый запрос системы получает худшую возможную реализацию по умолчанию.

**Предложение.** (1) Зафиксировать форму запроса списка: одна проекция с LEFT JOIN на фиксированные связи (agent/owner/task) — связи узкие, дублей не дают; (2) composite/partial index `ON session (last_activity_at DESC) WHERE archived_at IS NULL` + по `folder_id` для фильтра; (3) `q` по title — pg_trgm GIN, если поиск станет частым (можно отложить, но задокументировать).

### F3. AccessPolicy-фильтрация списков (share reverse-lookup) — **RISK**

**Факт.** Список = «свои + расшаренные» (`api-contracts.md:46,37`); грант: `share UNIQUE (subject_type, subject_id, resource_type, resource_id)` (`data-model.md:51`); группа субъекта требует `group_member` (`data-model.md:24–29`), у которого нет индекса по `user_id` (PK ведёт с `group_id`).

**Оценка.** Запрос «какие из этих сессий мне видны» = `EXISTS (share WHERE resource_type='SESSION' AND resource_id = s.id AND (subject_id = :me OR subject_id IN (:myGroups)))`. Уникальный индекс ведёт с `subject_type, subject_id` — для «мои гранты» отлично, но для reverse-lookup по `resource_id` на странице он бесполезен → на каждый `resource_id` — фильтрующий проход по share (пока share мало — ок, растёт с распространением шаринга). Плюс резолв групп пользователя без индекса `group_member(user_id)` — seq scan на каждый списковый запрос. По отдельности мелочи, вместе — постоянная надбавка к каждому списку и к каждой проверке деталей.

**Предложение.** (1) Индекс `ON group_member (user_id)` (или составной `(user_id, group_id)`); (2) индекс `ON share (resource_type, resource_id)` под reverse-lookup; (3) резолв myGroups — один запрос на запрос списка (кэш в рамках request), не на элемент.

## 7. idempotency_key

### G1. Вставки и конкурентные повторы — **OK**

**Факт.** PK `(scope, key)` сериализует конкурентные запросы с одним ключом: проигравший ждёт коммит победителя и получает его ответ; конфликт тел → 409 (`api-contracts.md:10`, `data-model.md:220–229`).

**Оценка.** Точечные PK-insert/read, конфликт-детект по `request_hash` — на целевом масштабе (дубликаты — единицы процентов POST) нагрузка ничтожна; семантика ожидания коммита корректна и описана. Уровень БД ровно тот, что нужен.

**Предложение.** Нет.

### G2. TTL-чистка без индекса `expires_at` — **RISK**

**Факт.** «TTL 24 ч; чистка джобой» (`data-model.md:227`). Индексов, кроме PK `(scope, key)`, нет → предикат `DELETE WHERE expires_at < now()` — seq scan.

**Оценка.** Таблица маленькая (24 ч записей; у нас POST-трафик скромный) — seq scan раз в час незаметен. Но: (1) `response_json` хранит **исходный ответ целиком** для replay — для 202/201-ответов это мелочь, но контракт позволяет и большие тела — таблица может распухнуть по TOAST незаметно; (2) если джобу запустят раз в сутки, чистка будет пачкой удалений — всплеск dead tuples + bloat; (3) забытая джоба (упала/не включена) не проявляется, пока таблица не начнёт тормозить PK-вставки из-за распухшего индекса. Дешёво фиксируется — потому RISK, не GAP.

**Предложение.** (1) `INDEX ON idempotency_key (expires_at)`; (2) батчевое удаление (LIMIT-пачками по 500–1000 до исчерпания) из ShedLock-джобы ежечасно; (3) в доке — cap на размер `response_json` (например, 256 KB; больше — хранить усечённый replay-маркер), чтобы replay MB-ответов не заводил второй TOAST-гигант.

## 8. Ёмкость прочего

### H1. Пул соединений к БД — **GAP**

**Факт.** Datasource собирается вручную (`architecture.md:47`); размер пула, таймауты — нигде. Потребители соединений: T = 20–40 Turn'ов (рендер + вставки каждый раунд), SSE-догонки, POLL-джоба, REST.

**Оценка.** Дефолт Hikari (10) при 30+ активных Turn'ах — очередь на connection: латентность каждого раунда растёт, виртуальные потоки честно ждут (пиннинга нет, но и пользы нет — узкое место сместится в пул). Классическая ловушка «виртуальные потоки × узкий пул», известная и по стек-ловушкам доки — но для пула она не зафиксирована.

**Предложение.** Зафиксировать формулу в `architecture.md` §4: pool ≈ maxConcurrentTurns × 1.5 + apiSlop (например, 60–80 при T=40), `connectionTimeout` явный; рассмотреть `spring.threads.virtual.enabled`-совместимые обёртки не требуется — просто размер. Метрика ожидания пула.

### H2. JVM-heap под рендер MB-контекста × параллельные Turn'ы — **RISK**

**Факт.** Рендер: один проход, полные payload только видимых; кэш «шапки» + дельта (`execution-model.md:76`); компакция при ~80% окна (`execution-model.md:62`). Heap/Xmx, бюджет памяти процесса — нигде (`architecture.md` §4).

**Оценка.** Дельта между раундами экономит, но одиночный раунд всё равно материализует строку контекста размером ~текущее окно токенов: для окна 200K токенов это сотни MB символов в пике сборки (плюс промежуточные jsonb→String→провайдерные DTO). L = 50–120 стримов, из них реально рендерящих одновременно — десятки: пиковое потребление легко уходит в гигабайты → GC-паузы/OOM без явного бюджета. Компакция режет хвост, но пик прямо перед компакцией — ровно максимальный.

**Предложение.** (1) Задокументировать Xmx и целевой профиль (например, 8–16 GB при T=40); (2) ограничить одновременные рендеры семафором (можно общий с D1 bulkhead'ом); (3) строить запрос провайдеру стримингом/по-частям, где SDK позволяет, и не держать одновременно jsonb-оригинал и собранную строку (проекция → сразу в буфер); (4) нагрузочный сценарий в smoke: 40 сессий × 150K-токенный контекст.

### H3. `GET /export` на MB-сессиях — **RISK**

**Факт.** Export отдаёт файл с `Content-Disposition` (`api-contracts.md:57`), форматы markdown/json; потоковость не оговорена. Курсорная догрузка сообщений существует (`api-contracts.md:51`).

**Оценка.** Наивная реализация соберёт весь экспорт (тысячи сообщений × MB) в String/byte[] в heap — одиночный запрос на большой сессии = OOM-кандидат, а VIEW-право есть у всех участников: таких запросов может быть много. Формат markdown вообще говоря стримится тривиально, json — тоже (пишем массив поэлементно) — просто это надо зафиксировать.

**Предложение.** В api-contracts: export — streaming (`StreamingResponseBody`/chunked), итерация по `session_message` курсором, без полной материализации; оговорить `Content-Length: unknown`/chunked.

### H4. Индекс `session.parent_session_id` — **GAP**

**Факт.** Поддерево используется: stop = отмена всего поддерева (`execution-model.md:83`), recovery-спуск по БД (`execution-model.md:86`), `GET /sessions/{id}/tree` рекурсивно (`api-contracts.md:60`). В `data-model.md` индекса на `parent_session_id` нет.

**Оценка.** stop/recovery/tree — рекурсивный CTE «дети по родителю»; без индекса каждый уровень — seq scan по `session`. При десятках сессий — незаметно; при тысячах (а сессии не удаляются) — каждый stop тянёт за собой полный скан растущей таблицы. Дешевейший фикс.

**Предложение.** `INDEX ON session (parent_session_id) WHERE parent_session_id IS NOT NULL`.

### H5. `task_transition_history`: курсор по `id` vs индекс — **RISK**

**Факт.** SSE `id`/курсор истории = id записи (UUID v7, «монотонный») (`api-contracts.md:78`); индекс таблицы — `(task_id, created_at)` (`data-model.md:161`). В `?since=` для history передаётся id, а не `created_at`.

**Оценка.** Запрос `WHERE task_id=? AND id > :since ORDER BY id` не обслуживается индексом `(task_id, created_at)` (UUID-сравнение ≠ timestamp) — либо скан по task_id с фильтром, либо план по created_at с пересортировкой. UUID v7 действительно монотонен во времени, т.е. `id` и `created_at` коррелированы почти идеально — но planner этого не знает. История на длинных задачах с циклами — сотни–тысячи записей: терпимо, но это SSE-курсор, т.е. запрос на каждый реконнект/догонку каждого наблюдателя.

**Предложение.** Либо `INDEX ON task_transition_history (task_id, id)` (курсорный путь — точный), либо сменить курсор на `(created_at, id)` пару с существующим индексом. Первое проще и не ломает контракт.

## 9. Итог

**Счёт: OK = 4, RISK = 11, GAP = 10 (всего 25).**

Позитив: append-only профиль таблиц (B1), двухфазный рендер с дельтами, пер-контейнерные лимиты, курсорная пагинация и реконнект-SSE продуманы. Основной кластер рисков — «декларации есть, несущей конструкции нет»: D-33 про дешёвые сканы без полей/индексов под них (A1–A5), «виртуальные потоки» без ограничителя параллелизма к провайдеру (D1–D2) и «мультипользовательские списки» без денормализации и индексов (F1–F3). Все три кластера лечатся схемой + одним-двумя механизмами (bulkhead, retention) — это дешёво сейчас и дорого после M2.

### Проверка арифметики коллег

**DeepSeek — сводка корректна:** OK=7, RISK=9, GAP=13, итого 29 — пересчитано по тексту, сходится.
