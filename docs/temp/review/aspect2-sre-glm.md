## A. Гонки

### F-1. Два инстанса приложения борются за CAS-лок сессии — OK

**Поведение по докам.** `execution-model.md` §2: «CAS-взятие лока: locked_by = инстанс, locked_at = now() (успех только если было NULL или locked_at старше TTL); не взяли → выходим». §8: «локи в БД делают безопасным горизонтальный запуск нескольких инстансов (CAS по locked_by)». `data-model.md` §7.4: «session.locked_by/locked_at — только CAS-переходы (взятие/освобождение), не прямые UPDATE».

**Вердикт: OK.** Взаимное исключение пары (взять/отпустить) специфицировано и защищено инвариантом схемы. Оговорки о TTL и зомби-владельце — отдельная находка F-7.

### F-2. EVENT-путь и POLL-джоба будят одну сессию одновременно — OK

**Поведение по докам.** `execution-model.md` §8: «ShedLock гарантирует единственность poll-джобы; EVENT-путь идемпотентен благодаря CAS-локу». Оба контура сходятся в один `tryStart(session)`, проигравший CAS выходит без действий (§2). Победитель обработает те же события — eligibility («есть события после конца последнего модельного хода») одинаков для обоих.

**Вердикт: OK.** Отдельная очередь не нужна — очередь это сама `session_message` (§1), двойная обработка исключена CAS-ом.

### F-3. Двойной POST message — OK

**Проверка вопроса:** да, `Idempotency-Key` для сообщений **обязателен**. `api-contracts.md` §0.3: «Idempotency-Key обязателен на `POST .../messages`, опционален на прочих POST, включая вебхуки». Повтор с тем же ключом и тем же телом → исходный ответ (replay-safe); тот же ключ с другим телом → `409 idempotency-conflict`. Хранение — `idempotency_key`, PK `(scope, key)`, TTL 24 ч (`data-model.md` §6).

**Вердикт: OK** (последовательный ретрай покрыт). Примечание (не отдельный вердикт): семантика **конкурентного** дубля — два одинаковых POST с одним ключом, пока первый in-flight — не специфицирована (replay предполагает завершённый первый запрос; поведение второго — ожидание/409/ошибка — не определено). Рекомендация: зафиксировать «второй конкурентный запрос с тем же ключом ждёт завершения первого или получает 409» — одной строкой в §0.3.

### F-4. Параллельный stop + переход задачи (transition) — GAP

**Поведение по докам.** `api-contracts.md` §4.1: stop = «suspend + отмена активных Turn'ов сессий задачи + терминал: current_state = '$CANCELLED'». `execution-model.md` §6: cancel_requested «проверяется между вызовами инструментов». `workflow-domain.md` §3: transition — инструмент агента, «валидация по разрешённым переходам ревизии; запись в task_transition_history; перевод задачи».

**Дыра.** Порядок событий не сериализован:
- Turn агента в полёте: cancel_requested проверяется только **между** инструментами — переход, уже начавший исполняться, коммитится **после** старта stop. Итог: `current_state = '$CANCELLED'` перезаписан переходом на легальный code (или наоборот: переход коммитится, затем stop пишет `$CANCELLED` from нового состояния — история противоречива).
- Нигде не сказано, что `transition` отклоняется при `suspended = true` / `cancel_requested = true`. Glossary §3.5 («планировщик и wake пропускают suspended-задачу») покрывает wake, но не in-flight вызов инструмента.

**Предложение.** Зафиксировать в `execution-model.md` §6/§7: (1) transition атомарно перепроверяет `suspended` и `cancel_requested` в той же транзакции (условный UPDATE по `current_state` = ожидаемому from); (2) stop идёт тем же механизмом CAS по `current_state` — тогда «transition vs stop» редуцируется к «выигрывает ровно один».

## B. Crash-моменты

### F-5. Crash между записью USER-сообщения и tryStart — OK

**Поведение по докам.** `execution-model.md` §1: POLL — «скан eligible-сессий, пропущенных контуром EVENT (падение инстанса, гонка)», джоба раз в ~5 сек. Сообщение уже в `session_message` → eligibility выполнено → POLL поднимет Turn.

**Вердикт: OK.** Потеря задержкой ≤ ~5 сек, данных нет.

### F-6. Crash между переводом task.current_state и созданием/seed STATE-сессии — GAP (топ-1)

**Поведение по докам.** `execution-model.md` §7: «1. Движок перевёл task.current_state… (транзакционно + запись в history + projection). 2. Если состояние агентское: найти/создать сессию пары…; seed-контекст → wake». Шаги 1 и 2 — очевидно разные транзакции (шаг 2 «транзакционно» не声明; и он включает wake — внешнее действие).

**Дыра.** Crash между шагами: задача в AGENT-состоянии, сессии нет. Ни один механизм восстановления не срабатывает:
- POLL сканирует **eligible-сессии** (§1) — сессии не существует, сканить нечего;
- стартовые сканы (§1: стухшие локи / TOOL_CALL без результата / осиротевшие контейнеры) — не содержат «AGENT-состояние без сессии»;
- у AGENT-состояния **нет обязательного timeout** — `workflow-domain.md` §2 правило 4: «timeout — опционально (для BASH_SCRIPT и WAIT_*)».

Итог: задача навсегда `RUNNING` без сессии, без таймаута, без самовосстановления. PARTIAL UNIQUE `(task_id, state_code)` делает повторное создание идемпотентным — механизм есть, но **кто и когда его вызовет, не определено**.

**Предложение.** Добавить в стартовые сканы (и/или в POLL) четвёртый пункт: «задачи в AGENT-состоянии без сессии пары (task_id, state_code) → найти/создать + seed + wake» (идемпотентно по partial unique). Либо объединить шаги 1–2 в одну транзакцию (сессию можно создать в той же TX, wake — после коммита; потерянный wake покрывает POLL, т.к. seed-событие уже в потоке).

### F-7. Смерть инстанса с зажатым локом; согласованность TTL лока и lockAtMostFor — GAP (топ-3)

**Поведение по докам.** `execution-model.md` §1: старт-скан — «стухшие локи (locked_at старше TTL) — освобождаются». Glossary Session: «locked_by/locked_at (TTL)». ShedLock: «раз в ~5 сек (lockAtMostFor ~10 сек, отпускает сама)» — это про **джобу**, не про сессионный лок.

**Дыры.**
1. **Значение TTL сессионного лока не задано нигде** — ни числа, ни принципа вывода.
2. **Нет heartbeat-продления**: Turn с LLM-стримом живёт минутами; если TTL < длительность Turn'а, другой инстанс легитимно возьмёт лок («locked_at старше TTL») → **два активных Turn'а одной сессии**: перемежающиеся раунды, двойные tool-calls, двойной биллинг LLM.
3. **Нет fencing для зомби**: CAS-освобождение «только если владелец — мы» защищает поле лока, но не останавливает вычисление старого владельца — зомби-Turn продолжает писать ASSISTANT/TOOL_RESULT и звать инструменты.
4. Наоборот, завышенный TTL → медленное восстановление после crash (сессия висит до стухания).
5. «Согласованность» с ShedLock lockAtMostFor — категория отсутствующая: это независимые таймеры для разных объектов; вопрос снимается, но подменяет собой отсутствие спеки сессионного TTL.

**Предложение.** Определить в `execution-model.md` §2: (а) TTL сессионного лока (напр., 60–120 с) **с продлением** (locked_at = now() на каждом раунде/между tool-calls); (б) поведение зомби: владелец перед каждой записью события проверяет «лок всё ещё мой» (fencing-проверка) — иначе дропает Turn.

### F-8. Crash во время каскадной отмены поддерева — AMBIG

**Поведение по докам.** `execution-model.md` §6: «выжившее после падения поддерево добивается recovery-спуском по БД». Glossary §5 (CancellationToken-дерево): «recovery добивает выжившие после падения по parent_session_id в БД».

**Неоднозначность.** Механизм упомянут, но не специфицирован: (1) триггер запуска — только старт процесса? Если в multi-instance другие инстансы живут, кто добивает поддерево? В стартовый список сканов `execution-model.md` §1 recovery-спуск **не входит** (там: стухшие локи, TOOL_CALL-сироты, контейнеры-сироты); (2) периодичность/дедупликация повторного спуска; (3) взаимодействие с идущим параллельно stop с другого инстанса.

**Предложение.** Включить recovery-спуск отмены в стартовые сканы §1 (пункт 4) + периодический лёгкий скан «cancel_requested = true без признака завершённой отмены» (маркер — например, синтетические «cancelled» TOOL_RESULT'ы по всему поддереву).

## C. Потерянные события

### F-9. Вебхук пришёл до входа задачи в WAIT_WEBHOOK (409) — AMBIG

**Поведение по докам.** `api-contracts.md` §4.4: «задача в WAIT_WEBHOOK → переход NEXT…; иначе `409 task-not-waiting-webhook`». `workflow-domain.md` §7 / D-26: «идемпотентность задач по построению (409 вне WAIT_WEBHOOK)».

**Неоднозначность.** Поведение сервера задано (409), но **кто повторяет и когда — не специфицировано**: сервер пассивен (§7), повтор — стихийная забота внешнего отправителя (нет ни `Retry-After`, ни рекомендации в доке). Реальный исход: событие потеряно, WAIT_WEBHOOK уйдёт по **TIMEOUT**-переходу (обязателен по правилу валидации 4) — задача не зависает навсегда, но идёт ложным путём с ложным reason. Сценар «принять раньше и применить при входе в состояние» или «RETRY-After + гайд отправителю» не отрефлексированы (D-26 — про security, не про ранний приход).

**Предложение.** Минимум — зафиксировать в `workflow-domain.md` §7: «повтор при 409 — ответственность отправителя; рекомендация: ретрай с backoff до N минут» + 429-style `Retry-After` на 409. Максимум (позже): буфер последнего вебхука на задачу, применяемый при входе в WAIT_WEBHOOK.

### F-10. Терминал подзадачи случился во время даунтайма родителя — покрывает ли POLL? — GAP (топ-2). Нет.

**Поведение по докам.** `execution-model.md` §1: POLL — «скан **eligible-сессий**». Eligibility (§1, glossary) — предикат над сессией. `workflow-domain.md` §3: WAIT_TASKS — «Сессия? **нет**»; «переоценка на каждый терминал подзадач» — это EVENT-контур (§1: «подзадача пришла в терминал → переоценка WAIT_TASKS у родителей»).

**Дыра.** Родитель WAIT_TASKS **бессессионен** → POLL его не видит никогда. Весь страховочный контур построен вокруг сессий, а переход WAIT_TASKS驱动 driven событиями. Если EVENT-переоценка потеряна (даунтайм, crash инстанса между коммитом терминала подзадачи и переоценкой родителя) — стартовые сканы (§1: локи/TOOL_CALL/контейнеры) тоже не переоценивают WAITING-задачи. Ущерб ограничен только обязательным TIMEOUT-переходом WAIT_TASKS — т.е. ложный путь по TIMEOUT вместо NEXT. Индекс `(blocked_task_id)` (data-model §4) — «обратный поиск для переоценки» — работает только в момент события.

**Предложение.** Расширить POLL (или отдельной джобой с тем же ShedLock): периодический скан «задачи в WAIT_TASKS (status_projection = WAITING), условие которых уже выполнено» — по существующим индексам `(parent_task_id, status_projection)` / GIN `(tags)` / `(blocked_task_id)`. Тот же скан заодно закрывает F-16 (resume).

### F-11. Поздний TOOL_RESULT для удалённой/заархивированной сессии — GAP

**Поведение по докам.** Glossary (Асинхронный инструмент): «завершение фона дописывает второй TOOL_RESULT с тем же call_id (late=true) → wake». Eligibility (`execution-model.md` §1): «есть события после конца последнего модельного хода И сессия не терминальна И задача не suspended И лок свободен или стух». Удаления сессий нет («Сессии не удаляются — резюмируемы», §6), есть `archived_at` (data-model §5).

**Дыра.** Eligibility-предикат **не содержит**: (а) `archived_at IS NULL`; (б) для STATE-сессии — «задача всё ещё в состоянии state_code этой сессии». Сценарий: async-тул завершился после архивации FREE-сессии или после перехода задачи в следующее состояние → wake → Turn поднимется в мёртвой/неактивной сессии: агент доработает в контексте, которого задача уже не ждёт; для архивной — сессия «оживёт» из архива. Побочный ущерб мал (результат просто дописан в поток), но семантика не определена.

**Предложение.** Дополнить eligibility: `AND archived_at IS NULL AND (kind = 'FREE' OR task.current_state = session.state_code)`. Поздний результат при этом всё равно дописывается в поток (аудит), но Turn не запускается; для SPAWN/нового входа в то же состояние сработает partial unique + resume.

## D. Идемпотентность переходов

### F-12. Двойной вызов transition (агент ретраит) — GAP

**Поведение по докам.** `workflow-domain.md` §3: «переходы из AGENT-состояния: цель инструмента transition — любое исходящее ребро текущего состояния»; `execution-model.md` §4: «валидация по разрешённым переходам ревизии; запись в task_transition_history; перевод задачи». Идемпотентность инструмента не описана.

**Дыра.** Ретрай после потерянного ответа (LLM не увидел результат из-за обрыва) → **второй** transition. Если граф ацикличен — второй вызов скорее всего невалиден (из нового состояния нет такого ребра) → отказ, полбеды. Но **циклы легальны и не ограничены** (glossary §3 Transition) → повторный переход по тому же ребру валиден → задача прыгает на два шага, история содержит два «обоснования», ни одно не ложь. Это незаметимая порча графа. Нет ни дедупликации по call_id/идему-ключу вызова, ни guard'а «переход из состояния, зафиксированного на момент выдачи хода».

**Предложение.** (а) transition выполняется условным UPDATE `WHERE current_state = <from, ожидаемый агентом>` — при несовпадении `409`-эквивалент в TOOL_RESULT; (б) в рендер контекста включать «вы уже переводили задачу в X» — модельная защита; (в) для ретраев того же хода — дедуп по (session, round, tool_call_id).

### F-13. Двойной терминал подзадачи → двойная переоценка WAIT_TASKS — GAP

**Поведение по докам.** `workflow-domain.md` §3: WAIT_TASKS — «переоценка на каждый терминал подзадач»; движковый переход — «транзакционно + запись в history + пересчёт projection» (`execution-model.md` §7). Про конкурентную переоценку — молчание.

**Дыра.** Две подзадачи приходят в терминал одновременно (параллельные подзадачи — штатный режим, «аналог стейджа GitLab CI») → два EVENT-wake → два инстанса/потока переоценивают одного родителя → оба видят условие выполненным → гонка за движковый переход. Guard (CAS по `current_state`, `SELECT FOR UPDATE` задачи, unique-ограничение на «один переход») нигде не описан. Возможный исход без guard'а: двойная запись в `task_transition_history` и/или двойной wake следующего состояния. Сам терминал подзадачи повторно не приходит (TERMINAL без исходящих рёбер — правило 4/§3), но **переоценка родителя** может легитимно случиться дважды и одновременно.

**Предложение.** Зафиксировать: движковый переход атомарен и однократен — условный UPDATE по `current_state` (тот же механизм, что в F-4/F-12); повторная переоценка видит уже сменившееся состояние и становится no-op. Одна фраза в `execution-model.md` §7 закрывает F-4, F-12, F-13 единым примитивом.

## E. Graceful shutdown

### F-14. Деплой при активных Turn'ах — GAP (доки молчат)

**Поведение по докам.** В `execution-model.md` нет ни слова о shutdown/drain/stop-принятии трафика. §8: «Один инстанс MVP: все Turn'ы — виртуальные потоки процесса». Косвенная восстановимость есть: рестарт-скан §1 даёт синтетические `TOOL_RESULT` «операция потеряна при перезапуске», POLL будит сессии с недоигранными событиями.

**Дыры.**
1. Политика дожития не задана: turn'ы обрываются SIGKILL'ом посреди LLM-стрима/инструмента — консистентность восстановится, но это аварийный, а не управляемый путь; drain-таймаут, «не принимать новые wake при остановке» — не описаны.
2. **Незакрытые async-тулы**: рестарт-скан превращает их в «операция потеряна» — но фоновая работа могла иметь **внешние эффекты** (docker-действие, сторонний вызов) — потеря фиксируется, компенсации нет и не отрефлексировано, что это осознанный выбор.
3. **Spawn-пары при crash**: родительский Turn умер в ожидании `spawn_subagent` → рестарт-скан даст родителю `TOOL_RESULT` «потеряна» → родитель решает дальше. Но дочерняя сессия: её лок стухнет, её собственные недоигранные события разбудит POLL → **субагент продолжит работать параллельно с уже «похороненным» родительским вызовом**. Кто закрыт recovery-спуском (F-8) — неясно: спуск описан для отмены, не для crash-разделения пары.
4. Для CLIENT_EXEC поведение задано (api-contracts §5: синтетический «потеряно при отключении исполнителя», PARKED_CLIENT) — аналогичный кейс для server-side контейнеров описан в D-30. Дыра именно в shutdown-оркестрации и spawn-парах.

**Предложение.** Секция «Остановка инстанса» в `execution-model.md`: SIGTERM → перестаём брать новые локи → drain-окно (T) на текущие раунды → помечаем незакрытые async-тулы «lost at shutdown» сами (не ждать рестарт-скана); spawn-пары: при потере родителя дочерние сессии поддерева помечаются cancel_requested и добиваются recovery-спуском (унификация с §6).

## F. Outbox: транзакция БД ↔ side-effects

### F-15. Где рассинхрон БД/мира — GAP

**Инвентаризация точек рассинхрона по докам:**

| Side-effect | Связь с TX БД | Покрытие доками | Вердикт |
|---|---|---|---|
| Wake tryStart после коммита | после коммита | потеря покрывается POLL ~5 c (§1: «пропущенных контуром EVENT») | OK |
| Seed STATE-сессии после перевода current_state | отдельная TX после TX перехода | никем: см. F-6 | GAP |
| Docker-исполнение (bash в контейнере) → запись TOOL_RESULT | эффект в мире, запись потом | D-30 покрывает смерть контейнера; обратный порядок (эффект исполнен, запись не удалась — workspace изменился, в потоке пусто) не покрыт; журнала docker-действий вне событийного потока нет | GAP |
| LLM-стрим (биллинг) → запись ASSISTANT | эффект в мире (деньги), запись потом | молчание: списание без записи = потерянный ход, модельные токены списаны | GAP |
| Вебхук-приём: payload → reason + переход | одна TX (проверка HMAC без БД, переход — с ней) | атомарно, replay по Idempotency-Key для вебхуков опционален; ранний/поздний приход — F-9 | OK/см. F-9 |

**Дыра.** Outbox-паттерн (или осознанный отказ от него с перечнем допустимых расхождений) нигде не зафиксирован. Расхождения реальны: F-6 (seed), docker-эффект без записи, списание LLM без ASSISTANT. Для MVP допустимо принять «at-least-once мир + событийный поток как источник истины», но это должно быть **написано**, иначе реализация соберёт рассинхрон молча.

**Предложение.** В `execution-model.md` §8 добавить принцип: «все мутации мира фиксируются событием потока до/после в рамках определённого порядка; wake — единственный допустимый потерянный side-effect (страхование POLL); docker/LLM-эффекты идемпотентизируются call_id». Для bash — журнал вызовов уже фактически есть (`TOOL_CALL`/`TOOL_RESULT`): запретить исполнять инструмент до INSERT `TOOL_CALL` (write-ahead), тогда «эффект без записи» невозможен в одну сторону, а «запись без эффекта» закрывается рестарт-сканом. Это дешёвый outbox из существующих сущностей.

## G. Дополнительные сценарии (найдены при проходе)

### F-16. Resume после suspend: кто переоценит WAIT_TASKS — AMBIG

**Поведение по докам.** Glossary §3.5: «task.suspended — аварийный стоп: планировщик и wake пропускают suspended-задачу. Снятие — явная команда». `api-contracts.md` §4.1: `POST /tasks/{id}/resume → 204`.

**Неоднозначность.** Терминал подзадачи, случившийся, пока родитель suspended: wake пропущен (по флагу), EVENT-переоценка не выполнена. После resume флаг снят — но **триггером чего** выполнится запоздалая переоценка? Новых терминалов может не быть; POLL сканирует сессии (родитель WAIT_TASKS бессессионен — F-10). Задача может остаться WAITING с уже выполненным условием до чужого события или TIMEOUT.

**Предложение.** Зафиксировать: `resume` синхронно выполняет переоценку WAIT_TASKS (если текущее состояние — WAIT_TASKS) и/или wake сессий задачи. Закрывается тем же периодическим сканом, что F-10.

### F-17. Ошибка LLM → FAILED: ретрай-политика отсутствует — AMBIG

**Поведение по докам.** `execution-model.md` §3, строка 6: «Ошибка LLM → статус FAILED, выход». `last_turn_outcome = FAILED` (data-model §5). Что дальше — не определено: eligibility говорит «сессия не терминальна», но **терминальность сессии нигде не определена** (у сессии нет статуса-перечисления; «не терминальна» — термин без носителя). Для FREE-сессии спасает новый USER-мессдж; для STATE-сессии — транзиентный сбой провайдера валит Turn, задача остаётся в состоянии без авторетрая.

**Предложение.** Определить: (а) что «терминальна» значит для сессии (напр., STATE-сессия терминальна, когда задача в терминале); (б) ретрай-политика LLM: N попыток с backoff+jitter внутри Turn'а, FAILED — только после исчерпания; (в) операция возобновления FAILED-Turn'а (новое событие / явная команда).

### F-18. Отмена mid-tool: sync-инструмент в полёте — AMBIG

**Поведение по докам.** `execution-model.md` §6: cancel_requested «проверяется между вызовами инструментов»; «Незакрытые async-тулы отменённых — синтетический TOOL_RESULT "cancelled"».

**Неоднозначность.** Про async-тулы поведение задано. Про **sync**-инструмент (bash в контейнере, до 30-сек окна и дольше) — молчание: добивает своё, процессы в контейнере киляются, контейнер целиком (следующий Turn создаст заново — liveness контейнера = lifecycle сессии, §4)? Не специфицировано.

**Предложение.** Одна строка в §6: «in-flight sync-инструмент получает CancellationToken; контейнерные исполнения прерываются (docker stop) с синтетическим TOOL_RESULT "cancelled"».

## Итоговые рекомендации (сводно)

1. **Единый примитив однократности движковых переходов** (условный UPDATE по `current_state` в транзакции с записью history): закрывает F-4, F-12, F-13 и половину рисков оркестратора. Самое дешёвое изменение с максимальным охватом.
2. **Два недостающих страховочных скана** (в POLL или стартовые сканы): (а) AGENT-состояние без сессии — F-6; (б) WAIT_TASKS с выполненным условием — F-10, F-16. POLL сегодня страхует только сессионный контур — а половина состояний движка бессессионна.
3. **Контракт сессионного лока**: числовой TTL + продление на границах раундов + fencing-проверка владельца перед записью — F-7; плюс recovery-спуск как постоянный скан — F-8.
4. **Write-ahead для tool-calls + секция graceful shutdown** — F-14, F-15: событийный поток уже есть, достаточно запретить side-effect до INSERT `TOOL_CALL` и описать остановку.
5. **Мелочи одним предложением каждое**: eligibility += archived/state-active (F-11); transition-гид при suspended/cancel_requested (F-4); Retry-After на 409 вебхука + ответственность отправителя (F-9); LLM-ретрай с backoff и определение «терминальности» сессии (F-17); прерывание sync-инструментов (F-18); конкурентный дубль Idempotency-Key (F-3 примечание).
