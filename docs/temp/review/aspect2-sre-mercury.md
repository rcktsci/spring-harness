## 1. Гонки

### 1.1 Два инстанса на CAS-локе сессии

**Сценарий:** Инстанс A и B пытаются взять лок сессии одновременно.

**Доки (execution-model.md §2):**
```
CAS-взятие лока: locked_by = инстанс, locked_at = now()
  (успех только если было NULL или locked_at старше TTL)
не взяли → выходим
```

**Вердикт:** ✅ OK
**Обоснование:** CAS-логика задокументирована. Один инстанс забирает, второй сразу выходит.

---

### 1.2 EVENT-путь и POLL-джоба будят одну сессию одновременно

**Сценарий:** WEB пришёл и вызвал tryStart; параллельно POLL-джоба видит сессию и тоже вызывает tryStart.

**Доки (execution-model.md §1):**
> EVENT-путь идентемпонтентен благодаря CAS-локу.

**Вердикт:** ✅ OK
**Обоснование:** CAS защищает от двойного выполнения. Второй вызов tryStart сразу выходит.

---

### 1.3 Двойной POST message (Idempotency-Key)

**Сценарий:** Два параллельных POST на тот же ресурс.

**Доки (api-contracts.md §0.3):**
> `Idempotency-Key` обязателен на `POST .../messages`

**Вердикт:** ✅ OK
**Обоснование:** Контракт обязателен. Повтор с тем же ключом → replay. Тот же ключ, другое тело → 409.

---

### 1.4 Параллельный stop + переход задачи

**Сценарий:** `stop(session)` и `transition` приходят одновременно.

**Доки (execution-model.md §6; api-contracts.md §2.12):**
> `stop(session)` = отмена Turn'а цели + всего поддерева
> Command-эндпоинты — осознанный RPC-стиль

**Вердикт:** ⚠️ AMBIG
**Обоснование:** Неясно, что происходит, если stop пришёл во время tryStart/хода Turn. Лок ещё не взят? Stop может установить `cancel_requested` между раундами? Не детализовано.

**Предложение:** Добавить в execution-model.md §6 поведение stop во время TryStart и во время Turn (отмена ленивая или мгновенная).

## 2. Crash-моменты

### 2.1 Между записью USER-сообщения и tryStart

**Сценарий:** Клиент POST сообщение → сообщение записано → инстанс падает до tryStart.

**Доки (execution-model.md §1, glossary.md §4):**
> Контур POLL (страховка): скан eligible-сессий, пропущенных контуром EVENT (падение инстанса, гонка).

**Вердикт:** ✅ OK
**Обоснование:** POLL раз в ~5 сек найдёт новую сессию и сделает tryStart.

---

### 2.2 Между переводом task.current_state и созданием/seed STATE-сессии

**Сценарий:** task.current_state записано → сессия не создана → падение.

**Доки (execution-model.md §7):**
> 1. Движок перевёл task.current_state... 2. Если состояние агентское: найти/создать сессию...

**Вердикт:** ⚠️ AMBIG
**Обоснование:** Неясно, атомарно ли это. Если не атомарно: задача в новом состоянии без сессии → POLL-джоба видит eligible? Задача не имеет сессии → зависает.

**Предложение:** Зафиксировать, что переход в AGENT-состояние и создание STATE-сессии — в одной транзакции. Иначе добавить recovery-скан: "задача в AGENT без сессии → создать".

---

### 2.3 Смерть инстанса с зажатым локом

**Сценарий:** Инстанс умер, лок не отпущен.

**Доки (execution-model.md §1; data-model.md §7.4):**
> стухшие локи (locked_at старше TTL) — освобождаются
> session.locked_by/locked_at — только CAS-переходы

**Вердикт:** ⚠️ GAP
**Обоснование:** В docs упоминается "TTL лока", но точное значение не зафиксировано. ShedLock-джоба имеет `lockAtMostFor ~10 сек`, но какой TTL на `locked_at`? Нужно зафиксировать в data-model или glossary.

**Предложение:** Добавить в glossary.md §4: "session.locked_at TTL = X минут (рекомендуется 5×period POLL)".

---

### 2.4 Crash во время каскадной отмены поддерева

**Сценарий:** `stop(session)` идёт по `parent_session_id`, инстанс падает на половине.

**Доки (execution-model.md §6; glossary.md §5):**
> Стоп середины дерева: узел + потомки гаснут; родитель жив, получает TOOL_RESULT «субагент отменён»
> выжившее после падения поддерево добивается recovery-спуском по БД

**Вердикт:** ✅ OK
**Обоснование:** recovery-спуск по БД покрывает.

## 3. Потерянные события

### 3.1 Вебхук пришёл до входа задачи в WAIT_WEBHOOK (409)

**Сценарий:** Внешняя система отправляет webhook → задача ещё не в WAIT_WEBHOOK → 409.

**Доки (api-contracts.md §0.4, §4.4):**
> идемпотентность задач по построению (409 вне WAIT_WEBHOOK)

**Вердикт:** ⚠️ GAP
**Обоснование:** docs говорят, что 409 — это нормально, но не говорят, *кто* и *когда* повторяет. Внешняя система должна ретраить? Через сколько?

**Предложение:** Добавить в workflow-domain.md §7 или glossary.md: "Если webhook пришёл не в WAIT_WEBHOOK, внешний отправитель обязан ретраить с экспоненциальным бэк-оффом; задача переводится в WAIT_WEBHOOK через API агентом предыдущего состояния."

### 3.2 Терминал подзадачи во время даунтайма родителя

**Сценарий:** Подзадача в терминал → родитель в даунтайме → wake потерян.

**Доки (execution-model.md §1; glossary.md §4):**
> Подзадача пришла в терминал → переоценка WAIT_TASKS у родителей → tryStart

**Вердикт:** ✅ OK
**Обоснование:** POLL-джоба сканирует задачи с WAIT_TASKS и делает tryStart.

---

### 3.3 Поздний TOOL_RESULT для удалённой/заархивированной сессии

**Сценарий:** Инструмент async завершается после архивации сессии.

**Доки (execution-model.md §3; glossary.md §4):**
> Модель «закончила» ⟺ в ответе нет ни одного tool-call
> ASYNC_ACCEPTED → фон дорабатывает → второй TOOL_RESULT → wake

**Вердикт:** ⚠️ GAP
**Обоснование:** Не зафиксировано, что делать с late TOOL_RESULT на archived-сессии. Wake должен проигнорировать?

**Предложение:** Добавить в execution-model.md §1 или glossary.md: "TOOL_RESULT на archived-сессии игнорируется; результат не записывается."

## 4. Идемпотентность переходов

### 4.1 Двойной вызов transition (агент ретраит)

**Сценарий:** Агент вызывает transition дважды из-за таймаута.

**Доки (workflow-domain.md §3):**
> каждый нетерминальный код имеет ≥1 исходящий переход; переходы замкнуты на существующие codes

**Вердикт:** ⚠️ GAP
**Обоснование:** Не зафиксировано, что transition идемпотентен. Если агент ретраит — что? 409? Запись дубликата в history?

**Предложение:** Добавить в workflow-domain.md §3 или glossary.md §3: "transition идемпотентен: если задача уже в указанной цели — 409; иначе запись в history."

---

### 4.2 Двойной терминал подзадачи → двойная переоценка WAIT_TASKS

**Сценарий:** Подзадача в терминал дважды (например, webhook дублирует).

**Доки (glossary.md §3; workflow-domain.md §3):**
> WAIT_TASKS: переоценка на каждый терминал подзадач

**Вердикт:** ✅ OK
**Обоснование:** Переоценка — детерминированная функция состояния. Двойная переоценка даёт тот же результат.

## 5. Graceful shutdown

### 5.1 Деплой при активных Turn'ах

**Сценарий:** Инстанс получает сигнал деплоя во время Turn.

**Доки:**
> Нет упоминаний в execution-model.md или glossary.md.

**Вердикт:** ❌ GAP
**Обоснование:** docs молчат о graceful shutdown. Что с:
- Незакрытыми async-тулами?
- Дочерними spawn-ожиданиями?
- Записывается ли лок перед остановкой?

**Предложение:** Добавить раздел в execution-model.md:
```
## 9. Graceful shutdown

При получении SIGTERM:
1. Остановить приём новых tryStart (снять из балансировщика)
2. Дожаться завершения текущих Turn'ов или установить deadline (например, 30 сек)
3. Незакрытые async-тулы → синтетический TOOL_RESULT "shutdown"
4. Снять лок через CAS (locked_by = null)
5. Exit
```

## 6. Outbox-вопрос

### 6.1 Транзакция БД ↔ side-effects

**Сценарий:**
1. Транзакция: USER-сообщение + task_transition + wake
2. Side-effects: docker-вызов, LLM-стрим, wake в другом инстансе
3. Шаг 2 падает → рассинхрон БД/мира

**Доки:**
> Нет упоминаний в execution-model.md.

**Вердикт:** ❌ GAP
**Обоснование:** Нет паттерна для гарантированной доставки side-effects.
- Что если Docker-контейнер не создан после записи SESSION?
- Что если LLM-стрим упал после записи TOOL_RESULT?

**Предложение:** Добавить в execution-model.md или glossary.md один из паттернов:
1. **Транзакционные side-effects** — все side-effects в той же транзакции (не всегда возможно).
2. **Outbox table** — side-effects пишутся в outbox-таблицу в той же транзакции; фоновая джоба доставляет.
3. **Retry-after** — side-effects в отдельном шаге с автоматическим ретраем до успеха.
