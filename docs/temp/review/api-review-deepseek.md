## CRITICAL

### C-1. Авторизация на эндпоинтах workflow и триггеров не определена
- **Место:** §0.1, §3 «Workflow» (стр. 74–84), §3 «Триггеры» (стр. 86–92).
- **Описание:** §0.1 объявляет «Auth на всех эндпоинтах», но колонка «Права» у `POST/GET /workflows`, `POST /workflows/{key}/revisions`, `POST/GET/DELETE /triggers` отсутствует («управление» — не грант). По глоссарию `Workflow`/`WorkflowRevision` иммутабельны и являются шаблонами, общими для всех задач; `configure_trigger` — инструмент оркестратора. Из спеки следует, что **любой аутентифицированный пользователь** может переписать шаблон workflow (создав новую ревизию) и завести триггер, создающий задачи от имени системы. Это privilege escalation.
- **Предложение:** ввести явную роль/скоуп (например, `WORKFLOW_ADMIN`, Keycloak-realm-role) и графу прав; для чтения — «аутентифицированный/VIEW по owner_user_id workflow»; создание/правку и триггеры — только администратор/оркестратор; зафиксировать это в колонке «Права» и в `AccessPolicy`.

### C-2. Модель прав на задачи (`VIEW`/`PARTICIPANT-уровень задачи`) не существует в системе
- **Место:** §3 «Задачи», стр. 61–70 (`PARTICIPANT-уровень задачи`, `PARTICIPANT`, `VIEW`).
- **Описание:** гранты доступа определены только для `Share.resource_type ∈ {SESSION, FOLDER}` (`glossary.md` §1; `data-model.md` §1). Отдельного уровня прав на `Task` нет ни в `share`, ни в `task` (`data-model.md` §4: поля `visibility` у `task` нет, хотя `glossary.md` §3 её упоминает). Таким образом, требования `GET /tasks/{id}` → VIEW, `POST /tasks/{id}/subtasks` → «PARTICIPANT-уровень задачи», `POST .../dependencies` → PARTICIPANT невыполнимы: непонятно, откуда берётся грант. `GET /tasks` → «по видимости» также не определён.
- **Предложение:** либо (а) добавить `task.visibility` и `Share.resource_type = TASK` с уровнями VIEW/PARTICIPATE, либо (б) вывести права задачи из прав `owner_user_id`/родительской задачи/связанных сессий и явно это описать. Спека не должна ссылаться на несуществующий грант.

### C-3. Подпись вебхука не защищает тело → повтор и подмена payload
- **Место:** §3 «Триггеры», стр. 90–92; §3 «Входящие вебхуки задач», стр. 96–98; `workflow-domain.md` §7; `glossary.md` §7.
- **Описание:** `signature = HMAC(secret, taskId)` (и `HMAC(secret, triggerId)`) — **статическая** подпись, зависящая только от публичного идентификатора в пути. Она (1) не покрывает тело запроса → любой, кто узнал/перехватил подписанный URL, может отправить произвольный payload; (2) бесконечно реплеится (нет timestamp/nonce); (3) передаётся в query string → утекает в access-логи, прокси и `Referer`. Для триггера подпись вообще тождественна самому URL — фактически bearer-токен без срока жизни и без отзыва, кроме `DELETE`.
- **Предложение:** подписывать `HMAC(secret, timestamp + method + path + sha256(body))`, добавить `X-Signature-Timestamp` и окно валидности, nonce/replay-защиту (уникальный `Idempotency-Key` уже обязателен — зафиксировать, что повтор с тем же ключом возвращает прежний ответ, а не новый переход); убрать секрет из query (заголовок `X-Hub-Signature-256`). Для триггеров — ротируемый per-trigger secret и явное `revoked_at`.

### C-4. Две несовместимые схемы вебхуков: спека противоречит glossary/workflow-domain (D-05)
- **Место:** §3, стр. 90–98 (`/api/webhooks/triggers/{triggerId}`, `/api/webhooks/tasks/{taskId}`) vs `glossary.md` §7 и `workflow-domain.md` §7 (`POST /api/webhooks/{taskId}?signature=...`), `decisions.md` D-05.
- **Описание:** утверждённые доки фиксируют **один** stateless-эндпоинт `POST /api/webhooks/{taskId}`. Спека вводит два разных корня (`/tasks/{taskId}` и `/triggers/{triggerId}`), т.е. меняет внешний контракт и трактовку D-05, не отражая это как решение. Дополнительно: вебхуки выведены из-под `/v1` (см. M-18), хотя это публичный внешний контракт с наибольшей ценой изменения.
- **Предложение:** привести к единой схеме из D-05 либо зафиксировать новое решение в `decisions.md` и синхронно поправить `glossary.md`/`workflow-domain.md`. Задать стабильный версионированный путь (например, `/api/v1/webhooks/...` или `/webhooks/v1/...`).

### C-5. `includeHidden=true` раскрывает скрытые COMPACT/rewind-сообщения любому VIEW
- **Место:** §1, стр. 25 (`?includeHidden=`), стр. 38–44.
- **Описание:** по инварианту видимость скрытых сообщений — производная от `COMPACT.covers` (`glossary.md` §4, инвариант 1), а `rewind` — «маркер отсечки, последующее скрыто». Флаг `includeHidden` в `GET /messages` и в SSE позволяет любому держателю VIEW выгрузить весь «сжатый»/откатанный контент. Это ломает смысл rewind (откат перестаёт быть откатом) и может раскрывать то, что модель вытеснила из контекста (в т.ч. секреты/tool-output).
- **Предложение:** убрать `includeHidden` из публичного контракта либо ограничить его владельцем/ролью аудита и явно задокументировать, что это debug/audit-режим с повышенными правами; для rewind-скрытого — отдельное право. В спеке описать интеракцию «includeHidden × COMPACT × rewind».

## MAJOR

### M-1. Scope `TAGGED(x)` для WAIT_TASKS нечем выразить
- **Место:** §3 «Задачи», стр. 59–70; `glossary.md` §3 (`TAGGED(x)`), `workflow-domain.md` §2 (`scope: TAGGED(x)`).
- **Описание:** `TAGGED(x)` — подзадачи с тегом; поля тегов нет ни в `task` (`data-model.md` §4), ни в `TaskDto`, ни в API создания/патча задачи. Барьерные стейджи из сценария «Сделай биллинг» (`workflow-domain.md` §5) на группах подзадач не собираются.
- **Предложение:** добавить `tags` в `TaskDto` и `task` (или `params`), параметры `tags?` в `POST /tasks`, `POST /tasks/{id}/subtasks`, `PATCH /tasks/{id}`; описать, что `TAGGED` матчит.

### M-2. Нет API папок (`Folder`) и folder-shares
- **Место:** §1, стр. 20 (`?folder=`), стр. 31 (`shares`); `glossary.md` §1; `data-model.md` §1 (`folder`, `Share.resource_type=FOLDER`).
- **Описание:** `folderId` можно задать, `?folder=` фильтрует, `Share` умеет `resource_type=FOLDER`, но создать/перечислить/переименовать папку и выдать folder-share нечем. Центральный сценарий мультипользовательности (D-18) не реализуем через API.
- **Предложение:** добавить `/api/v1/folders` (POST/GET, GET/PATCH/DELETE `{id}`, `GET /folders/{id}/tree`) и `GET/POST/DELETE /folders/{id}/shares`.

### M-3. Комментарии задачи только пишутся, но не читаются
- **Место:** §3, стр. 68 (`POST /tasks/{id}/comments`).
- **Описание:** `TaskComment` append-only, но `GET /tasks/{id}/comments` отсутствует. Прочитать обсуждение задачи невозможно (история переходов его не содержит).
- **Предложение:** добавить `GET /tasks/{id}/comments` с пагинацией (`?cursor=&limit=`), `author`, `body`, `createdAt`, с учётом прав M-2/C-2.

### M-4. Триггеры требуют таблицу, но data-model это отрицает, и вопрос открыт
- **Место:** §3 «Триггеры», стр. 86–92; §6.3, стр. 138; `data-model.md` §6; `glossary.md` §6.
- **Описание:** `POST /triggers` → `TriggerDto {id, url}`, `GET/DELETE` подразумевают хранение сущности (secret/owner/состояние), однако `data-model.md` §6 прямо утверждает «Отдельных таблиц нет». При этом §6.3 спеки выносит необходимость `trigger`-таблицы как **открытый вопрос** — при том что документ объявлен источником истины и уже описывает контракт по ней.
- **Предложение:** либо закрыть открытый вопрос решением (D-XX) и добавить `trigger` в `data-model.md`, либо убрать триггеры из спеки до подтверждения. Спека-источник-истины не должна содержать непринятых решений.

### M-5. Пагинация и конверты списков несогласованы
- **Место:** §0.4 (стр. 10) vs §1 стр. 25 (`MessageDto[]`, курсор = max seq), стр. 30 (`tree` → `TreeNode[]`), §3 стр. 60/67/68/69/70, §6.
- **Описание:** §0.4 требует `?cursor=&limit=` и поле `nextCursor` в списковых ответах. Фактически: `GET /messages` возвращает голый массив с `?since=<seq>` (не `cursor`), без `nextCursor`; `tree`, `comments`, `dependencies`, `/workflows`, `/triggers`, `/shares` — голые массивы без пагинации. `GET /tasks/{id}/history?since=&cursor=` смешивает оба режима без приоритета.
- **Предложение:** единый конверт `{ items, nextCursor? }` для всех коллекций; явно развести «потоковую» (`since`, для messages/events) и «списковую» (`cursor`) пагинации; определить поведение при одновременной передаче `since`+`cursor`.

### M-6. Кэшируемость не определена, rate limiting отсутствует
- **Место:** §0 (в целом).
- **Описание:** измерение «кэшируемость» в спеке не раскрыто: нет `ETag`/`If-None-Match`/`Cache-Control` ни для `GET /sessions/{id}`, ни для immutable-ресурсов (`MessageDto`, `WorkflowRevision`, `TransitionDto`), ни для `WorkflowRegistry`. Immutable append-only сущности — идеальные кандидаты на вечные кэши. Также нет `429`/`Retry-After` для анонимных вебхуков (риск DoS/брутфорса).
- **Предложение:** задать политику кэширования (immutable → `Cache-Control: immutable, max-age=...` + `ETag`; персональные списки → `private, no-cache`), описать условные запросы и `429`.

### M-7. Браузерные SSE/WS не могут передать `Authorization: Bearer`
- **Место:** §0.1 (стр. 7), §2 (стр. 44), §4 (стр. 102).
- **Описание:** спека объявляет Bearer JWT на всех эндпоинтах, но нативный `EventSource` (SSE) и `WebSocket` **не позволяют задавать заголовки**. Для WebUI (D-19) контракт неисполним в браузере без переноса токена в query/subprotocol/cookie, а токен в query утекает в логи.
- **Предложение:** определить способ передачи токена для SSE/WS: WebSocket — `Sec-WebSocket-Protocol` (subprotocol) или short-lived одноразовый `ticket`; SSE — cookie с `SameSite=Strict`/refresh или одноразовый ticket; явно запретить долгоживущий JWT в query.

### M-8. SSE: `session.status` без `seq` → пропуск статус-переходов при переподключении
- **Место:** §2, стр. 44–51.
- **Описание:** переподключение предлагается «повторным `?since=` от последнего seq» и `Last-Event-ID = seq`. Но `seq` есть только у сообщений; у `session.status` (и `ping`) нет `seq`. Если клиент продолжит с `since = lastMessageSeq`, он **не получит** переходы `runtimeStatus`, произошедшие, пока он был отключён (у них нет позиции в потоке). Не сказано также, что SSE-событие несёт поле `id:` (без него `Last-Event-ID` не работает).
- **Предложение:** либо ввести сквозной монотонный `eventSeq` на все типы событий, либо на реконнекте всегда отдавать текущий `session.status` первым событием; явно указать `id: <seq>` в протоколе; описать приоритет `since` vs `Last-Event-ID`.

### M-9. Relay: нет контракта ошибок, отмены in-flight и переподключения
- **Место:** §4, стр. 104–119.
- **Описание:** определены только `register/registered/tool.call/tool.result/tool.progress/ping`. Не определено: (1) как сервер сообщает об ошибке (например, `409 executor-already-connected`, недопустимый `tool`, отказ в правах) — по WS нет HTTP-статусов; (2) что происходит с выданным `tool.call`, если Turn отменён/task ушёл из CLIENT_EXEC (в дизайне — «синтетический `TOOL_RESULT` cancelled»); (3) что делать с незавершёнными вызовами при разрыве («разрыв = исполнитель отпущен» — но кто закрывает pending_tool_calls?); (4) как переподключиться (resume/`since`).
- **Предложение:** добавить `type:error {code, message, refId}`, `type:tool.cancel {callId}`, `type:hello/welcome` с protocol version, семантику разрыва и повторной регистрации; связать с рестарт-сканом и `pending_tool_calls`.

### M-10. Relay: нет авторизации workspace по `taskId` при регистрации
- **Место:** §4, стр. 104–110.
- **Описание:** клиент регистрирует workspace `{taskId, binding}`. Не сказано, что сервер проверяет право вызывающего на эту задачу (`PARTICIPANT`/владелец). Любой аутентифицированный клиент может зарегистрироваться на чужой `taskId` и получать/выполнять `tool.call` (в т.ч. читать/писать файлы) — перехват исполнения.
- **Предложение:** явно указать проверку `AccessPolicy` на `taskId` при `register`, коды ошибок, и что workspace-лок освобождается по TTL/дисконнекту.

### M-11. Архивация сессии (`DELETE`) не представлена в схеме; фильтр архивных не определён
- **Место:** §1, стр. 23 (`DELETE → архивация → 204`); `data-model.md` §5 (`session`).
- **Описание:** в `session` нет поля `archived_at`/`status`, поэтому «архивация» нечем хранить. Не сказано, попадают ли архивные сессии в `GET /sessions`, в SSE, в `tree`, в `mine`. Плюс семантический зазор: `DELETE` = soft-archive (см. m-2).
- **Предложение:** добавить поле архива в модель данных и параметр фильтра (`?archived=`), либо переименовать операцию в `POST /sessions/{id}/archive`; описать влияние на видимость и attach.

### M-12. Fork/rewind-маркеры не представлены в схеме и ДТО
- **Место:** §1, стр. 26–27; `glossary.md` §4 (`Fork`: `source_session_id + seq_cutoff`); `data-model.md` §5.
- **Описание:** `fork` опирается на `source_session_id` и `seq_cutoff`, `rewind` — на «маркер отсечки», но этих полей нет в `session`, а `SessionDto` не несёт `forkedFrom`/`cutoff`/`rewindSeq`. После форка клиент не отличит форк от обычной сессии и не поймёт область видимости.
- **Предложение:** добавить поля в `data-model` и/или в `SessionDto` (`forkedFrom: {sessionId, atSeq}?`, `rewindToSeq?`); определить, что возвращает `GET /messages` для форка до cutoff.

### M-13. `/compact` не ограничен FREE-сессиями, вопреки глоссарию
- **Место:** §1, стр. 28; `glossary.md` §4 («`/compact` — та же механика по команде для свободных сессий»); `execution-model.md` §5.
- **Описание:** спека даёт владельцу право вызвать `/compact` на любой сессии (в т.ч. STATE). Для STATE-сессий это подменяет контекст аудируемой задачи и не согласуется с ограничением «только FREE», как у fork/rewind.
- **Предложение:** либо на STATE возвращать `409 wrong-session-kind` (согласованно с fork/rewind), либо зафиксировать решение, что компакция разрешена и в STATE, поправив глоссарий.

### M-14. `POST /sessions/{id}/export` — POST на чтение с правами VIEW
- **Место:** §1, стр. 30.
- **Описание:** экспорт — безопасная, идемпотентная, кэшируемая операция чтения, но выражена небезопасным `POST` (при этом права — VIEW). Это ломает семантику HTTP-методов, кэширование и клиентские ретраи.
- **Предложение:** `GET /sessions/{id}/export?format=markdown|json` с content negotiation (`Accept`/`Content-Disposition`); если экспорт дорогой — `202 + GET /exports/{id}`.

### M-15. Нет потоковой подписки на события задачи/поддерева
- **Место:** §2 (только session SSE), §3 (`GET /tasks/{id}/history`, `tree`, без стриминга).
- **Описание:** клиент, «следящий вместе с оркестратором» (`glossary.md` §3) или мониторящий billing-сценарий, не получает push о смене `currentState`/`statusProjection`, о разрешении `WAIT_TASKS`, о входах подзадач в терминал. Есть только polling `history` с неоднозначным `?since=&cursor=`. При большом дереве это неэффективно и не даёт реального «слежения».
- **Предложение:** добавить SSE `GET /api/v1/tasks/{id}/events?since=` (переходы, смена статуса, suspended, терминалы подзадач) или `GET /api/v1/events` с фильтром по поддереву; определить `seq` для истории переходов.

### M-16. Схема Validation Details для `422` не определена; каталог ошибок неполон
- **Место:** §0.2 (стр. 8), §3 стр. 79/84, §5 (стр. 121–132).
- **Описание:** сказано «`422` с деталями / с указанием вершины/правила», но структура деталей не задана (нет `errors[]`, `pointer`, `rule`). Каталог кодов не покрывает 400 (невалидное тело/параметр), 401 (нет/просрочен токен), 403 vs 404 для недоступных сессий, 405, 415, 429, а также ошибки relay (M-9). Расширение `code` объявлено «машиночитаемым каталогом», но в спецификации он неполон — SDK не сгенерирует корректную обработку.
- **Предложение:** определить JSON-схему `errors[]` для 422 (например, `{pointer, rule, message}`), дополнить каталог всеми реальными кодами, зафиксировать `instance` (что именно кладётся) и `type`-URI.

### M-17. `PATCH`: не определено различие `null` и отсутствующего поля
- **Место:** §1, стр. 22; §3, стр. 62.
- **Описание:** `PATCH /sessions/{id}` `{ title?, folderId?, visibility? }` — не сказано, как очистить `folderId` (вынести из папки) или сбросить `title`. `null` может означать «не менять» и «очистить» одновременно — двусмысленность, влияющая на реализацию и SDK.
- **Предложение:** явно задать семантику (например, `null` = очистить, отсутствие = не трогать), либо использовать JSON Merge Patch (RFC 7396) с оговоркой; применить единообразно к задачам.

### M-18. Версионирование: вебхуки вне `/v1`, и сам `/v1` не решён
- **Место:** §0.5 (стр. 11), §3 стр. 90/92/98, §6.4 (стр. 139).
- **Описание:** §0.5 требует `/api/v1/...`, но публичные вебхуки — `/api/webhooks/...` (без версии), хотя это наиболее дорогой для изменения внешний контракт. Одновременно §6.4 оставляет необходимость `/v1` открытым вопросом, при том что весь документ уже построен на `/v1`. Спека-источник-истины содержит нерешённые пункты.
- **Предложение:** принять решение по `/v1` (закрыть §6.4), версионировать вебхуки явно (`/webhooks/v1/...` или `/api/v1/webhooks/...`), убрать открытые вопросы из утверждённой спеки в отдельный список задач.

### M-19. Создание сессии: не определены `kind` и правило выбора ревизии агента
- **Место:** §1, стр. 19; `SessionDto` стр. 34; `glossary.md` §4; `data-model.md` §5.
- **Описание:** `POST /sessions { title?, agentKey, folderId?, visibility? }` не содержит `kind`, но `SessionDto.kind ∈ FREE|STATE`, а STATE-сессии создаёт движок при входе задачи в состояние (`execution-model.md` §7). Не сказано, что публичный POST создаёт **только FREE**, и что делать при попытке создать STATE вручную. Также `agentKey` без `rev`: не зафиксировано, что берётся последняя ревизия агента и что `SessionDto.agent.rev` — именно она.
- **Предложение:** явно указать «создаёт только FREE»; описать правило пина ревизии агента (последняя на момент создания) и, при необходимости, опциональный `agentRev`.

### M-20. Дерево: глубина/семантика и отсутствие `lastSeq` для attach к субагенту
- **Место:** §1, стр. 32 (`TreeNode[]`), §3 стр. 70.
- **Описание:** `tree` назван «поддерево», но не сказано — прямые дети или рекурсивно; поля узла `{id, parentSessionId, agent, runtimeStatus, lastActivityAt}` не содержат `lastSeq`, а для «проваливания в субагента» (Attach-CLI, `glossary.md` §8) клиенту нужен курсор attach и признак STATE/FREE. `Task tree` — аналогично без глубины/пагинации.
- **Предложение:** определить рекурсивность (или параметр `depth`), добавить в `TreeNode` `kind`, `lastSeq`, `taskId?`; добавить пагинацию/лимит.

## MINOR

### m-1. Action-эндпоинты (RPC-стиль)
- **Место:** §1–§3 (`/fork`, `/rewind`, `/compact`, `/stop`, `/suspend`, `/resume`, `/export`).
- **Описание:** смешение ресурсного и командного стилей. Допустимо, но затрудняет единообразие SDK и кэширование.
- **Предложение:** либо последовательно оформить команды как подресурсы (`POST /sessions/{id}/stop-requests`), либо явно декларировать RPC-подход и не применять к ним REST-ожидания.

### m-2. `DELETE` = архивация — семантический разрыв
- **Место:** §1, стр. 23.
- **Описание:** `DELETE` исторически означает удаление; клиенты/SDK могут считать ресурс исчезнувшим, тогда как он лишь архивируется (см. M-11).
- **Предложение:** `POST /sessions/{id}/archive` (+ `DELETE` для настоящего удаления, если появится) либо явная документация клиентам.

### m-3. `201` без `Location`
- **Место:** §1 стр. 19/26, §3 стр. 59/63/68/79/82/90/92.
- **Описание:** RFC 9110 рекомендует `Location` для `201`. Не указан.
- **Предложение:** добавить `Location` в ответы создания.

### m-4. Несогласованные статусы
- **Место:** §3, стр. 64–69.
- **Описание:** `suspend` → `202`, но `resume` → `204`; `dependencies` → `204` (создание ресурса не отражено).
- **Предложение:** единообразие: suspend/resume — `202/204` симметрично; создание зависимости — `201` или обоснованный `204`.

### m-5. `Idempotency-Key`: TTL, scope и поведение повтора не определены
- **Место:** §0.3, стр. 9; §5 `idempotency-conflict`.
- **Описание:** не сказано, что последовательность `same key + same body` возвращает исходный ответ (replay), каков TTL, scope (per-user/per-session) и что делать при отсутствии ключа на вебхуке (400?).
- **Предложение:** описать поведение, TTL, scope и коды для отсутствующего/просроченного ключа.

### m-6. `ping` как SSE-комментарий vs элемент списка; нет `retry:`
- **Место:** §2, стр. 46–49.
- **Описание:** `ping` объявлен «SSE-комментарием», но перечислен среди событий; не задан `retry:`.
- **Предложение:** либо комментарий `: ping`, либо именованное событие; задать `retry`.

### m-7. `atSeq`/`toSeq`: включительно/исключительно
- **Место:** §1, стр. 26–27.
- **Описание:** не определено, входит ли указанный seq в форк/в остаток после rewind.
- **Предложение:** явно описать границы (half-open interval).

### m-8. Смешение имён/enum: `runtimeStatus` vs `statusProjection`, повтор `kind`
- **Место:** §1 стр. 20/34/36.
- **Описание:** два разных enum статусов и один параметр `kind` для сессий и сообщений — источник ошибок интеграции.
- **Предложение:** переименовать (`messageKind` vs `sessionKind`) или явно разграничить в описании.

### m-9. Форматы `binding` / `workspaceId` / `lockedBy` не определены
- **Место:** §2 стр. 48; §4 стр. 106–109.
- **Описание:** термины отсутствуют в глоссарии; неясно, `lockedBy` — id инстанса или пользователь, как формируется `workspaceId`.
- **Предложение:** внести в глоссарий и задать форматы.

### m-10. Нет `GET /messages/{id}` и списка разрешённых переходов
- **Место:** §1, §3.
- **Описание:** `COMPACT.covers` ссылается на id сообщений, но получить сообщение по id нельзя (только диапазон `since`). UI не может построить навигацию.
- **Предложение:** добавить `GET /sessions/{id}/messages/{messageId}`; опционально `nextStates` в `TaskDto`.

### m-11. Нет пагинации у `/workflows`, `/triggers`, `/shares`, `tree`, `dependencies`
- **Место:** §1 стр. 31–32; §3 стр. 69–70, 78–91.
- **Описание:** коллекции без `limit`/`cursor` — риск больших ответов.
- **Предложение:** применить единый конверт (M-5).

### m-12. Нет сортировки и описания полей поиска `q`
- **Место:** §1 стр. 20; §3 стр. 60.
- **Описание:** неясно, какие поля ищет `q`, в каком порядке отдаются результаты.
- **Предложение:** задать поля поиска и параметр `sort`.

### m-13. CORS/405/415/406 не описаны
- **Место:** §0.
- **Описание:** для WebUI (другой origin) CORS критичен; коды 405/415/406 отсутствуют.
- **Предложение:** описать CORS-политику и дополнительные коды.

### m-14. Экспорт: media type и `Content-Disposition` не заданы
- **Место:** §1, стр. 30.
- **Описание:** `200 file` — не определены `Content-Type` (`text/markdown`, `application/json`), имя файла, кодировка.
- **Предложение:** задать заголовки и имена.

### m-15. VIEW видит сырые `TOOL_RESULT`/`SYSTEM` (в т.ч. seed-контекст состояний)
- **Место:** §2, стр. 47; §1 стр. 36; `execution-model.md` §7.
- **Описание:** VIEW-подписчик получает полные payloads инструментов и системные сообщения (пути, вывод команд, возможно секреты окружения). Спека не декларирует маскирование или отдельный уровень раскрытия.
- **Предложение:** ввести «проекцию для VIEW» (без сырых payloads) или отдельное право на tool-output; задокументировать, что относится к чувствительным данным.

### m-16. Нет эндпоинта скачивания артефактов workspace
- **Место:** §0–§6; `glossary.md` §8 (WebUI: «кнопка скачать»); D-19.
- **Описание:** заявленный сценарий WebUI не покрыт API.
- **Предложение:** добавить `GET /sessions/{id}/workspace/files` / `GET .../files/{path}` (с правами VIEW) либо зафиксировать отложенность.

### m-17. Нет кода/статуса для «клиент не подключён» в CLIENT_EXEC
- **Место:** §4, стр. 118; §5.
- **Описание:** «нет подключённого исполнителя → Turn паркуется, задача WAITING» — но во внешнем API нет ни кода, ни способа увидеть причину парковки (есть только `PARKED_ASYNC`).
- **Предложение:** добавить код/признак (например, `client-not-connected`) и/или `runtimeStatus` `PARKED_CLIENT`.

### m-18. 403 vs 404: энумерация сессий
- **Место:** §5, стр. 126 (`forbidden` 403).
- **Описание:** ответ `403` на существующую, но недоступную сессию позволяет перечислять чужие id; `404` скрывает существование.
- **Предложение:** для отсутствия гранта отдавать `404` (или обосновать выбор `403`) единообразно.

## Приоритет исправлений (топ-3)
1. **C-1 / C-2 / C-3** — безопасность и права: без определённой авторизации workflow/триггеров, без модели прав задач и со статической подписью без покрытия тела спека небезопасна и нереализуема.
2. **C-4 / M-4 / M-18** — контракт вебхуков и триггеров: две противоречащие схемы, нерешённая сущность и открытый вопрос в источнике истины.

## 2.2. Новые проблемы v2

### N-1 (CRITICAL). Capability-токен вебхука выдаётся держателям TASK-VIEW — эскалация VIEW → переход задачи
- **Место:** §4.4 («`webhookUrl` выдаётся … полем TaskDto (WAIT_WEBHOOK, TASK-VIEW)»), §4.1 `TaskDto.webhookUrl?`, §7 (задача VIEW = «TaskDto, history, tree, SSE»).
- **Описание:** `webhookUrl` — это и есть capability-токен (единственный секрет; иного proof на вебхуке нет). Спека отдаёт его всем, у кого TASK-VIEW, тогда как движение задачи (`transition`, `subtasks`, `dependencies`) требует TASK-PARTICIPATE. Итого read-only грант фактически даёт write-capability: любой VIEW-участник может дёрнуть `POST /api/webhooks/tasks/{taskId}/{token}` и перевести задачу. Плюс `TaskDto` фигурирует и в списковом `GET /tasks`, т.е. токен размножается по выдаче.
- **Предложение:** выдавать `webhookUrl` только TASK-PARTICIPATE (и владельцу), а не TASK-VIEW; либо отдельный эндпоинт `GET /tasks/{id}/webhook-url` с правом PARTICIPATE. Явно разграничить: D-27 разрешает *видеть* payloads, но не *исполнять* переходы.

### N-2 (MAJOR). Обязательный `Idempotency-Key` на вебхуках нереализуем для внешних отправителей и противоречит «stateless/без БД»
- **Место:** §0.3, §4.4 (`Idempotency-Key` — компенсация), §4.4 «проверка без БД» (продублировано в `glossary.md` §7), `data-model.md` §6 (таблица `idempotency_key`).
- **Описание:** Внешняя система, получившая capability-URL, обычно не знает о внутреннем контракте и не пришлёт `Idempotency-Key`. Что тогда — `400`? Это ломает основной сценарий триггеров (внешний вебхук → задача). Одновременно «stateless, проверка без БД» уже неверно: replay-защита требует записи/чтения `idempotency_key`, т.е. состояния и БД на анонимном пути (который к тому же доступен для записи в таблицу без аутентификации → возможность замусорить хранилище).
- **Предложение:** сделать `Idempotency-Key` на вебхуках **опциональным** (при отсутствии — защита только rate-limit + `409` вне WAIT_WEBHOOK + окно дедупликации по `(token, taskId, body-hash)` на N секунд), либо явно вернуть БД в «stateless»-формулировку; определить, чем является «субъект» scope для анонимного вызывающего.

### N-3 (MAJOR). `idempotency_key` без PK/уникальности: коллизии между эндпоинтами и областями
- **Место:** `data-model.md` §6 `idempotency_key (key, scope, request_hash, response_json, expires_at)`.
- **Описание:** PK/UNIQUE не задан. Если ключом сделают `key`, то один и тот же `Idempotency-Key` на `POST /messages` и на вебхуке столкнётся (а спека обещает «`scope` = путь + субъект»). Если `(scope,key)` — надо это зафиксировать. Также не задан индекс очистки по `expires_at`.
- **Предложение:** PK `(scope, key)`, INDEX `(expires_at)`; описать субъект для анонимных вебхуков.

### N-4 (MAJOR). `GET /sessions/{id}/workspace/files?path=` — path traversal и утечка секретов workspace
- **Место:** §2 (право VIEW), §8 (вне объёма — только задачные состояния).
- **Описание:** относительный путь из запроса без описанной нормализации/jail позволяет выйти за пределы workspace (`../../`, symlink). Право VIEW (а не владелец) даёт чтение любого файла каталога, в т.ч. `.env`, ключей, результатов чужих состояний. Для STATE-сессий эндпоинт вообще вне v1 (§8), но вызов на STATE не определён (404? 403? пусто?).
- **Предложение:** нормализовать путь и жёстко ограничить корнем workspace, запретить symlink-выход, задать allowlist/max-size, вернуть `400 invalid-path`; определить поведение для STATE-сессий.

### N-5 (MAJOR). События задачи (§3.2) не решают реконнект — фикс M-8 применён только к сессиям
- **Место:** §3.1 (сессии — «первым всегда текущий `session.status`») vs §3.2 (задачи — только перечень событий и `?since=`).
- **Описание:** у `task.transition` есть id, но у `task.status`/`subtask.terminal`/`task.comment` своей позиции нет; не сказано ни «первым отдаём текущий `task.status`», ни приоритет `Last-Event-ID`, ни значение `?since=` для статусных событий. Клиент после дисконнекта пропустит смену статуса/терминал подзадачи — ровно тот дефект, что закрыт для сессий.
- **Предложение:** распространить механику §3.1 на §3.2: сквозной `eventSeq` либо первым событием текущий `task.status`; определить `id:` и приоритет `Last-Event-ID`.

### N-6 (MAJOR). Relay: нет подтверждения `register` и не определено число workspace на соединение
- **Место:** §5 (таблица фреймов).
- **Описание:** `hello`/`welcome` определены, а успешный ответ на `register {taskId,binding,basePath}` — нет (`workspaceId` из v1 удалён, но ack не заменён). Клиент не знает, принята ли регистрация, до первого `tool.call`. Также не сказано, сколько workspace может держать одно WS-соединение и как их различать (в `tool.call` есть только `sessionId`).
- **Предложение:** добавить `← registered { workspaceRef }`; задать `maxWorkspaces`/разрешить несколько `register` на соединение либо явно «одно соединение = один workspace»; термины `binding`/`workspaceRef` внести в глоссарий.

### N-7 (MAJOR). Папки: внутреннее противоречие про cascade, цикл перемещения, наследование при перемещении сессии
- **Место:** §1.6 (`PATCH/DELETE /folders/{id}` — «только пустой или каскадом — `409 folder-not-empty`»), §1.6 (наследование FOLDER→SESSION).
- **Описание:** «только пустой **или** каскадом — 409» читается двояко: каскад разрешён или всегда 409? Если каскад — нет параметра (`?cascade=`/тело) и не сказано, что делать с сессиями/шарами. Не описана защита от цикла при `PATCH parentId` (перенос папки в собственного потомка). Не определено, что происходит с правами при `PATCH /sessions/{id}` с `folderId`: сессия, перемещённая в расшаренную папку, мгновенно становится видна? перемещённая наружу — теряет доступ? Как приоритет SESSION-share vs FOLDER-share.
- **Предложение:** развести семантику явным флагом каскада; запретить цикл (`422 folder-cycle`); описать пересчёт прав при перемещении и приоритет явного SESSION-share над наследованным FOLDER-share.

### N-8 (MAJOR). Смежные доки синхронизированы не полностью: старая схема вебхуков осталась
- **Место:** `glossary.md:43` (WAIT_WEBHOOK: `POST /api/webhooks/{taskId}?signature=HMAC(secret, taskId)`), `workflow-domain.md:43` (та же строка в §3), `decisions.md` D-05 (`POST /webhooks/{taskId}?signature=HMAC(secret, taskId)`) — против v2 §4.4, `glossary.md` §7, `workflow-domain.md` §7 и D-26.
- **Описание:** при заявленной синхронизации три места сохранили прежний контракт, противоречащий v2 и D-26. Спека-источник-истины ссылается на доки, которые сами себе противоречат (§3 vs §7 в `workflow-domain.md`). Для контракт-first это дефект.
- **Предложение:** обновить три места либо пометить D-05 как «заменено D-26» и убрать старую строку из §3 `workflow-domain.md`.

### N-9 (MINOR). Роль `harness-admin` не определена
- **Место:** §4.2, D-28. **Описание:** роль используется как грант, но её нет ни в `glossary.md`, ни в описании маппинга Keycloak-realm-roles. Непонятно, кто её выдаёт.
- **Предложение:** зафиксировать realm-role и способ назначения (в рамках §9.6, не оспаривая сам концепт).

### N-10 (MINOR). Приоритет `since` vs `Last-Event-ID` противоречит сам себе
- **Место:** §0.4 («Переданы оба — `since` приоритетен») vs §3.1 («При наличии `Last-Event-ID` он приоритетен над `?since=`»).
- **Предложение:** оставить одно правило; для SSE логичен `Last-Event-ID`, тогда §0.4 надо оговорить.

### N-11 (MINOR). `POST /auth/ticket` → 201 без `Location`, противоречит §0.7
- **Место:** §0.7 vs §1.4. **Предложение:** исключить билет/токены из правила `201 + Location` явной оговоркой.

### N-12 (MINOR). Открытая ремарка в матрице прав + scope экспорта
- **Место:** §7 («TaskDto (без params при PRIVATE-владельце? — нет: params скрыт не-владельцу)»).
- **Описание:** спека-источник-истины содержит вопросительную формулировку, а `TaskDto`-схема безусловно отдаёт `params` (которые могут содержать секреты) и `webhookUrl`. Также не определено, включает ли `export` скрытые COMPACT/rewind-оригиналы.
- **Предложение:** убрать ремарку в решение; явно описать, скрывается ли `params`/`webhookUrl` от не-владельца, и что попадает в export.

### N-13 (MINOR). `validation-failed` с двумя статусами 400/422
- **Место:** §6. **Описание:** один code на два HTTP-статуса ломает таблицу «code → HTTP» и клиентскую обработку. **Предложение:** развести (`invalid-request` 400 / `validation-failed` 422) или зафиксировать, что 400 — только malformed JSON.

### N-14 (MINOR). `compact` на простаивающей FREE-сессии: доставка и момент выполнения не определены
- **Место:** §2 («результат — `COMPACT`-событие … внутри активного Turn — на границе раунда»). **Описание:** если Turn не активен, чем команда будит сессию (событие? отдельный wake-source `API`) и когда выполнится — не сказано. **Предложение:** описать доставку через событие/synthetic SYSTEM и eligibility.

### N-15 (MINOR). Мелкие несогласованности, введённые/оставшиеся
- `POST /tasks/{id}/dependencies`: «чужой id» → `422 dependency-invalid`, но отсутствие гранта по §6 → `404 forbidden`; какой код побеждает — не определено.
- `GET /tasks?tags=` — семантика совпадения (any/all) не задана.
- `GET /triggers`/`/shares` — без пагинации (остаток m-11); `DELETE /shares` — цель (коллекция или `/shares/{shareId}`?) не указана (ср. minimax MA-3).
- `export?format=markdown|json` — строчные значения при правиле §0.8 «enum `SCREAMING_SNAKE`».
