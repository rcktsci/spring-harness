## 1. S — Spoofing

### S1. Подделка отправителя вебхука (задачный) — ЗАКРЫТО (принято, D-26)
- **Вектор**: любой, кто узнал URL, дёргает `POST /api/webhooks/tasks/{taskId}/{token}` и форсирует переход / подсовывает payload.
- **Компенсация** (api-contracts §4.4): «токен в URL — как unsubscribe-ссылки: утёкший URL позволяет дёрнуть переход. Компенсации: идемпотентность задач по построению (`409` вне WAIT_WEBHOOK), опциональный `Idempotency-Key`…, TLS-only, rate-limit, логирование всех вызовов в `reason`».
- Вред ограничен одним легальным переходом + аудируемый след. Принять как есть.

### S2. Подделка `?source=` (атрибуция в аудите) — ДЫРА (minor)
- **Вектор**: держатель URL пишет `?source=github/ci` — в `reason` попадает ложная атрибуция источника.
- **Дыра**: `source` нигде не охарактеризован; это свободный текст, а не идентичность.
- **Предложение**: в security §3 зафиксировать: «`source` вебхука — untrusted-метка, не идентичность»; при записи в `reason` — ограничить длину/набор символов (санитизация, заодно защита лог-инъекций).

### S3. Подмена атрибуции USER-сообщений — ЗАКРЫТО
- **Вектор**: клиент подсовывает чужой `author`.
- **Компенсация** (api-contracts §2): тело `POST /messages` — только `{ text }`; MessageDto `author?: string (username; только USER)` — проставляется сервером из JWT. Патчей сообщений нет (D-02).

### S4. «Дописывание субагенту» от имени другого — ЗАКРЫТО, но остаточный T/S — ДЫРА (minor)
- **Компенсация** (api-contracts §2): «`POST /messages` на любую сессию дерева **с атрибуцией**» — атрибуция всегда реальный caller, спуфинга нет.
- **Дыра (остаточная)**: если рендер контекста не включает `author`, участник А пишет в сессию субагента, и модель не отличит его текст от слов владельца (социальная инженерия агента).
- **Предложение**: одна строка в execution-model §5: «USER-сообщения рендерятся в контекст вместе с `author`».

### S5. MCP-сервер, выдающий себя за корпоративный — ЗАКРЫТО
- **Компенсация** (agent-tools §3): «серверы из конфигурации (корпоративные 12+ за SSO-прокси), токены обновляет сервер — агент про OAuth не знает». Агент не выбирает сервер и не видит токены; зона доверия — серверная конфигурация + TLS.

### S6. Подмена участника в relay — ЗАКРЫТО
- **Компенсация** (api-contracts §5): `register` — «проверка прав на задачу (TASK-PARTICIPATE), иначе `error forbidden`»; соединение — по билету, «привязан к пользователю» (§1.4).

### S7. Подделка/перебор capability-токена — ЗАКРЫТО
- **Компенсация** (security §1): «capability-токен `HMAC(server_secret, kind:id)` в пути (D-26)»; security §6: «перебор HMAC невозможен».

## 2. T — Tampering

### T1. `graph_jsonb` между ревизией и исполнением — ЗАКРЫТО
- **Вектор**: правка графа «под себя» после создания задач.
- **Компенсация**: workflow-domain §1 — «иммутабельные `WorkflowRevision`», задача пинит ревизию; правка = новая ревизия; право правки — «владелец workflow или роль `harness-admin`» (api-contracts §4.2, аргумент «privilege-эскалация через графики»); инструментальный путь закрыт D-32 («закрыта дыра инструментного пути `edit_workflow`»).

### T2. `task.params` между ревизией и исполнением — ДЫРА (minor)
- **Вектор**: матрица разрешает владельцу менять `params` (api-contracts §7: «`params` — владелец»), при этом `${task.params.*}` участвует в разрешении workspace (`SERVER_DIR PATH: path?: "${...}"`), scope `WAIT_TASKS` (`EXPLICIT(${task.params.key})`) и триггерах. Правка params на лету меняет поведение следующих состояний задачи, включая путь workspace.
- **Предложение (минимальное)**: `params` задачи иммутабельны с первого перехода; правка — только в `suspended`, каждое изменение — строка в `task_transition_history` (SYSTEM, «params updated»). Одна инвариантная строка в data-model §6 + матрица §7.

### T3. Tool-output инъекция (prompt injection через TOOL_RESULT/MCP) — ЗАКРЫТО (принятый остаточный риск)
- **Вектор**: вредоносный вывод инструмента/MCP-сервера инструктирует агента.
- **Компенсация**: agent-tools §4: «Текстовые deny-паттерны bash… **не считаются** security-границей…; реальная граница — биндинг workspace и (эволюция) контейнеры» + D-32 (пересечение прав) + лимит/усечение вывода. Урон инъекции ограничен правами сессии.
- **Предложение (doc-only)**: в security §6 строка «весь tool-output/MCP-вывод — untrusted text; граница — D-32 + контейнер (принятый риск)».

### T4. Подмена helper-образа — ДЫРА (minor)
- **Вектор**: компрометация registry / подмена образа при backoff-обновлении.
- **Компенсация (частичная)**: execution-model §1 — «образ обязан присутствовать локально на VM (собирается при деплое); pull из registry — только retry/backoff на случай обновления»; security §6 — «выделенная VM без других нагрузок».
- **Дыра**: digest не пинится — при «обновлении» ничто не сверяет содержимое.
- **Предложение**: пин helper-образа по digest в конфиге (`HARNESS_HELPER_IMAGE@sha256:…`); проверка digest при создании контейнера. В стиле проекта: одна конфиг-строка + одна проверка.

### T5. Payload вебхука в `reason` — ДЫРА (minor; размер — см. D2)
- **Вектор**: внешний текст пишется в бессрочный `task_transition_history` (security §5) — ложные следы в аудите, неограниченный размер.
- **Компенсация (частичная)**: `payloadSchema` состояния опциональна (workflow-domain §2); «в `reason`/payload вебхуки пишут тела вызовов (по дизайну аудита)» (security §3).
- **Предложение**: усечение payload при записи в `reason` (конфиг-лимит, маркер усечения — как у tool-вывода); для WAIT_WEBHOOK-состояний с внешними отправителями — рекомендовать обязательную `payloadSchema` (ERROR-переход уже предусмотрен).

### T6. Подмена/удаление сообщений задним числом — ЗАКРЫТО
- **Компенсация**: «Сообщения неизменяемы: PATCH/DELETE не существует» (api-contracts §2); D-02 «строки не мутируют никогда»; UPDATE/DELETE запрещены инвариантом data-model §7.

### T7. Фальсификация `tool.result` relay-клиентом — ЗАКРЫТО (принятая граница доверия)
- **Вектор**: клиент присылает выдуманные output/exitCode, не исполняя ничего.
- **Компенсация**: исполнитель — машина участника с TASK-PARTICIPATE (D-18, один тенант); верификация исполнения вне MVP.
- **Предложение (doc-only)**: зафиксировать в security §6 как принятый риск (см. R3).

## 3. R — Repudiation

### R1. Переходы задачи — ЗАКРЫТО
- **Компенсация**: «`task_transition_history` (каждый ход задачи с обоснованием — **хранится бессрочно**)» (security §5); `transition` с обязательным `reason` (agent-tools §2); append-only.

### R2. Bash-исполнения — ЗАКРЫТО
- **Компенсация**: operations §1: «контейнерный stdout агентского bash не durable — полный вывод живёт в `TOOL_RESULT` сессии»; текст команды — в `TOOL_CALL` (append-only `session_message`); для BASH_SCRIPT — «вывод+exit → reason» (workflow-domain §3).

### R3. Relay-исполнения на клиенте — ДЫРА (частичная,_accepted residual_)
- **Вектор**: участник отрицает «это не я исполнял/испортил файлы» — сервер не знает, кто и когда держал workspace.
- **Есть**: `TOOL_CALL`/`TOOL_RESULT` пишутся в сессию; «Локальный audit-файл relay-клиента (`~/.harness/logs/relay-audit.jsonl`) — рекомендация в client-cli, не серверный контракт» (operations §8).
- **Дыра**: на сервере нет следа факта регистрации/отпускания исполнителя.
- **Предложение (минимальное)**: SYSTEM-сообщение в сессию задачи на `register`/разрыв («executor подключился: user X, binding Y» / «отпущен») — уже есть механика seed-SYSTEM; плюс строка в security §6 «неверифицируемость relay-исполнения — принятый риск (машина участника)».

### R4. Кто дёрнул вебхук — ЗАКРЫТО с оговоркой
- **Компенсация**: «логирование всех вызовов в `reason`» (D-26). Оговорка: идентичности нет по построению — см. S2 (source = untrusted-метка).

## 4. I — Info disclosure

### I1. VIEW видит сырые payload — ЗАКРЫТО (принято, D-27)
- «VIEW видит сырые payload'ы осознанно (D-27 — прозрачность)» (security §6); api-contracts §7 повторяет.

### I2. `params`/`webhookUrl` у не-владельца — ЗАКРЫТО
- **Компенсация**: TaskDto VIEW — «**без** `params`/`webhookUrl`» (security §2); «`webhookUrl`… отдаётся только TASK-PARTICIPATE и владельцу — capability не выдаётся READ-уровню» (api-contracts §4.1). Capability не утекает через READ — хорошо продумано.

### I3. SSE чужих сессий — ЗАКРЫТО
- **Компенсация**: билет «одноразовый, TTL 60 с, привязан к пользователю» (§1.4); стримы — «права VIEW» (§3.1/3.2); JWT в query запрещён; билеты маскируются в логах (operations §1).

### I4. workspace-files: скачивание любых файлов workspace по VIEW — ЗАКРЫТО (принято)
- Включая случайно попавшие секреты — это поле D-27 (workspace = зона прозрачности FREE-сессий). Path-traversal закрыт: «только относительные пути, резолв внутри корня, `422`» (security §6). Отдельного действия не требует; при желании — одна строка политики «секреты в workspace запрещены».

### I5. Экспорт по VIEW — ЗАКРЫТО (принято)
- `?format=markdown|json` — то же поле прозрачности, что I1.

### I6. Логи — ЗАКРЫТО
- **Компенсация** (operations §1): «обязательный список маскирования (api_key, Authorization, билеты, capability-токены, `task.params`, промпты)».

### I7. `reason` с внешним payload виден TASK-VIEW — ЗАКРЫТО (принято + смягчение в T5)
- Вытекает из D-27; внешние секреты (токены CI) в payload — смягчается усечением/schema (T5).

### I8. MCP-токены — ЗАКРЫТО
- «токены обновляет сервер — агент про OAuth не знает» (agent-tools §3); `api_key` шифруется и «DTO не отдаёт» (security §3).

### I9. Скрытое (COMPACT-оригиналы, скрытое rewind) — ЗАКРЫТО
- «`includeHidden=true` — **только владелец** (аудит-режим)» (api-contracts §2); `read_compacted` у агента ограничен правами сессии.

### I10. Перечисление чужих id — ЗАКРЫТО
- «отсутствие гранта = `404`, не `403`» (security §6, каталог ошибок §6).

## 5. D — DoS

### D1. Глубина/количество `spawn_subagent` (форк-бомба сессий) — **ДЫРА (major)**
- **Вектор**: агент/участник запускает сессию, где агент спавнит субагентов, те — своих… Синхронность spawn (родитель ждёт) не мешает: рекурсия по дереву всё равно плодит сессии, сообщения, LLM-вызовы.
- **Есть**: bulkhead LLM (дефолт 8), потолок контейнеров 50, pids/cpus/memory-лимиты — защищают серверную часть, **но** не ограничивают: число сессий, строк БД, расход токенов, размер очереди eligible.
- **Дыра**: лимитов глубины/ширины spawn и квот сессий в доках нет вовсе.
- **Предложение (минимальное, в стиле проекта)**: конфиг `harness.spawn.maxDepth` (напр. 5) и `harness.spawn.maxChildrenPerSession` (напр. 16) + квота активных сессий на пользователя; превышение → `TOOL_RESULT ERROR` с человекочитаемой причиной (модель видит честный отказ). Строка в execution-model §4 + алерт в operations §7 (активные сессии/пользователь).

### D2. Размер payload вебхуков — ДЫРА (minor)
- **Вектор**: гигантское тело → память + БД (payload → `reason`).
- **Дыра**: max body size для `/api/webhooks/**` не указан (rate-limit есть, размера нет).
- **Предложение**: лимит тела (напр. 1 МБ) → `413` (добавить в каталог §6), усечение при записи в `reason` (T5).

### D3. Триггер-шторм (утечка trigger-URL) — **ДЫРА (major)**
- **Вектор**: утечка trigger-URL → «триггер без ключа создаёт задачу на каждый вызов — дубликаты задокументированы» (api-contracts §0.3) → каждая задача = расход LLM на первом AGENT-состоянии. Rate-limit по IP+пути не спасает от распределённого шторма и не ограничивает суммарный темп.
- **Есть**: revoke убивает URL («`revokedAt=now` — URL умирает мгновенно», D-25), rate-limit 429, `Idempotency-Key` «рекомендован».
- **Дыра**: рекомендованный ключ не обязателен; per-trigger потолка создания задач нет; алерта нет.
- **Предложение**: per-trigger rate-cap (задач/мин, конфиг, превышение → `429`) + алерт «создано задач из одного триггера > N/мин» в operations §7; в D-26-эволюцию — опциональный `maxTasksPerHour` у триггера.

### D4. Гигантские файлы в workspace — ЗАКРЫТО
- **Компенсация**: «дисковая квота workspace — 5 GB (конфиг)» (execution-model §4) + алерт «Диск workspace-тома > 80%» (operations §7); вывод инструментов усекается («вывод инструмента ограничен (защита контекста)», agent-tools §1).

### D5. Fork-шторм — ЗАКРЫТО (принято)
- Fork — только владельцу (api-contracts §2) и только FREE; штормить может владелец только свою сессию (сам себе DoS). Закрывается той же пользовательской квотой сессий, что D1.

### D6. Контейнерный ресурс-шторм — ЗАКРЫТО
- **Компенсация**: «`cpus=2`, `memory=2g`, `pids-limit=512`… потолок одновременно живых контейнеров — конфиг (дефолт 50); idle-вытеснение… reconcile… сироты → удаление» (execution-model §4); алерт «Живые контейнеры ≥ 90% потолка» (operations §7).

### D7. Сжигание токенов через сообщения в шаренных сессиях — ДЫРА (minor)
- **Вектор**: участник PARTICIPATE льёт сообщения → каждый = LLM-вызов за счёт владельца.
- **Дыра**: rate-limit на `POST .../messages` не задан (есть только на вебхуки и билеты).
- **Предложение**: распространить rate-limiting §0.10 на `POST /sessions/{id}/messages` (лимит на пользователя). Одна строка в api-contracts §0.10.

### D8. Rate вебхуков (брутфорс токена) — ЗАКРЫТО
- **Компенсация**: «лимит по IP+пути (`429` + `Retry-After`)», «перебор HMAC невозможен» (security §6). Для брутфорса достаточно; для шторма задач — см. D3.

### D9. SSE-подключения — ЗАКРЫТО (принято)
- Gauge «SSE-подписки» есть (operations §2), жёсткого лимита нет — один тенант, MVP; принять.

## 6. E — Elevation of Privilege

### E1. Дыра D-32: `spawn_subagent(agent_key)` может расширить права вниз — **ДЫРА (major, спек-уровень)**
- **Вектор**: субагент с узкой декларацией спавнит `agent_key` оркестратора (`metaTools = true`). По формуле agent-tools §2b «эффективные права = пересечение прав владельца сессии и декларации агента» ребёнок получает **свои** права оркестратора (владелец тот же) — если у родительского агента metaTools не было, права **расширились вниз**, вопреки глоссарию.
- **Есть**: глоссарий фиксирует свойство: «Вниз по дереву права не расширяются: субагентская сессия наследует не больше прав родительской цепочки» — но **механизм не специфицирован**, а формула в agent-tools §2b ему противоречит (не включает родительскую цепочку).
- **Предложение (минимальное)**:
  1. Единая формула в глоссарии/agent-tools §2b: «эффективные права дочерней сессии = пересечение (**эффективных прав родительской сессии**) и (декларации дочернего агента)».
  2. Гвард: `spawn_subagent` агента с `metaTools = true` разрешён только из сессии, чьи эффективные права включают metaTools, иначе `TOOL_RESULT forbidden`.
- Это одно предложение текста + один предикат в коде — закрывает главный инструментный путь эскалации.

### E2. Мета-инструменты у субагентов (статически) — ЗАКРЫТО (при условии E1)
- «Доступны только агентам, у которых `permissions_jsonb.metaTools = true`» (agent-tools §2b) — проверка по декларации агента сессии; дыра была только в формуле наследования (E1).

### E3. Оркестратор в шаренной сессии — ЗАКРЫТО (принятый остаточный риск)
- **Вектор**: участник шаренной FREE-сессии убеждает оркестратора действовать правами владельца (создать задачу/триггер, править workflow владельца).
- **Компенсация**: D-32 «агент не превышает полномочия принципала»; пересечение; обязательный `reason`; полный аудит.
- **Предложение (doc-only)**: строка в security §6: «prompt-injection в шаренных сессиях → действия правами владельца — принятый риск; эволюция — подтверждение владельцем мета-операций».

### E4. Создание задач «от чужого имени» — ЗАКРЫТО
- **Компенсация**: owner не принимается от клиента: `create_task` — «owner = owner сессии оркестратора», `create_subtask` — «owner = owner родительской задачи» (agent-tools §2b); data-model: «`owner_user_id` при создании задачи агентом наследуется от породившей сессии».

### E5. Relay `register` на чужую задачу — ЗАКРЫТО
- **Компенсация**: «проверка прав на задачу (TASK-PARTICIPATE), иначе `error forbidden`; занято → `error workspace-occupied` (close-код 4409)» (api-contracts §5); VIEW-уровень не проходит (нужен PARTICIPATE); `tool.call` вне CLIENT_EXEC не выдаётся. Не-безопасностная заметка: валидировать `register` по состоянию задачи (уже предложено в api-review) — на эскалацию не влияет.

### E6. Триггеры, создающие задачи с чужими owner — ДЫРА (minor, спек-недоопределённость)
- **Вектор**: владелец триггера вешает его на **чужой** workflow (чтение — всем аутентифицированным) — это легально; но чей owner у задачи, созданной trigger-вебхуком, в доках не сказано. Нефиксация = риск реализации с `owner = null` или автором вызова.
- **Предложение**: одна фраза в api-contracts §4.4: «owner задачи, созданной триггером, = `owner_user_id` триггера» (плюс: `params` задачи — из `params_jsonb` триггера, валидированных при создании).

### E7. Вебхук задачи как эскалация — ЗАКРЫТО (принято, D-26)
- Держатель URL форсирует один легальный, валидируемый ревизией переход с аудитом — это S1, принято.

### E8. Workflow-ревизии как путь эскалации — ЗАКРЫТО
- REST: «владелец workflow или роль `harness-admin`» (api-contracts §4.2); агентный путь: «правка — по делегированию… иначе `forbidden`» (agent-tools §2b); D-32 прямо называет это закрытой дырой.

### E9. Билеты SSE/WS — ЗАКРЫТО
- «одноразовый, TTL 60 с, привязан к пользователю… Повторное использование — `401 ticket-used`. JWT в query запрещён» (§1.4) + «лимит на пользователя» (§0.10) + маскирование в логах.

### E10. `transition` в обход графа — ЗАКРЫТО
- «агент не может "проскочить" — только разрешённые переходы, каждое движение — с обоснованием» (workflow-domain §8); валидация по ревизии; цель — «любое исходящее ребро» (§3), не произвольный код.

## 7. Топ-3 дыры

1. **E1 — формула делегирования при `spawn_subagent`.** agent-tools §2b задает права ребёнка как «владелец × декларация агента», игнорируя родительскую цепочку — узкий субагент, заспавнив оркестратора, легально получает metaTools. Фикс: одна формула («пересечение эффективных прав родителя × декларация ребёнка») + гвард на spawn metaTools-агента. Самый дешёвый фикс с самым дорогим потенциальным уроном.
2. **D1 — неограниченный `spawn_subagent` (форк-бомба сессий).** Нет глубины/ширины/квот: bulkhead и потолок контейнеров защищают инфраструктуру, но не очередь, БД и бюджет токенов. Фикс: два конфиг-лимита + пользовательская квота сессий + честный `TOOL_RESULT ERROR`.
3. **D3 — trigger-URL как фабрика задач.** Ключ идемпотентности лишь «рекомендован», per-trigger потолка и алерта нет; утечка URL = неограниченный расход LLM. Фикс: per-trigger rate-cap + алерт в operations §7 (+ опциональный потолок задач/час у триггера в эволюцию D-26).

### 9.3 Дискуссия: DS E-1 («принципал = автор инструкции») против D-32

**Диагноз DS — agree.** D-32 закрыл путь «агент просит инструмент выше прав владельца» (инструментный `edit_workflow`), но не путь «**не-владелец направляет агента, действующего правами владельца**». В шаренной сессии оркестратора любой PARTICIPATE получает прокси с правами владельца: напрямую он workflow чужой править не может, а через `POST /messages` — может. Это реальный канал эскалации относительно матрицы AccessPolicy, и сейчас он — *тихое следствие* матрицы, нигде не названное. Сильнейшая находка всех трёх отчётов.

**Рецепт DS («эффективные права = пересечение прав инициатора…») — disagree, по существу формула D-32 верна.** Три причины:

1. **Ломает дизайн делегирования.** Принципиальная модель проекта: агент — прокси владельца («агент не превышает полномочия принципала», глоссарий; сценарий «дописать субагенту» предполагает, что участник направляет чужого агента). При «авторе-принципале» PARTICIPATE на сессии оркестратора обесценивается: коллега с меньшими правами не может ничего попросить — но именно для этого его и допускают.
2. **Механически плохо определён.** Раунд Turn'а смешивает события разных источников (USER от A, late `TOOL_RESULT`, SYSTEM вебхука, парковка/продолжение). «Автор инструкции» для промежуточных раундов не определён — придётся тянуть provenance через весь Turn ради граничного случая. Заметное усложнение движка.
3. **Не закрывает суть.** Инъекция (T-2) проходит и «от имени владельца»: владелец просит прочитать отравленный файл и говорит «продолжай» — инструменты выполнятся с правами владельца при честном author-tracking. Выигрыш модели частичный, цена высокая.

**Кто прав по существу: DS — в диагнозе, D-32 — в формуле.** Канал надо признать и оформить, но лечится он без смены принципала:

1. **Док-фикс** (и это же их п.2 — принимаю): «PARTICIPATE на сессии агента с `metaTools = true` = право направлять агента, действующего правами владельца — осознанная делегация; предупреждение при выдаче share на такие сессии» (glossary «Делегирование» + security §2).
2. **`instructionSource`-аудит** (их идея, дешёвая, без enforce): мета-операции пишут автора последней USER-инструкции — расследуемость без ломки движка.
3. **Эволюция**: подтверждение владельцем privileged мета-операций (`edit_workflow` не-своих, `configure_trigger`) — закрывает заодно часть T-2.

Мой E3 из «accepted residual, doc-only» повышается до «accepted + обязательная док-фиксация делегации + instructionSource-аудит».
