# Безопасность spring-harness (MVP)

> Уровень проекта: закрытая внутренняя разработка, один инстанс на VM, без прода, «сломалось — пофиксили — передеплоили». D-41.

## 1. Аутентификация и доступ

| Поверхность | Механизм |
|---|---|
| REST/SSE/WS | `Authorization: Bearer <Keycloak JWT>` (OIDC). Анонимного доступа нет. |
| Вебхуки | capability-токен `HMAC(secret, kind:id)` в пути (D-26) — без JWT. |
| **SSO-гейт** | единственный барьер: JWT должен содержать группу из `harness.security.allowed-groups` (claim `groups`, конфиг). Не прошёл — `401`. |

**Правило доступа одно (D-41)**: аутентифицированный видит всё и пишет куда угодно. Прав, ролей, шарингов, папок, матриц — нет; `permissions_jsonb` агента остаётся allowlist'ом его инструментов (внутренняя дисциплина агентов, не security-граница уровня людей).

## 2. Секреты

| Секрет | Хранение |
|---|---|
| `llm_credentials.api_key` | шифрование на уровне приложения (`api_key_encrypted`, `key_version`); наружу не отдаётся |
| `server_secret` (HMAC вебхуков) | env/конфиг |
| `task.params` | БД; в логах маскируется |

Правило: секреты не логируются (маскирование: api_key, Authorization, capability-токены, `task.params` — `operations.md` §1).

## 3. Технические гварды (дёшево и осталось)

- Workspace-пути: только относительные, canonical-path-резолв внутри корня (symlink-обход — `422`).
- Bash/файлы на хосте — изоляция per-session/task контейнерами (D-30), cpu/mem-лимиты (конфиг).
- `/var/run/docker.sock` ≡ root на VM: выделенная VM без других нагрузок; опционально docker-socket-proxy.
- Спавн: единственный лимит `spawn.maxDepth` (конфиг).

## 4. Осознанно не делаем (D-41)

Матрица прав, делегирование, harness-admin, группы/папки/шары, билеты (до WebUI-фазы), rate-limit, origin-маркировка контента, digest-пин образа, identификация «кто виноват» сверх атрибуции сообщений и истории переходов.
