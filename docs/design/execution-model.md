# Исполнительная модель spring-harness

> Как сессия просыпается, обрабатывается и останавливается. Термины — по `docs/glossary.md`.

## 1. Два контура пробуждения (wake)

**Контур EVENT (быстрый путь).** Источник, добавивший сессии работу, сразу вызывает tryStart:
- клиент прислал сообщение → сохранён `USER` → tryStart;
- вебхук прошёл проверку подписи → `SYSTEM`-событие → tryStart;
- асинхронный инструмент завершился → поздний `TOOL_RESULT` → tryStart;
- подзадача пришла в терминал → переоценка `WAIT_TASKS` у родителей → tryStart (или переход).

**Контур POLL (страховка).** ShedLock-джоба раз в ~5 сек (`lockAtMostFor` ~10 сек, отпускает сама). Сканирует **два уровня**:
- *сессии*: eligible-сессии, пропущенные контуром EVENT (падение инстанса, гонка);
- *задачи* (бессессионные инварианты, дёшево по индексам): (а) задача в AGENT-состоянии **без живой сессии** → bootstrap STATE-сессии (лечит crash между переводом и созданием сессии); (б) задачи в WAIT_TASKS / WAIT_WEBHOOK → переоценка условий (лечит потерянный EVENT-wake терминала подзадачи во время даунтайма).

Отдельной очереди нет — очередь это сама `session_message`; для задач — их собственные поля состояния. Outbox не заводим (D-33): все side-effects выводимы из durable-состояния сканами.

**Одноразовые сканы при старте процесса (scope — только мёртвые по реестру `instance`, чтобы rolling deploy не трогал живые Turn'ы):**
1. локи мёртвых инстансов (heartbeat 10с/порог 30с) — освобождаются с записью LOST; локи живых и TTL-страховка — отдельно;
2. `TOOL_CALL` без парного финального `TOOL_RESULT` **у сессий, чьи локи принадлежали мёртвым инстансам** → синтетический `TOOL_RESULT` «операция потеряна при перезапуске»; незалоченные сессии не трогаем (их поздние результаты ещё прибудут);
3. осиротевшие helper-контейнеры (контейнер без живой сессии) — удаление;
4. **Докатка отмен**: сессии с `cancel_requested` и без живого Turn → каскад отмены вниз по `parent_session_id` (идемпотентно: флаг уже стоит — повтор no-op).

**Поздние результаты async (гварды)**: late-`TOOL_RESULT` принимается только если сессия жива (не архивна) и задача в соответствующем состоянии; **первый финальный результат по call_id выигрывает** (синтетический LOST/CANCELLED — тоже финальный): дубли игнорируются.

**Отказы контейнера в рантайме (D-30):**
- контейнер умер во время async-выполнения → docker-java event/факт смерти при попытке досылки результата → синтетический `TOOL_RESULT` `LOST` «контейнер исполения умер»;
- pull helper-образа: образ обязан присутствовать локально на VM (собирается при деплое); pull из registry — только retry/backoff на случай обновления, недоступность registry не блокирует существующие сессии;
- отказ монтирования workspace-тома при старте контейнера → инструмент отвечает `ERROR` с причиной → задача идёт по ERROR-пути состояния.

**Eligibility:** `last_seq > last_consumed_seq` (денормализации, index-only скан) И сессия не терминальна И не архивна И задача не suspended И лок свободен или стух.

**LLM-семафор и ретраи**: параллельные стримы ограничены bulkhead'ом (конфиг, дефолт 8); 429/5xx → экспоненциальный backoff (3 попытки) → **парковка Turn'а** (событие-повтор через POLL), терминальный FAILED — только после исчерпания.

**Write-ahead раунда**: стрим модели завершился → сначала запись ASSISTANT + TOOL_CALL в сессию → потом исполнение инструментов. Crash между — рестарт-скан честно закроет TOOL_RESULT'ом LOST, повторной генерации и двойного расхода нет.

**Отмена in-flight sync-инструментов**: длительные синхронные операции (bash) прерываются по cancel-флагу (убийство процесса в контейнере); результат — синтетический CANCELLED.

## 2. Turn — жизненный цикл

**Лок и fencing**: TTL лока — **60 сек**; Turn продлевает `locked_at` heartbeat'ом **каждые 30 сек**; перед каждым раундом — проверка `locked_by == мы` (fencing: лок украли по TTL — Turn завершается без side-effects). `lockAtMostFor` ShedLock-джобы (~10 сек) — отдельный лок самой джобы, к сессионным отношения не имеет.

```
tryStart(session):
  CAS-взятие лока: locked_by = инстанс, locked_at = now()
    (успех только если было NULL или locked_at старше TTL)
  не взяли → выходим
  try:
    цикл раундов:
      если locked_by != мы (лок украли) → тихий выход
      если cancel_requested → статус CANCELLED, выход
      если pending_tool_calls == 0 и модель закончила и новых событий нет → выход (готово)
      context = renderVisibleEvents(session)        // §5
      ответ = LlmGateway.stream(agent, context, tools)
      выполнить tool-calls (§4)
      выбрать продолжение (§3)
  finally:
    CAS-освобождение лока (только если владелец — мы)
```

## 3. Условия продолжения/выхода цикла (исчерпывающий список)

Модель «закончила» ⟺ в ответе нет ни одного tool-call (единственный формальный признак).

| № | Ситуация | Действие |
|---|---|---|
| 1 | Модель вызвала синхронные инструменты (или **смесь** sync+async) | sync выполняются немедленно, async-часть уходит в плейсхолдеры `ASYNC_ACCEPTED` → результаты дописаны → новый раунд |
| 2 | Модель вызвала **только** async-инструменты и новых событий нет | парковка: выход, ждём wake от поздних `TOOL_RESULT` |
| 3 | Во время хода пришли новые события (юзер, поздний результат) | новый раунд — модель должна их увидеть |
| 4 | Превышен порог контекста (~80% окна) | страховочная компакция (§5) → новый раунд |
| 5 | `cancel_requested` | статус CANCELLED, выход |
| 6 | Ошибка LLM | ретраи по D-35 (429/5xx → backoff×3 → парковка Turn'а); FAILED — только исчерпание ретраев/не-429 ошибки |

## 4. Выполнение инструментов

- Каждый инструмент декларирует `sync | async`. Async: синхронное окно ~30 сек → плейсхолдер `ASYNC_ACCEPTED(call_id)` → ход возвращается агенту → фон дорабатывает → второй `TOOL_RESULT` с тем же `call_id`, флаг `late=true` → wake (см. `glossary.md`).
- Источники — ровно два: нативные workspace-инструменты через `WorkspaceTools` (биндинг SERVER_DIR/CLIENT_EXEC из декларации состояния) и MCP-клиенты.
- Серверное исполнение — в per-session Docker-контейнере (D-30): helper-образ (минимальная ОС + find/grep/coreutils/git), имя `harness-<sessionId>`, workspace-каталог примонтирован томом, lifecycle контейнера = lifecycle сессии (создание лениво при первом вызове, удаление при архивации/чистке). **Системные состояния без сессии (BASH_SCRIPT) исполняются в task-контейнере `harness-task-<taskId>`** (lifecycle = задача: лениво при первом системном исполнении, удаление на терминале); тот же образ и лимиты. Лимиты по умолчанию: `cpus=2`, `memory=2g`, `pids-limit=512`, дисковая квота workspace — 5 GB (конфиг); **потолок одновременно живых контейнеров** — конфиг (дефолт 50); idle-вытеснение: контейнер неактивен 30 мин → стоп, пересоздание по требованию; reconcile контейнеров — периодически в POLL-джобе (сироты → удаление). Сеть — только состояниям, которым нужен git-клон.
- **spawn_subagent** — синхронный: дочерняя сессия (`parent_session_id`), родительский виртуальный поток ждёт; завершение субагента = «модель закончила ход И pending_tool_calls == 0»; финальный ответ → `TOOL_RESULT` родителя.
- **transition** — инструмент агента в AGENT-состоянии: обязательный аргумент-обоснование; валидация по разрешённым переходам ревизии; запись в `task_transition_history`; перевод задачи; обеспечение сессии следующего состояния; wake.

## 5. Рендеринг контекста и компакции

- Видимые события = поток сессии минус покрытые поздними `COMPACT.covers`. Один проход: лёгкая проекция (без payload) → SET покрытий → полные payload только видимых. Кэш «шапки» рендера + дельта между раундами (стабильный префикс = провайдерский prompt-cache).
- **Страховочная компакция**: порог ~80% окна → система сама (маленький LLM-вызов) сворачивает старые сообщения в `COMPACT`-событие → раунд продолжается.
- **`/compact`** — та же механика по явной команде (свободные сессии).

## 6. Отмена

- `cancel_requested` на сессии; проверка между вызовами инструментов; CancellationToken-дерево в памяти: дочерние Turn'ы в области родителя.
- **`stop(session)` = отмена Turn'а цели + всего поддерева** (спуск по `parent_session_id`).
- Стоп середины дерева: узел + потомки гаснут; родитель жив, получает `TOOL_RESULT` «субагент отменён» и решает дальше.
- Незакрытые async-тулы отменённых — синтетический `TOOL_RESULT` «cancelled».
- Сессии не удаляются — резюмируемы; выжившее после падения поддерево добивается recovery-спуском по БД.

## 7. Вход задачи в состояние (без сокращений)

1. Движок перевёл `task.current_state` на новый code (транзакционно + запись в `task_transition_history` + пересчёт `status_projection`).
2. Если состояние **агентское**: найти/создать сессию пары (задача, code) — **создание атомарно** (в одной транзакции: insert сессии + seed-`SYSTEM`-сообщение + `last_seq`; состояния «сессия есть, seed не записан» не существует); при создании — записать ревизию агента, workspace-резолв, seed-контекст → wake.
3. Если состояние **выполнения скрипта**: выполнить скрипт через `WorkspaceTools` (обычно SERVER_DIR); по коду выхода/таймауту — детерминированный переход (NEXT/ERROR/TIMEOUT); вывод и exit-код — в `reason` записи `task_transition_history`.
4. Если состояние **ожидания вебхука** — задача ждёт; URL определяется stateless-схемой (`workflow-domain.md` §7).
5. Если состояние **ожидания подзадач** — задача ждёт; переоценка по событиям терминалов подзадач.
6. Если состояние **терминальное** — статус задачи финален; события получают родители-подписчики (`WAIT_TASKS`).

## 8. Хостинг исполнения и graceful shutdown

- Один инстанс MVP: все Turn'ы — виртуальные потоки процесса; локи в БД делают безопасным горизонтальный запуск нескольких инстансов (CAS по `locked_by`).
- ShedLock гарантирует единственность poll-джобы; EVENT-путь идемпотентен благодаря CAS-локу.
- **Graceful shutdown (SIGTERM при деплое)**: (1) перестаём принимать новые Turn'ы (tryStart отклоняет); (2) активным Turn'ам выставляем `cancel_requested` после окна дренирования **30 сек** (долгие LLM-стримы рвём отменимым вызовом); (3) не успевшие — паркуются: события останутся непоглощёнными, POLL/следующий старт поднимет их заново; незакрытые async-тулы закроет рестарт-скан синтетическим LOST; spawn-ожидатели отменяются каскадом как дети. Контейнер оркестратора: `stop_grace_period: 45s` — больше окна дренажа (`operations.md` §5).
