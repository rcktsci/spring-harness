# Глоссарий spring-harness

> Единый словарь проекта. Каждое поле, тип и правило зафиксированы здесь. Изменение термина = изменение этого файла.
> Статус: утверждён в брейншторме 2026-09-16. Смежные документы: `docs/design/*`.

## 1. Идентичность и доступ

| Термин | Определение |
|---|---|
| **User** | Человек, аутентифицированный через Keycloak (SSO/OIDC). Локальных паролей нет. Уникальность по `keycloak_subject`. Масштаб: компания 50+ человек. |
| **Group** | Именованная группа пользователей. Субъект шаринга. |
| **GroupMembership** | Связь user ↔ group. |
| **Folder** | Папка для организации сессий. Дерево (`parent_id`). Субъект шаринга. |
| **Share** | Грант доступа: `subject_type` (USER \| GROUP), `resource_type` (SESSION \| FOLDER \| TASK), `resource_id`, `level`. |
| **Уровни доступа** | `VIEW` — видеть и attach-иться на чтение; `PARTICIPATE` — дополнительно писать сообщения в сессию. |
| **AccessPolicy** | Единственный Java-контракт проверки «кому что видно/можно». Все проверки — через него. |
| **harness-admin** | Роль в Keycloak (realm-role, назначается администратором Keycloak). Даёт право создавать новые ревизии любых workflow — на REST-уровне (JWT человека) и **по наследованию в его прямые сессии**: оркестратор в сессии с администратором может звать `edit_workflow` любых workflow. |
| **Делегирование прав в сессиях** | Эффективные права агентской сессии = **пересечение** прав владельца сессии (Keycloak-роли + гранты) и декларации агента (`permissions_jsonb`). Агент никогда не превышает полномочия своего принципала. Вниз по дереву права не расширяются: субагентская сессия наследует не больше прав родительской цепочки. Инструмент без прав → `TOOL_RESULT forbidden`. |
| **Атрибуция** | В шаренных сессиях сообщение пользователя помечается автором (`[username]: …`) — и для людей (чат), и для агента («кто сказал»). Реализовано полем `author_user_id`. |

## 2. LLM-профилирование (три уровня, DRY)

| Термин | Определение |
|---|---|
| **LlmCredentials** | Подключение: `base_url` (OpenAI-совместимый), `api_key` (шифрован). Используется корпоративный LiteLLM-подобный бэкенд. |
| **LlmModel** | `model_id` + `params_jsonb` (например `reasoning_effort`) + ссылка на `LlmCredentials`. |
| **Agent** | Версионированное описание исполнителя: роль (системный промпт), набор инструментов (нативные + MCP), разрешения, навыки, ссылка на `LlmModel`. **Иммутабелен: правка = новая ревизия.** Ссылки на агента хранят конкретную ревизию. |

Из `LlmModel` собирается per-agent `ChatModel` (автоконфигурации Spring AI отключены намеренно).

## 3. Workflow-домен

| Термин | Определение |
|---|---|
| **Workflow** | Именованный шаблон графа (`key`, `name`). Не мутирует — только новые ревизии. |
| **WorkflowRevision** | Иммутабельный граф состояний и переходов (`rev`, `graph_jsonb`, JSON-Schema-контракт). Задача **пинится** к ревизии при создании; правки шаблона не задевают идущие задачи. |
| **State.code** | `varchar`, **уникален в рамках ревизии**. Придумывает оркестратор (примеры: `WRITE_BACKEND_CODE`, `REVIEWER_1`, `REVIEW_JUDGE`). На code ссылаются переходы, выражения, UI, логи. |
| **Типы состояний** | `AGENT` — сессия + агент; `BASH_SCRIPT` — выполнение скрипта; `WAIT_WEBHOOK` — ожидание вебхука; `WAIT_TASKS` — ожидание задач/подзадач; `TERMINAL` — терминал с исходом `SUCCESS` \| `FAILED` \| `CANCELLED`. |
| **Transition** | Направленное ребро `from_state → to_state` с kind: `NEXT` \| `ERROR` \| `TIMEOUT` \| `CANCEL`. **Циклы (возвраты на доработку) легальны и не ограничены движком.** Параллельный fan-out из состояния **запрещён**. |
| **Task** | Инстанс пути по workflow. Поля: title, description, author_user, owner_user, `workflow_revision_id`, `current_state` (code), `status_projection` (RUNNING \| WAITING \| SUCCEEDED \| FAILED \| CANCELLED), `params_jsonb`, `parent_task_id`, `tags` (для `TAGGED`-scope), `suspended`, visibility (PRIVATE \| PUBLIC + share TASK). Шаблон 1 : N задач; отдельной сущности «инстанс workflow» нет — **инстанс и есть задача**. Права: TASK-VIEW / TASK-PARTICIPATE (share или владелец); STATE-сессии наследуют доступ от задачи. |
| **Subtask** | Обычная Task с `parent_task_id`. Создаётся агентом инструментом. |
| **TaskDependency** | Ребро `blocked_by` между любыми двумя задачами (в т.ч. смежными, не только parent-child). Управляется агентами инструментом. |
| **TaskComment** | Комментарии задачи: append-only, иммутабельные. Автор — user или агент. |
| **TaskTransitionHistory** | Журнал каждого хода задачи по графу: `(task, from_state, to_state, kind, reason)`. `reason`: для bash — stdout/stderr + exit-код; для агента — **обязательный аргумент** инструмента `transition`; для вебхука — источник + сводка payload; для WAIT_TASKS — какие задачи закрыли условие. |
| **Scope-выражения WAIT_TASKS** | `ALL_CHILDREN` — все мои подзадачи; `BLOCKED_BY` — разблокировавшие задачи; `TAGGED(x)` — подзадачи с тегом; `EXPLICIT(${task.params.key})` — явный список из параметров задачи. Условие: все в терминале / все успешно; опциональный таймаут. |
| **Orchestrator** | Агент-«CEO»: инструменты создать/отредактировать workflow (→ новая ревизия), создать задачу/подзадачи, проставить зависимости, настроить триггер. Пользователь может начать сессию с ним и «следить вместе с ним». |

### Инварианты workflow-домена

1. Задача находится **ровно в одном состоянии**. Параллелизм — только **между задачами** (подзадачи идут одновременно) и **внутри сессии агента** (субагенты).
2. Состояние = **одна активная сессия** с **одним агентом**. Поле сессий состояния — список, MVP валидирует `length == 1` (дверь для будущего multi-instance).
3. Разделение «шаблон/инстанс»: ID, токены, пути живут **в задаче**; шаблон содержит только scope-выражения и переменные — **канон имён: `${task.id}`, `${task.params.<key>}`, `${session.id}`, env**. Язык выражений минимальен: подстановки, без скриптинга; алиас `${params.*}` не используется.
4. `status_projection` — денормализованная проекция текущего состояния для списков/индексов, обновляется транзакционно вместе с `current_state`.
5. `task.suspended` — аварийный стоп: планировщик и wake пропускают suspended-задачу. Снятие — явная команда. Каскад на подзадачи — явное действие, не наследование.

## 4. Сессии и сообщения

| Термин | Определение |
|---|---|
| **Session** | Диалог. Род `FREE` (свободная, владелец — User) или `STATE` (принадлежит паре «задача × состояние», уникальность пары; **повторный вход в состояние резюмирует ту же сессию**). Поля: `title`, `agent_revision_id`, workspace (FREE — всегда `SERVER_DIR auto` `workspaces/sessions/{sessionId}`; STATE — из декларации состояния), visibility, `folder_id`, `parent_session_id` (для субагентских), `locked_by`/`locked_at` (TTL), `cancel_requested`, `last_turn_outcome`. **Наследование владельца**: созданное агентом (подзадачи, субагентские сессии, триггеры) получает `owner_user_id` породившей сессии — транзитивно до человека. |
| **SessionMessage** | Событие append-only потока. Поля: `id` (короткий ULID — будущие маркеры в контексте), `session_id`, `seq`, `kind`, `author_user_id`, `payload_jsonb`, `tokens`, `created_at`. PK `(session_id, seq)`. **Строки никогда не апдейтятся.** |
| **Виды сообщений** | `USER`, `ASSISTANT`, `SYSTEM`, `TOOL_CALL`, `TOOL_RESULT`, `COMPACT` (зарезервирован и введён). |
| **COMPACT** | Событие компакции. `payload.covers` — список id/диапазонов сжатого + пересказ. **Видимость — производная**: сообщение скрыто ⟺ существует более поздний COMPACT, покрывающий его. Оригиналы целы, читаются инструментом по id из `covers`. Рендеринг = один проход с учётом видимости. |
| **Страховочная компакция** | При рендере порог ~80% окна контекста → система сама сворачивает старые сообщения в SYSTEM-резюме (отдельный маленький LLM-вызов) → ход продолжается. **`/compact`** — та же механика по команде для свободных сессий. |
| **Асинхронный инструмент** | Признак `async` на инструменте. Синхронное окно ожидания ~30 сек → плейсхолдер `ASYNC_ACCEPTED (call_id)` → ход возвращается агенту → завершение фона дописывает **второй** `TOOL_RESULT` с тем же `call_id` (флаг `late=true`) → wake. Не все инструменты асинхронны; `spawn_subagent` — синхронный. |
| **pending_tool_calls** | Число `TOOL_CALL` без парного **финального** `TOOL_RESULT`. Потребители: завершение субагента, рестарт-скан, отмена. |
| **Turn** (бывш. Run) | Одна активация сессии: виртуальный поток взял лок → раунды модель↔инструменты → отпустил лок. Единица отмены и wake-отчётности (`wake_source`: POLL \| EVENT \| API). |
| **Eligibility** | Сессия готова к обработке ⟺ есть события после конца последнего модельного хода И не терминальна И задача не suspended И лок свободен/стух. |
| **Wake** | Пробуждение. Два контура: **EVENT** — источник, добавивший работу, сразу делает tryStart; **POLL** — ShedLock-джоба раз в ~5 сек как страховка (`lockAtMostFor` ~10 сек). Отдельной очереди нет — очередь это сама `session_message`. |
| **Fork** | Копия свободной сессии с момента N: `source_session_id + seq_cutoff`, байты не копируются; вид форка стабилен (видимость считается только по событиям ≤ cutoff). **Только FREE-сессиям.** |
| **Rewind** | Мягкий откат свободной сессии: маркер отсечки, последующее скрыто, ничего не удаляется. **Только FREE. Состоянийным сессиям fork/rewind запрещены** (целостность аудита workflow). Вытащить знание из задачной сессии — export, не fork. |
| **Экспорт** | Выгрузка сессии в Markdown/JSON. |
| **Рестарт-скан** | При старте процесса: `TOOL_CALL` без парного результата → синтетический `TOOL_RESULT` «операция потеряна при перезапуске». Иначе сессия висит вечно. |

## 5. Субагенты и отмена

| Термин | Определение |
|---|---|
| **spawn_subagent** | Синхронный инструмент: создаёт дочернюю сессию (`parent_session_id`), родительский поток ждёт. Завершение субагента = «модель закончила ход **И** pending_tool_calls == 0». Финальный ответ субагента → `TOOL_RESULT` вызова родителя. |
| **Двухуровневая параллельность** | Уровень движка: строгий последовательный граф, одна сессия на состояние. Уровень агента: внутри сессии свободен — субагенты, форки, любые паттерны (модель корпоративного навыка ревью). |
| **Отмена** | `cancel_requested` на сессии; цикл агента проверяет между вызовами инструментов. **`stop(session) = отмена Turn'а цели + всего поддерева вниз`** (по `parent_session_id`). Стоп середины: узел+потомки гаснут, родитель жив и получает `TOOL_RESULT` «субагент отменён», сам решает дальше. Незакрытые async-тулы получают синтетический «cancelled». Сессии не умирают — резюмируемы. |
| **CancellationToken-дерево** | In-memory область отмены: дочерние Turn'ы живут в области родителя; recovery добивает выжившие после падения по `parent_session_id` в БД. |

## 6. Исполнение инструментов

| Термин | Определение |
|---|---|
| **Workspace** | Каталог исполнения по декларации **состояния** workflow. Типы: `SERVER_DIR` (`auto` — движок создаёт папку, напр. `workspaces/sessions/{sessionId}/`, чистится по retention; `explicit` — путь с переменными `${task.id}`, `${session.id}`) и `CLIENT_EXEC` — исполнение на подключённом клиенте. |
| **SERVER_DIR** | Клонирование репозитория — не тип биндинга, а **bash-состояние подготовки** в графе (успех/ошибка/таймаут — обычные переходы). Разделение каталогов между состояниями — конвенцией путей (`workspaces/tasks/${task.id}/…`). |
| **WorkspaceTools** | Java-контракт нативных инструментов рабочего каталога: `read_file, write_file, edit_file, bash, glob, grep`. Реализации-адаптеры: `ContainerWorkspaceTools` (per-session Docker-контейнер из helper-образа, docker-java, D-30), `ClientRelayWorkspaceTools` (роуминг). |
| **Источники инструментов** | Ровно два: (1) нативные из workspace через `WorkspaceTools`; (2) MCP-клиенты (корпоративные серверы за SSO-прокси, токены обновляются автоматически). MCP-сервер наружу в MVP **не делается** (дверь: адаптер над InboundTriggers). |
| **CLIENT_EXEC** | Требует подключённого клиента; если клиента нет — состояние ждёт/ошибка. Сценарий: роуминг дом↔офис, `git pull`, та же сессия. |

## 7. Интеграции и триггеры

| Термин | Определение |
|---|---|
| **Stateless webhook** | Capability-URL: `POST /api/webhooks/tasks/{taskId}/{token}` (задача в WAIT_WEBHOOK) и `POST /api/webhooks/triggers/{triggerId}/{token}` (создание задачи), `token = HMAC(server_secret, kind + ':' + entityId)`. Сервер пассивен, наружу не инициирует; URL (с токеном) выдаётся через API (`webhookUrl`); регистрацию во внешней системе делает агент предыдущего состояния или человек. Проверка — пересчёт HMAC, для задач без БД. Тело запроса → `reason` перехода. История — журнал сессии/переходов. Threat-model: D-26. |
| **Trigger** | Настройка оркестратора: внешний вебхук → создание задачи на указанном workflow (таблица `trigger`, отзыв через revoke). |
| **InboundTriggers** | Единственная дверь внешних событий в систему (вебхуки, будущие адаптеры Jira/Trello/GitLab и пр.). |
| **Триггер создания задачи** | Настраивается оркестратором: внешний вебхук → создание задачи по указанному workflow. |
| **SSO** | Keycloak (OIDC). Пользователи и группы синхронизируются оттуда. |

## 8. Клиенты

| Термин | Определение |
|---|---|
| **Attach-CLI** | Первый клиент (Java, консоль): список сессий, attach с курсора (`since=seq`), стриминг (SSE), отправка сообщений, провал в субагентов (VIEW), дописывание им (PARTICIPATE), stop поддерева. |
| **WebUI** | Второй клиент, позже. Скачивание артефактов из workspace (кнопка «скачать»). |
| **Курсорный attach** | `?since=seq` — клиент получает хвост событий и далее живой поток (SSE). |

## 9. Сводка инвариантов (кратко)

1. `session_message` — append-only, мутаций строк нет; скрытие — производная видимости от `COMPACT.covers`.
2. Задача ровно в одном состоянии; состояние — одна активная сессия; граф с циклами, без fan-out.
3. Шаблон не содержит инстанс-данных; резолв — выражениями из данных задачи.
4. Каждая добавленная сущность обязана иметь сценарий необходимости.
5. Движок жёсток, агент внутри сессии свободен.
6. Fork/rewind — только свободные сессии.
7. Отмена — поддерево; субагент завершён только при `pending_tool_calls == 0`.
