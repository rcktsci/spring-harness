## Context

M3 закрыл MCP-клиент и мета-инструменты оркестратора; `AgentTurnEngine.executeToolCall` уже умеет резолвить инструменты из колбэков (native + metaTools + MCP) и маршрутизировать async-результаты через сессионный канал `message.created`. Workspace-инструменты исполняются в Docker-контейнерах сервера (`harness-<sessionId>`, `harness-task-<taskId>`). WS/SSE-инфраструктура в проекте есть (SSE-потоки сессий и задач), WebSocket-эндпоинта ещё нет. `runtimeStatus` содержит зарезервированное значение `PARKED_CLIENT`. Текущая тройка источников инструментов — native, metaTools, MCP; добавляется четвёртый — клиентский оверлей.

## Goals / Non-Goals

**Goals:**
- WS-релей `/api/v1/relay`: handshake, регистрация исполнителя с декларацией инструментов, двунаправленная маршрутизация tool-фреймов, heartbeat, grace-период переподключения.
- Клиентские инструменты как runtime-оверлей манифеста сессии с валидацией args по JSON Schema.
- Иерархия toolset: root+клиент = CLIENT (включая sub-сессии spawn_subagent), task-сессии = SERVER.
- `GET /sessions/{id}/workspace/files` + canonical-path-гвард.
- `PARKED_CLIENT` — реальное runtimeStatus.
- Приёмка: роуминг-сценарий «одна сессия, два офиса».

**Non-Goals:**
- Web Desktop (Electron + VueJS) — отдельный этап (клиент в M4 только тестовый WS-клиент).
- `auth/ticket` для браузерного WS — Web Desktop-фаза.
- HYBRID-toolset — отказ владельца.
- Persisting клиентских инструментов в БД.
- multi-instance реестра соединений (один инстанс на VM — D-78).

## Decisions

### D-79: Иерархия workspace.toolset — root+клиент = CLIENT / task = SERVER

**Решение**: toolset определяется runtime-контекстом сессии, а не конфигом агента. Root FREE-сессия с зарегистрированным WS-клиентом → CLIENT (оркестратор и его `spawn_subagent`-sub-сессии видят клиентские инструменты). Сессии задач (`create_task` → собственный `session_id`, ролевой агент) → SERVER жёстко, override невозможен. HYBRID нет.

**Альтернативы**: per-agent `permissions_jsonb.workspace.toolset` (первоначальный вариант) — отвергнут владельцем: «по задачам всегда серверные, а чистые внешние с клиентом — всегда клиентские»; per-state в графе — отвергнут как избыточное усложнение графа (CLIENT_EXEC-состояние уже несёт нужный сигнал, а инструментальный манифест собирается по сессии, а не по состоянию).

**Почему**: семантика владельца естественнее — «я подключился к своей сессии с оркестратором, он и его субагенты могут звать мои инструменты; задача пошла по workflow — там свои ролевые агенты на серверных инструментах». Реализуется одной проверкой происхождения сессии (root vs task) при сборке манифеста.

### D-80: Клиентский оверлей — runtime-only, не персистится

**Решение**: клиентские инструменты живут в in-memory оверлее на время активного WS-соединения. `permissions_jsonb`/`tools_jsonb` агента не мутируются.

**Альтернативы**: запись в БД при register (с revisioning) — даёт историю и multi-instance, но это сущность и миграция ради эфемерных данных; владелец не формулировал потребности в истории клиентских инструментов.

**Почему**: декларация может меняться между подключениями (клиент перенастроил свой MCP-стек); персист только породил бы рассинхрон «в БД одно — по факту другое». Рестарт-скан уже умеет закрывать осиротевшие вызовы — sync-точка не нужна.

### D-81: Маршрутизация tool.call по сессии, идемпотентность по callId

**Решение**: `tool.call` маршрутизируется по `(sessionId → активное соединение root-сессии)`. Результаты идемпотентны по `callId` — первый финальный (OK|ERROR|CANCELLED|LOST) выигрывает, дубликаты игнорируются. Та же семантика, что у async/MCP (M3) — единый контракт TOOL_RESULT.

**Альтернативы**: маршрутизация по `(taskId, binding)` напрямую —технически эквивалентно, но инструментальный вызов уже несёт sessionId (контекст Turn'а), а задача → root-сессия → соединение — один лишний хоп без выгоды.

**Почему**: переиспользуем существующий идемпотент-механизм; клиент не обязан знать внутренние id задач для ответа — только `callId`.

### D-82: source — информативное поле, сервер к MCP-серверам клиента не ходит

**Решение**: `source: "client" | "client.mcp:<server>"` — метка для UI/аудита. Сервер не резолвит `client.mcp:jira` никак — весь вызов уходит в WS.

**Альтернативы**: сервер сам подключается к MCP-серверам клиента (как в mcp-client, но к клиентским) — требует сеть от сервера к клиентской машине (анти-паттерн для изоляции, DMZ/VM), плюс дублирование уже решённой в M3 задачи.

**Почему**: владелец явно сказал «клиент приносит любые tools, даже от внешних MCP-серверов» — перенос ответственности за MCP-стек на клиента; сервер — тупой маршрутизатор.

### D-72: Canonical-path-гвард — точечный, в эндпоинте скачивания

**Решение**: realpath-резолв каждого сегмента + резолв symlink'ов; выход за `workspaces/sessions/{sessionId}` → 422. Гвард живёт только в `GET /sessions/{id}/workspace/files`. Safe-лист расширений + max-bytes лимит.

**Альтернативы**: общий path-guard во всём workspace-слое (был удалён коммитом `70e5260`) — владелец отказал: «слои безопасности в глубину не плодить»; naming угрозу и потребителя не признал.

**Почему**: один публичный вход в файлы workspace — достаточно прикрыть его; внутренние инструменты изолированы контейнером (D-30).

### D-77: WS-handshake-аудит — логи, не БД

**Решение**: register/disconnect логируются с MDC (taskId, binding, sessionId, principal); audit-таблицы нет.

**Альтернативы**: таблица `ws_connection_log` — D-41 отказал в audit-таблицах для webhook'ов; тот же принцип.

**Почему**: один инстанс, внутренняя разработка, «сломалось — пофicksили».

### D-78: Реестр соединений — один инстанс, без распределённой блокировки

**Решение**: in-memory `ConcurrentHashMap<(taskId, binding), Connection>`; занятость workspace — CAS на эту карту. multi-instance не предполагается (одна VM).

**Альтернативы**: ShedLock/Redis-реестр — проект одного инстанса, избыточно.

**Почему**: `workspace-occupied` — локальный CAS; при рестарте реестр обнуляется, а незавершённые вызовы закрывает рестарт-скан.

### D-83: Spring MVC WebSocket (не WebFlux)

**Решение**: `@EnableWebSocket` + `WebSocketHandler` на сервлет-стеке (проект — MVC-монолит Boot 4).

**Альтернативы**: WebFlux/Reactive — переписывать существующий стек; STOMP — избыточный pub/sub для прямого фреймового протокола.

**Почему**: минимальные изменения; виртуальные потоки сервлет-стэка покроют hold-соединения.

## Risks / Trade-offs

- **Холдинг потоков на WS-соединениях**: сервлет-стэк с virtual threads (Boot 4) — приёмлемо; мониторим。
- **Гонка register/отключение**: CAS на реестре + идемпотентность по callId закрывают; grace-период — конфиг.
- **Двойная отправка tool.call при reconnect**: LOST уже записан → повторный `tool.result` игнорируется по callId; повторной отправки того же callId не делаем (вызов закрыт).
- **tool-not-available как тупик для агента**: в CLIENT-сессии без клиента модель может зациклиться на вызове отсутствующего инструмента — принимаем (владелец: всегда ERROR), разруливает промпт/ERROR-переход.
- **Safe-лист расширений — 操作上nеудобства**: бинарные артефакты (отчёты, скриншоты) не скачиваются — эволюция (медиа-allow-list).
- **Канонический резолв symlink'ов на Windows dev-машине**: target-рантайм — Linux VM; гвард тестируем через Testcontainers/реальную ФС.
