## Context

M3 закрыл MCP-клиент и мета-инструменты оркестратора; `AgentTurnEngine.executeToolCall` резолвит инструменты из колбэков (native + metaTools + MCP) и маршрутизирует async-результаты через сессионный канал `message.created`. Workspace-инструменты исполняются в Docker-контейнерах сервера. WS/SSE-инфраструктура: SSE-потоки есть, WebSocket-эндпоинта и `spring-boot-starter-websocket` в pom нет. `PARKED_CLIENT` — зарезервированное значение enum. Источники инструментов — native, metaTools, MCP; добавляется четвёртый — клиентский оверлей.

## Goals / Non-Goals

**Goals:**
- WS-релей `/api/v1/relay`: handshake, регистрация на сессию с декларацией инструментов, takeover/идемпотентность, маршрутизация tool-фреймов, heartbeat, безопасный разрыв.
- Клиентские инструменты как runtime-оверлей манифеста сессии; видимость по parent-цепочке; гейт нативных файловых на уровне резолвера.
- `GET /sessions/{id}/workspace/files` + canonical-path-гвард.
- Приёмка: роуминг-сценарий (reconnect и продолжение работы).

**Non-Goals:**
- Web Desktop (Electron + VueJS) — отдельный этап (клиент в M4 — только тестовый WS-клиент).
- `PARKED_CLIENT` — не реализуется (нет авто-парковки; grace-таймеры задач — вне M4).
- `auth/ticket` для браузерного WS — Web Desktop-фаза.
- HYBRID-toolset — отказ владельца.
- Persisting клиентских инструментов в БД; download клиентских локальных файлов.
- multi-instance реестра соединений (один инстанс на VM).

## Decisions

### D-84: Единица маршрутизации — сессия (supersede D-12)

**Решение**: релеи регистрируются на **сессии** (`register { sessionId, ... }`), не на `(taskId, binding)` состояния задачи. Оверлей виден root-сессии и её sub-сессиям через parent-цепочку. `CLIENT_EXEC` как тип workspace состояния задачи (D-11/D-12) больше не используется релеем: задачи исполняются только серверно, их сессии — SERVER автоматически (в parent-цепочке нет соединения).

**Альтернативы**: каноническая per-state модель `register { taskId, binding }` (изначально в api-contracts §5) — противоречит модели владельца («подключаюсь к новой сессии с оркестратором… если он завёл задачу — там только серверные тулы»); per-agent permissions_jsonb — отвергнуто владельцем ранее.

**Почему**: точно выражает семантику владельца без отдельного правила для задач: toolset = «есть ли connection в parent-цепочке». Отключение клиента → connection пропадает → toolset снова SERVER (нативные серверные инструменты доступны; клиентский оверлей пуст). Убирает из проекта всю task-side часть релея (binding, logicalKey, workspaceBindings в TaskDto).

**`CLIENT_EXEC` в graph-валидаторе**: остаётся **зарезервированным** значением (`WORKSPACE_TYPES` не трогается) — не отклоняется валидатором и не исполняется релеем; задача с `workspace:{type:CLIENT_EXEC}` исполняется серверно (BashStateExecutor fallback). Фиксируется в `workflow-domain.md`/`glossary.md` правкой task 6.4.

### D-80: Клиентский оверлей — runtime-only, не персистится

**Решение**: клиентские инструменты живут в in-memory оверлее на время активного WS-соединения. `permissions_jsonb`/`tools_jsonb` агента не мутируются.

**Альтернативы**: запись в БД при register — сущность и миграция ради эфемерных данных; история клиентских инструментов не нужна.

**Почему**: декларация меняется между подключениями (клиент перенастроил MCP-стек); персист породил бы рассинхрон. Рестарт-скан уже закрывает осиротевшие вызовы.

### D-81: Идемпотентность по callId; журнал — только Turn-поток

**Решение**: completion-map на соединение (`callId → CompletableFuture`), tombstone до конца соединения. Адаптер блокирует Turn-поток на future; WS-поток только complete'ит его. Финальную запись в журнал делает Turn-поток под `sess`-локом (как для async/MCP — D-64). Гоняют между собой поздний `tool.result`, синтетический `tool-timeout` и LOST-при-разрыве — побеждает первый финал на future.

**Альтернативы**: запись из WS-потока — потребовала бы `sess`-лок на WS-потоке (Turn держит его); распределённый completion (Redis) — один инстанс, избыточно.

**Почему**: переиспользует M3-механизм; единый инвариант «один финал на callId».

### D-82: source — информативное поле, сервер к MCP-серверам клиента не ходит

**Решение**: `source: "client" | "client.mcp:<server>"` — метка для UI/аудита; вызов целиком уходит в WS.

**Альтернативы**: сервер подключается к клиентским MCP-серверам — сеть от сервера к клиентской машине (анти-паттерн изоляции) + дублирование mcp-client.

**Почему**: владелец: «клиент приносит любые tools, даже от внешних MCP-серверов» — MCP-стек на клиенте; сервер — маршрутизатор.

### D-72: Canonical-path-гвард — точечный, NOFOLLOW, pre-stat

**Решение**: посегментный symlink-чек + canonical-резолв + containment в `workspaces/sessions/{sessionId}` + `LinkOption.NOFOLLOW_LINKS` на финальный компонент. Размер — pre-stat → честный 413 до стрима; отдача — потоковая с `Content-Length`. Только в `GET /sessions/{id}/workspace/files`.

**Альтернативы**: общий path-guard (удалён `70e5260`) — владелец: «слои безопасности в глубину не плодить»; stream-усечение с 413 «в процессе» — невозможно в HTTP после заголовков.

**Почему**: один публичный вход в файлы workspace; внутренние инструменты изолированы контейнером (D-30). Остаточный TOCTOU принят осознанно с обеими сторонами угрозы: **писатель** workspace — агент (arbitrary `bash` в примонтированном каталоге, prompt-injection может растить symlink/менять файлы), **читатель** — аутентифицированный SSO-пользователь; митигация — NOFOLLOW на финальном компоненте и ре-канонизация каждого сегмента.

### D-77: WS-handshake-аудит — логи, не БД

**Решение**: register/disconnect логируются с MDC (sessionId, principal, число инструментов); audit-таблицы нет. Тот же принцип, что для webhook'ов (D-41).

### D-78: Реестр соединений — CAS по identity, takeover

**Решение**: in-memory `ConcurrentHashMap<sessionId, Connection>`; `register` — takeover при том же principal (старое → 4409 `superseded`), отказ при другом (`workspace-occupied`); `unregister` — `remove(key, expectedConnection)`. Один инстанс на VM.

**Альтернативы**: ShedLock/Redis-реестр — избыточно; запрет takeover → half-open реконнект ловил бы 4409 внутри «живого» старого сокета.

**Почему**: владелец переключается между «офисами» — takeover обязан работать; identity-CAS защищает от вытеснения протухшим сокетом.

### D-83: Spring MVC WebSocket + исходящий мьютекс на соединение

**Решение**: `@EnableWebSocket` + `WebSocketHandler` на сервлет-стеке (Boot 4); исходящие кадры сериализуются `ConcurrentWebSocketSessionDecorator` (параллельные отправки из Turn'ов root + sub-сессий + ping). `spring-boot-starter-websocket` добавляется в pom.

**Альтернативы**: WebFlux — переписывать существующий стек; STOMP — избыточный pub/sub для прямого фреймового протокола.

**Почему**: минимальные изменения; виртуальные потоки покроют hold-соединения.

### D-85: Архитектура — relay → execution через SPI

**Решение**: канон направлений — `api → relay`, `relay → execution`; `execution ↛ relay` (обращение только через интерфейс, реализованный в `relay`, связывание — Spring). SPI — интерфейс `ClientToolBridge` в `execution`: `boolean isClientSession(sessionId)` (гейт нативных файловых), `Optional<ToolDescriptor> resolve(sessionId, toolName)` (манифест), `ToolResult invoke(sessionId, callId, toolName, args)` (вызов в релей). `ClientToolAdapter` в `relay` реализует `ToolCallback` и делегирует в `ClientToolBridge`. ArchUnit: `relay` — технический слой; `api` может зависеть от `relay`, но **`execution ↛ relay` строго** (любая форма зависимости): доменные классы `execution` используют только интерфейс `ClientToolBridge` из собственного пакета, реализация — Spring-бин в `relay`.

**Альтернативы**: цикл execution ↔ relay — запрещён `noCyclesBetweenModules`; релей внутри execution — смешение WS-инфраструктуры и домена.

## Risks / Trade-offs

- **Stale-манифест внутри Turn'а**: манифест собирается на Turn; disconnect клиента внутри Turn'а оставляет инструменты в манифесте до конца Turn'а, вызовы → `tool-not-available`. Резолв live, поэтому новые подключения внутри Turn'а подхватываются. Принято.
- **tool-not-available как тупик для агента**: в CLIENT-сессии без клиента модель может зациклиться — владелец принял («всегда ERROR»); разруливается промптом/остановкой.
- **TOCTOU canonical-гварда**: residual risk — писатель workspace — агент, читатель — аутентифицированный SSO-пользователь; митигация NOFOLLOW + ре-канонизация сегментов (D-72).
- **Download для CLIENT-сессий**: серверный workspace может быть пуст — задокументировано; роуминг не зависит от download (клиент хранит файлы сам).
- **Hold потоков на WS-соединениях**: сервлет-стэк + virtual threads (Boot 4); мониторим.
- **Гонка stop-vs-dispatch (W-2)**: `tool.cancel` может опередить `tool.call` (stop между публикацией вызова и отправкой кадра) — клиент игнорирует cancel для неизвестного `callId` (api-contracts §5.3); остаточное окно принято (одиночный инстанс).
- **Нет durable grace**: отключённый клиент не вызывает ERROR-переходов задач — сессия просто получает `tool-not-available`; продолжение — reconnect'ом. Осознанное упрощение по решению владельца.
