# client-tool-bridge Specification

## Purpose

Клиент «приносит» свои инструменты (включая транслированные из внешних MCP-серверов клиента) — сервер регистрирует их как runtime-оверлей манифеста сессии и маршрутизирует вызовы обратно в релей. Иерархия toolset: root-сессия с подключённым клиентом — CLIENT, сессии задач — SERVER.

## ADDED Requirements

### Requirement: Декларация клиентских инструментов

Клиент SHALL декларировать инструменты в фрейме `register`: `tools[]: { name, description, inputSchema, source }`. `name` — уникально в рамках декларации (дубликаты → `error duplicate-tool-name`, close 4409); `inputSchema` — JSON Schema (используется для валидации args на стороне сервера перед отправкой `tool.call` — единый контракт с MCP/native). `source` ∈ {`client`, `client.mcp:<server>`} — информативное поле для UI/аудита, на сервере не интерпретируется (D-82: мы не знаем и не ходим к MCP-серверам клиента). Пустая декларация валидна — клиент исполняет только стандартные имена, если они есть в его toolset.

#### Scenario: декларация с MCP-источником

- **WHEN** клиент декларирует `jira.list_issues` с `source: "client.mcp:jira"`
- **THEN** инструмент появляется в манифесте сессии; вызов маршрутизируется клиенту; сервер к MCP-серверу jira не обращается

#### Scenario: дублирующее имя

- **WHEN** в одной декларации два инструмента с именем `BASH`
- **THEN** регистрация отклоняется, close 4409 `duplicate-tool-name`

### Requirement: Иерархия workspace.toolset

Toolset сессии SHALL определяться runtime-контекстом, а не конфигом агента (D-79, поправка к первоначальной per-agent модели): root FREE-сессия с зарегистрированным WS-клиентом → `CLIENT`; sub-сессии, порождённые `spawn_subagent` от root-сессии оркестратора, наследуют `CLIENT` и видят те же клиентские инструменты; сессии задач (созданные через `create_task`/metaTools, со собственным `session_id` и ролевым агентом) → `SERVER` **жёстко** — клиентский оверлей для них не собирается, override невозможен. HYBRID не существует.

#### Scenario: root-сессия с клиентом

- **WHEN** клиент зарегистрировался на workspace задачи root-сессии оркестратора
- **THEN** манифест root-сессии содержит клиентские инструменты; toolset = CLIENT

#### Scenario: sub-сессия наследует CLIENT

- **WHEN** оркестратор spawn'ит субагента из CLIENT-root-сессии
- **THEN** дочерняя сессия получает toolset CLIENT и видит клиентские инструменты родителя

#### Scenario: task-сессия всегда SERVER

- **WHEN** create_task/metaTools порождает задачу, входящую в CLIENT_EXEC-состояние
- **THEN** task-сессии, порождённые этой задачей на последующих SERVER-состояниях, имеют toolset SERVER; клиентские инструменты в них не видны

### Requirement: Резолв инструментов и отказ tool-not-available

При вызове инструмента SHALL применяться порядок: (1) серверный `ToolCallback` (native + metaTools + MCP — как в M3); (2) client_provided-оверлей активного соединения **этой** сессии; (3) иначе — `TOOL_RESULT ERROR tool-not-available` с именем инструмента. В `CLIENT`-toolset нативные файловые инструменты (bash/read_file/write_file/edit_file/glob/grep) НЕ подгружаются в манифест — клиент либо декларирует их сам, либо их нет. Вызов клиентского инструмента, когда WS-клиент отключился (toolset остаётся CLIENT, оверлей пуст) → `ERROR tool-not-available`, автоматической парковки нет (Q3 owner).

#### Scenario: неизвестный инструмент

- **WHEN** модель вызывает `foo.bar`, которого нет ни в серверных колбэках, ни в клиентской декларации
- **THEN** TOOL_RESULT ERROR tool-not-available

#### Scenario: клиент ушёл, инструмент вызван

- **WHEN** root-сессия CLIENT, клиент отключился, модель вызывает клиентский инструмент
- **THEN** TOOL_RESULT ERROR tool-not-available; сессия не паркуется автоматически

### Requirement: Оверлей — runtime-only, не персистится

Клиентские инструменты SHALL существовать только в in-memory оверлее на время активного WS-соединения (D-80). В БД они не пишутся; `permissions_jsonb`/`tools_jsonb` агента НЕ мутируются клиентской регистрацией. После отключения оверлей этой сессии очищается; повторное подключение восстанавливает его из новой декларации.

#### Scenario: disconnect очищает оверлей

- **WHEN** клиент отключился
- **THEN** клиентские инструменты пропадают из манифестов затронутых сессий (до reconnect); БД неизменна

#### Scenario: reconnect восстанавливает

- **WHEN** клиент переподключается и декларирует инструменты снова
- **THEN** манифесты сессий снова содержат их; состав может отличаться от предыдущего

### Requirement: Валидация args перед маршрутизацией

Перед отправкой `tool.call` клиенту сервер SHALL валидировать `args` против `inputSchema` декларации (JSON Schema валидатор, уже используемый для MCP/native-инструментов). Невалидные args → `TOOL_RESULT ERROR params-schema` (тот же код ошибок, что у графов/ MCP) — клиент не дёргается.

#### Scenario: кривые args

- **WHEN** модель вызывает клиентский инструмент с args, не подходящими под inputSchema
- **THEN** TOOL_RESULT ERROR params-schema; `tool.call` клиенту не отправляется

#### Scenario: валидные args

- **WHEN** args проходят валидацию
- **THEN** клиенту отправляется `tool.call` с этими args
