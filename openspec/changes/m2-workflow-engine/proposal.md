## Why

M2 вводит **домен задач** поверх готового ядра сессий (M1): шаблоны workflow с ревизиями, инстансы задач с историей переходов, системные состояния (BASH/WAIT_WEBHOOK/WAIT_TASKS), резюмируемые сессии для AGENT-состояний, capability-URL вебхуков и триггеры. Без этого оркестратор не может поручить задачу и собрать её результат — базовый сценарий «написал код, прогнал, собрал биллинг» не работает.

## What Changes

- **Новые сущности БД**: `workflow`, `workflow_revision` (иммутабельные), `task`, `task_dependency` (PK пары, циклы запрещены), `task_comment` (append-only), `task_transition_history` (append-only), `trigger`. Все PK — UUID v7; ревизии — `UNIQUE (workflow_id, rev)`; UPDATE запрещён; `task_transition_history` и `session_message` — только INSERT.
- **Миграции**: создание таблиц (`010..016_create_table_*`), частичные индексы `(parent_task_id, status_projection)`, GIN `(tags)`, partial по `current_state_kind = 'WAIT_TASKS'` для POLL-скана (WAIT_WEBHOOK пассивен — его страхует таймаут-скан), partial по `deadline_at IS NOT NULL` для таймаут-скана, partial по `(current_state_kind='AGENT' AND status_projection='RUNNING')` для bootstrap-скана, `INDEX (blocked_task_id)` на `task_dependency` для переоценки WAIT_TASKS; колонки `session.task_id`/`state_code`/`agent_revision_id` и PARTIAL UNIQUE `(task_id, state_code) WHERE kind = 'STATE'` — **уже существуют с M1 (миграция 005), переиспользуются без изменений**.
- **Контракты**: `WorkflowRegistry` (CRUD ревизий + JSON-Schema валидации графа), `TaskRegistry` (создание с пином ревизии, переходы, зависимости, suspend/resume/stop, история, комментарии, дерево, переоценка WAIT_TASKS).
- **Движок**: цикл обработки задач (BASH_SCRIPT → `WorkspaceTools` в `harness-task-<taskId>` с `state_attempt` для идемпотентности; WAIT_WEBHOOK → `POST /api/webhooks/tasks/{id}/{token}`; WAIT_TASKS → переоценка при терминале подзадач/разблокировке); таймаут-скан `deadline_at`; POLL-страховка задачного слоя; AGENT-состояние → bootstrap-создание/возобновление STATE-сессии с привязкой `task_id`+`state_code` и `agent_revision_id`.
- **Мета-инструмент `transition`**: обязательный `reason`, цель = ребро текущего состояния, вид ребра (NEXT/ERROR/TIMEOUT/CANCEL) пишется в `task_transition_history`. Гейт metaTools (D-38; supersession в M2 — D-59): разрешён только при `instructionSource = USER` (для первой версии — `USER`-сообщение прямо в сессию состояния).
- **STATE-сессии**: `kind=STATE`, `task_id`/`state_code`/`agent_revision_id`; повторный вход в то же `(task_id, state_code)` резюмирует ту же сессию (PARTIAL UNIQUE гарантирует это); сессия иммутабельна по `task_id`+`state_code`, нельзя превратить FREE→STATE или наоборот.
- **Suspend + Stop (D-29)**: `POST /tasks/{id}/suspend { cascade }` → 204 (Turn дорабатывает), `resume` для нетерминальной (снимает suspended + публикует `task-wake`); `POST /tasks/{id}/stop` — **всегда каскадный** (без параметра `cascade`): suspend + отмена Turn'ов + запись терминала `'$CANCELLED'` (псевдо-код вне codes ревизии; `task_transition_history` `kind=CANCEL`, `to_state='$CANCELLED'`); resume CANCELLED → 409 `task-already-terminal`.
- **Вебхуки (capability-URL, D-05/D-26)**: `POST /api/webhooks/tasks/{taskId}/{token}` — задача в WAIT_WEBHOOK → переход NEXT (payload+source → `reason`); вне WAIT_WEBHOOK → 409 `task-not-waiting-webhook`; кривой токен → 401 `signature-invalid`. `POST /api/webhooks/triggers/{triggerId}/{token}` → создание задачи по workflow триггера → 202 `{ taskId }`; отозванный → 410 `trigger-revoked`. `token = HMAC(server_secret, kind+':'+entityId)`; проверка чистая (без БД для задач; для триггера — `revoked_at`).
- **Триггеры (D-25)**: `POST /api/v1/triggers` (rev пин, params, tags), `GET` (список), `DELETE` (revoke через `revoked_at`, URL умирает мгновенно). Revoke — `UPDATE … SET revoked_at=now()`.
- **REST+SSE задач**: `POST /api/v1/tasks`, `GET /api/v1/tasks`, `GET /api/v1/tasks/{id}`, `PATCH /api/v1/tasks/{id}` (merge-patch, `params` иммутабельны), `/subtasks`, `/suspend`/`/resume`/`/stop`, `/dependencies` (POST/DELETE, валидация циклов → 422 `dependency-invalid`), `/comments`, `/history` (курсор `(created_at, id)`), `/tree`. `GET /api/v1/tasks/{id}/events` (SSE: `task.transition`, `task.status`, `subtask.terminal`, `task.comment`, снапшот+ping; курсор `since=` — монотонный durable `task_event_seq`, снапшот = последний `task.status`).
- **Сессии M1 → дополнения**: `SessionDto.kind=STATE`, `taskId`, `stateCode`, `runtimeStatus` расширяется до `IDLE|TURN_RUNNING|PARKED_ASYNC|PARKED_CLIENT` (enum с M2; фактическое присвоение: `PARKED_ASYNC` — с M3, async-инструменты; `PARKED_CLIENT` — с M4, релей); `POST /api/v1/sessions` остаётся только FREE; SSE задач — новый поток. `GET /api/v1/sessions/{id}/tree` дополняется `taskId`+`stateCode`.
- **Без идемпотентность-хранилища (D-29/D-41)**: replay-safe POST не требуется; вебхук задачи идемпотентен по построению (`409` вне WAIT_WEBHOOK).
- **SessionDto — аддитивное расширение (без BREAKING)**: `kind`, `taskId?`, `stateCode?` — новые поля; `agent {key, rev}` обязателен уже с M1 (миграции клиентов не требуется). Решение владельца (J-11): **триггеры и вебхук-эндпоинты остаются в M2** (roadmap.md синхронизирован).

## Capabilities

### New Capabilities

- `workflow-engine`: шаблоны и ревизии workflow (`WorkflowRegistry`); JSON-Schema валидация графа (§2 workflow-domain.md); правила §2.1–§2.5 (уникальность codes, отсутствие fan-out — ≤1 ребро каждого kind, ≥1 исходящий, BASH/WAIT обязательные ERROR- и TIMEOUT-рёбра, достижимость TERMINAL). Циклы — разрешены.
- `task-engine`: жизненный цикл задач и системные состояния. `TaskRegistry`: создание с пином ревизии, переходы (атомарный CAS `current_state`, история), подзадачи, зависимости (валидация циклов → 422), suspend/resume/stop, история, комментарии, дерево, переоценка WAIT_TASKS. Системные состояния: `BASH_SCRIPT` (через `WorkspaceTools` с `state_attempt`), `WAIT_WEBHOOK`, `WAIT_TASKS` (scope/condition, см. §3). STATE-сессии (резюм по `task_id`+`state_code`). Мета-инструмент `transition` с обязательным reason. Таймаут-скан по `deadline_at`. POLL-страховка задачного слоя (D-33).
- `inbound-triggers`: вебхуки задач и триггеров (capability-URL). `POST /api/webhooks/tasks/{taskId}/{token}` (WAIT_WEBHOOK→NEXT, иначе 409), `POST /api/webhooks/triggers/{triggerId}/{token}` (создание задачи, revoked→410), CRUD триггеров `POST /api/v1/triggers` / `GET` / `DELETE` (revoke).

### Modified Capabilities

- `session-api`: расширение `SessionDto` (`kind`, `taskId?`, `stateCode?`, `runtimeStatus: IDLE|TURN_RUNNING|PARKED_ASYNC|PARKED_CLIENT`; `agent: { key, rev }` — уже обязателен с M1); `POST /api/v1/sessions` остаётся только FREE; новый SSE-поток `GET /api/v1/tasks/{id}/events` (api-contracts §3.2 — `task.transition`/`task.status`/`subtask.terminal`/`task.comment`, снапшот при коннекте, курсор `task_event_seq`, ping). Каталог ошибок §6 дополняется **единственным новым кодом** `wrong-transition` (409); остальные M2-коды уже в §6: `task-not-found`, `workflow-not-found`, `trigger-not-found`, `task-not-waiting-webhook`, `task-already-terminal`, `dependency-invalid`, `graph-invalid`, `params-schema`, `trigger-revoked`, `signature-invalid`.
- `agent-turn`: добавление мета-инструмента `transition(taskId, toState, kind, reason)` (в контракте реестра `taskId` обязателен; адаптер при вызове из STATE-сессии резолвит его из сессии неявно — J-14) с гейтом metaTools (D-38/D-52/D-59): разрешён только при `instructionSource = USER`; в M2 единственная точка входа — USER-сообщение прямо в сессию состояния (через `POST /api/v1/sessions/{id}/messages` — без нового endpoint). Применение `transition` — транзакционно **в момент исполнения tool-call** (CAS + история атомарны с исполнением инструмента), не на turn-finish. Связь с `TaskRegistry` — через контракт (execution/api знают `task`, сессии и движок не лезут в task.impl).

## Impact

- **Код**: новые пакеты `workflow` (+ `impl/`), `task` (+ `impl/`); расширения `session` (`Session.kind=STATE`, маппинг `task_id`/`state_code`/`agent_revision_id` — колонки с 005), `execution.impl` (`AgentTurnEngine`, `TaskEngine`, `BashStateExecutor`, `StopTaskFacade` — поверх контрактов `WorkspaceTools`/`TaskRegistry`, таймаут-скан, задачный wake), `api/impl` (`WebhookHandlers` — делегация в `task` через `TaskRegistry`; триггер-CRUD); `intelligence` — без изменений; ArchUnit-правила (10.1) расширяются: `execution → {task, session, workflow}` теперь полностью действует (пакеты появляются).
- **API**: ~24 новых операций + новый SSE-поток. OpenAPI: генерация из замороженной спеки (шаг 1 contract-first) → расширение M2-подмножеством api-contracts §4 → полный ревью-цикл → заморозка → шаг 2 (генерация, контроллеры). Ошибки — каталог §6 дополняется единственным новым кодом `wrong-transition` (остальные M2-коды уже в §6).
- **БД**: 7 таблиц (`workflow`, `workflow_revision`, `task`, `task_dependency`, `task_comment`, `task_transition_history`, `trigger`), ~12 индексов, миграции `010..016` (после `001..007` M1).
- **Конфиг**: `harness.task.poll-interval` (~5 с), `harness.task.scheduler.batch-size`, `harness.task.timeout.scan-interval`, `harness.task.transition.max-per-turn` (дефолт 1), `harness.task.transition.metaTool.allowed-instruction-sources=[USER]` (по умолчанию), `harness.task.transition.kind-timeouts.{bash,wait-webhook,wait-tasks,agent}.default` (дефолты таймаутов состояний), `harness.webhook.secret` (HMAC), `harness.webhook.base-url` (capability-URL), `harness.trigger.idempotency-window` = отсутствует (D-41).
- **Зависимости**: без новых; ShedLock-таблица переиспользуется (джоба `task-scheduler` под своим именем).
- **Решения (ADR)**: D-29 (suspend+stop, нет idempotency-хранилища), D-05/D-26 (capability-URL), D-25 (trigger-сущность), **D-59** (metaTools-гейт `instructionSource=USER` — частично supersede D-41 в границах M2). D-47…D-58 фиксируются в `decisions.md` в пачке M (приёмка).
- **Критерий M2 (roadmap.md)**: сценарий «двухфазное ревью с возвратом» на тестовом графе проходит — агент переводит задачу инструментом `transition`, включая таймауты и error-пути bash-состояний. End-to-end-тест с WireMock-LLM и реальным helper-контейнером для BASH.
- **Вне M2**: `@Tool` metaTools-агенты, async-инструменты, MCP, роуминг workspace, fork/rewind, экспорт, архивация, раннеры — отложено в M3+ (см. `roadmap.md`).
