## Context

`handleToolCall` выбирал рабочий каталог из изменяемого поля `this.basePath ?? this.registration?.basePath`, игнорируя `call.sessionId`. Сервер маршрутизирует вызовы строго по сессии (`connections.findForSession(rootSessionId)`), поэтому `tool.call` сессии A может прилететь на соединение в любой момент, когда A зарегистрирована на нём — включая моменты, когда поле `this.basePath` уже перезаписано регистрацией B. Результат живого прогона: исполнение в чужом `~/harness-workspaces/<другой-uuid>`.

Сопутствующие: fetch к token endpoint Keycloak без таймаута (зависший UI без сообщения); регистрация релея: consent-диалог исчезает (~10–16 с), регистрация молча умирает без видимой причины.

## Goals / Non-Goals

**Goals:**
- Каталог вызова — только по `call.sessionId`; незарегистрированная сессия — явный отказ.
- Соответствие `sessionId → basePath` актуально при переключении/разрыве/реконнекте; решение по записям прошлых сессий задокументировано.
- Политика конкурентных регистраций выбрана и обоснована (запрет).
- Таймаут запросов к KC — из конфига; таймаут — временный исход с видимой причиной.
- Consent-ожидание не съедает таймаут регистрации; срыв по таймауту виден пользователю и повторим.

**Non-Goals:** параллельные регистрации; UI-выбор basePath при авто-подключении; транспортная отмена вызовов.

## Decisions

### D-1: Маршрутизация каталога — соответствие `sessionId → basePath`

**Решение**: `sessionBasePaths: Map<sessionId, basePath>`; запись добавляется при успехе регистрации (`registered`), `handleToolCall` читает **только** `sessionBasePaths.get(call.sessionId)`; отсутствие записи → `tool.result` с отказом «no registration for session …» (exitCode -1) и локальный `toolResult`-эмит — как и всякий отказ, он виден в ленте. Поле `this.basePath` сохраняется только для UI (currentStatus) и больше не участвует в выборе каталога. `disconnect()` очищает соответствие; close (разрыв с последующим reconnect+re-register) — **не** чистит: повторная регистрация той же сессии восстанавливает ту же запись, а вызовы, прилетевшие в окно разрыва/пере-регистрации, исполняются в своём каталоге.

**Записи прошлых сессий** (переключились A→B): **оставляются до `disconnect()`**. Обоснование: (1) сервер после отвязки A новые вызовы A не шлёт, но вызов «в полёте» на момент переключения может прилететь — исполнение в каталоге A корректнее отказа; (2) запись используется только для выбора каталога, неверное исполнение она дать не может (каталог A принадлежит A); (3) рост соответствия ограничен числом сессий, реально регистрировавшихся на соединении за его жизнь. Очистка при `disconnect()` — точка, после которой соединение и все его сессии мертвы (reconnect восстанавливает записи повторной регистрацией).

**Альтернативы**: чистить map при каждой регистрации новой сессии — полётный вызов старой сессии получал бы отказ из-за гонки; хранить только одну пару — возвращает баг; ассоциировать basePath с соединением — то же поле в другой обёртке.

### D-2: Конкурентные регистрации — запрет (уже в проде), плюс map

**Решение**: политика не меняется: старт регистрации сессии B, пока A в полёте/ждёт согласование, отклоняется (`register-in-progress`/`consent-pending`); обратный порядок ack'ов структурно недостижим. Per-session map при этом сохраняется: он устраняет сам класс бага (выбор каталога по «текущему полю») и покрывает легальные последовательные переключения A→B (вызовы обеих сессий исполняются в своих каталогах) и смену basePath при повторной регистрации той же сессии.

**Альтернативы**: разрешить параллельные регистрации с корректностью независимо от порядка ack'ов — усложняет consent-политику (два модальных диалога, порядок ответов) без сценария необходимости (UI один, активная сессия одна).

### D-3: Таймаут запросов к Keycloak — из конфига, исход временный

**Решение**: новый параметр `keycloakRequestTimeoutMs` (DEFAULT_CONFIG), применяется к обоим fetch token endpoint (`refreshTokens`, `exchangeCode`) через `AbortSignal.timeout`. Срабатывание таймаута попадает в уже существующую транзиентную ветку (токены сохраняются, вызывающие получают «нет токена»/`exchange-failed`), причина (`TimeoutError`) — в тексте ошибки и логе; формулировки различают зависание (`timed out after <N> ms`) и недоступность endpoint (`unreachable`).

**Альтернативы**: глобальный таймаут на fetch-обёртку — её нет (fetch точечный); бесконечное ожидание — исходный дефект.

### D-4: Consent вне таймаута регистрации; видимый срыв

**Решение**: таймер `sendRegister` стартует в момент отправки register-фрейма — то есть **после** ответа пользователя (подтверждается тестом: произвольное ожидание consent не приводит к таймауту). Срыв по таймауту больше не молчит: эмитится статус `{connected, registered:false, phase:'connected', code:'register-timeout', reason:'registration timeout'}` — строка релея показывает причину; повтор — существующей кнопкой/переоткрытием сессии (dedup снят, consent будет запрошен заново).

**Альтернативы**: пауза/пер-запуск таймера вокруг consent — не нужен при старте после ответа; молчаливый срыв — исходный дефект.

## Риски

- Вызовы, прилетевшие для сессии, которая никогда не регистрировалась на этом клиенте (злоупотребление/баг сервера), получают отказ — это и требование; исполнение вне соответствия исключено.
- Записи прошлых сессий живут до disconnect — ограничено числом переключений за жизнь соединения.
