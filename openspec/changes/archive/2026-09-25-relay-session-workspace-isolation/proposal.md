## Why

Живой прогон на VM: запрос ушёл в сессию `000cb7ed-09b8-…`, а клиент исполнил `bash` в каталоге `~/harness-workspaces/000cb76a-5c12-…` — **другой сессии** (видно в логе `local-tools.ts:102` и в сообщениях сессии в БД). Причина: `handleToolCall` берёт каталог из изменяемого поля `this.basePath ?? this.registration?.basePath` и игнорирует `call.sessionId`, тогда как сервер маршрутизирует вызовы строго по сессии. Поле перезаписывается при каждой регистрации — гонка стартовой авторегистрации сохранённой сессии и регистрации вновь открытой сессии приводит к исполнению команды одной сессии в каталоге другой (нарушение per-session basePath, D-88/D-79; тихое смешивание файлов сессий на машине пользователя).

Сопутствующие:
- **Запросы к token endpoint Keycloak идут без таймаута** (silent refresh и обмен кода): зависание сети до KC подвешивает весь UI с пустыми списками и без сообщения.
- **Таймаут регистрации реле отсчитывается так, что consent-диалог исчезает** (~10–16 с на живом прогоне), регистрация молча умирает; пользователь не видит причину.

## What Changes

- **Per-session workspace routing**: соответствие `sessionId → basePath`; каталог для `tool.call` определяется по `call.sessionId`; вызов для сессии без записи — явный отказ (`no registration for session …`), не исполнение в чужом каталоге. Записи пишутся при успешной регистрации, чистятся при `disconnect()`; записи прошлых сессий переживают переключение сессий в пределах соединения (вызовы «в полёте» исполняются в своём каталоге). Конкурентные регистрации разных сессий запрещены (политика `register-in-progress`, уже в проде) — обратный порядок ack'ов недостижим; per-session map дополнительно гарантирует правильный каталог при любом порядке.
- **Таймаут запросов к Keycloak** — конфиг `keycloakRequestTimeoutMs`; исход таймаута — временный (токены сохраняются, как в `silent-refresh-single-flight`), причина в логе/сообщении.
- **Регистрация vs consent**: ожидание ответа пользователя не consumes таймаут регистрации (таймер старта register-фрейма стартует после ответа — фиксируется тестом); при срыве по таймауту эмитится статус с причиной (`register-timeout`), повтор — кнопкой/переоткрытием без перезапуска приложения.

## Capabilities

### Modified Capabilities

- `desktop-relay-client` — «Локальное исполнение tool.call»: маршрутизация каталога по `call.sessionId`, отказ для незарегистрированных сессий, семантика соответствия при переключении/разрыве; «Регистрация на сессии с декларацией»: consent вне таймаута регистрации, видимый исход таймаута.
- `desktop-shell` — «SSO-логин и хранение токена»: таймаут запросов к token endpoint из конфига; таймаут — временный исход.

### New Capabilities

Нет.

## Impact

- **Код**: `web-desktop/src/main/relay-client.ts` (per-session map, отказ, timeout-статус), `auth.ts` (AbortSignal-таймаут), `shared/ipc-contract.ts` (+`keycloakRequestTimeoutMs`), `tests/e2e/stub-server.ts` (при необходимости — расширение под гонку регистраций).
- **Тесты**: `relay-client.test.ts` (+изоляция каталогов: отказ, последовательные регистрации, реконнект, consent-vs-таймаут), `auth-refresh.test.ts` (+abort hanging fetch).
- **Backend**: без изменений (сервер уже маршрутизирует по сессии).

## Non-goals

- Параллельные регистрации разных сессий (остаются запрещёнными).
- Каталог-выбор UI при авто-подключении (basePath по-прежнему дефолт D-88).
- AbortController для транспортной отмены уже отправленных вызовов.
