# desktop-relay-client Specification

## Purpose

WebSocket-клиент релея в Web Desktop (живёт в **main**-процессе, D-91): подключение к `/api/v1/relay`, регистрация на сессии с декларацией локальных инструментов, локальное исполнение `tool.call`, heartbeat, переподключение и takeover. Контракт — api-contracts §5 (M4).

## MODIFIED Requirements

### Requirement: Локальное исполнение tool.call

Получив `tool.call { callId, sessionId, tool, args }`, клиент SHALL определять рабочий каталог **строго по `call.sessionId`** через соответствие `sessionId → basePath`, поддерживаемое успешными регистрациями; вызов для сессии без записи в соответствии SHALL завершаться явным отказом («no registration for session …») без запуска процесса и без использования каталога другой сессии. Запись добавляется при `registered`; записи сессий, регистрировавшихся ранее на соединении, сохраняются до `disconnect()` (вызов «в полёте» после переключения активной сессии исполняется в своём каталоге); `disconnect()` и терминальные закрытия соединения (4409 `superseded`, 4403 protocol-mismatch) очищают соответствие целиком (reconnect восстанавливает записи повторными регистрациями). Закрытие соединения с последующим реконнектом не SHALL оставлять исполнение в устаревшем каталоге: повторная регистрация восстанавливает соответствие, в том числе при смене basePath. Исполнение — как прежде: `bash` — через `child_process.spawn` в `basePath` (shell ОС, таймаут из args/конфига, stdout+stderr объединены, non-zero exit = OK с exitCode); `read_file`/`write_file`/`edit_file` — через `fs` с лимитами вывода (конфиг); `glob` — поиск в `basePath`; `grep` — поиск по содержимому. Результат SHALL отправляться фреймом `tool.result { callId, output, exitCode }`; длинный вывод — через опциональные `tool.progress { callId, chunk }` (streaming) с финальным `tool.result`. `tool.cancel { callId }` SHALL прерывать исполняемый процесс (SIGTERM → SIGKILL по таймауту) и отменять незавершённый `tool.result`; cancel для неизвестного `callId` — игнорируется клиентом. Конкурентные регистрации разных сессий запрещены (см. «Регистрация на сессии с декларацией»); вызовы последовательно регистрировавшихся сессий исполняются каждая в своём каталоге.

#### Scenario: bash-вызов

- **WHEN** оркестратор вызывает клиентский `bash`
- **THEN** команда исполняется локально в basePath, соответствующем `call.sessionId`; клиент отправляет tool.result с output и exitCode

#### Scenario: вызов для незарегистрированной сессии

- **WHEN** приходит `tool.call` с `sessionId`, отсутствующим в соответствии (никогда не регистрировалась на этом клиенте)
- **THEN** явный отказ «no registration for session …» без запуска процесса; чужой каталог не используется

#### Scenario: последовательные регистрации A→B

- **WHEN** сессия A была зарегистрирована, затем активной стала B ( basePath B отличается)
- **THEN** вызовы B исполняются в каталоге B; вызов A «в полёте» исполняется в каталоге A

#### Scenario: реконнект не меняет каталог

- **WHEN** соединение разорвано и та же сессия перерегистрирована (в том числе с иным basePath)
- **THEN** следующий вызов исполняется в актуальном каталоге этой сессии, а не в каталоге прошлой регистрации

#### Scenario: длинный вывод

- **WHEN** вывод bash превышает лимит
- **THEN** клиент стримит его через tool.progress и завершает tool.result с маркером truncated

#### Scenario: отмена

- **WHEN** приходит `tool.cancel` во время исполнения bash
- **THEN** процесс убивается; `tool.result` для этого `callId` НЕ отправляется (если процесс успел завершиться до cancel — отправляется, сервер игнорирует дубль по идемпотентности callId)

#### Scenario: отмена неизвестного вызова

- **WHEN** приходит `tool.cancel` с `callId`, которого нет в выполняемых вызовах (гонка stop с публикацией вызова)
- **THEN** фрейм игнорируется, ошибка пользователю не показывается

#### Scenario: клиентский таймаут меньше серверного

- **WHEN** локальный bash превышает клиентский таймаут (конфиг; обязан быть < серверного `tool-call-timeout` 5 мин, §5.4)
- **THEN** процесс убивается, шлётся `tool.result` с ошибкой timeout; `tool.progress` потолок НЕ продлевает (известное ограничение контракта)

### Requirement: Регистрация на сессии с декларацией

Клиент SHALL отправлять `register { sessionId, basePath, client: { version, tools[] } }` для активной FREE root-сессии (STATE-сессии не регистрируются). `basePath` — локальный корень (по умолчанию `~/harness-workspaces/{sessionId}` или каталог, выбранный пользователем); main-process SHALL создавать его (`fs.mkdir recursive`) при обработке register, до отправки фрейма. `tools[]` — стандартный файловый набор (см. «Локальные инструменты»). Обработка ответов: `registered` — подтверждение; `error workspace-occupied` — сообщение «сессия занята другим пользователем» (кнопки «забрать» нет — takeover работает только для того же principal); `error superseded` (при reconnect) — прежнее подключение того же principal закрыто; `error session-not-found`/`wrong-session-kind`/`duplicate-tool-name` — соответствующие сообщения пользователю. При старте приложения с сохранённой активной сессией клиент SHALL автоматически connect + register. Renderer SHALL инициировать connect + register автоматически при открытии FREE root-сессии (без ручной кнопки), используя канал регистрации, сохраняющий активную сессию (`relayActiveSessionId`); повторный триггер для той же сессии, пока регистрация в процессе или уже выполнена, SHALL дедуплицироваться (per-session, без блокировки других сессий). Пока регистрация одной сессии не завершена (согласование ожидается или `register` в полёте), регистрация другой сессии SHALL отклоняться с явным кодом (`register-in-progress`) без побочных эффектов для первой; повторный запрос той же сессии, пока ожидается её согласование, отклоняется с кодом `consent-pending`; после отказа согласования клиент SHALL эмитить статус с причиной отказа для показа пользователю. Ожидание ответа пользователя на согласование SHALL НЕ расходовать таймаут регистрации: таймер регистрации стартует с отправкой register-фрейма (после ответа). Срыв регистрации по таймауту SHALL быть виден пользователю (статус с причиной `register-timeout`) и повторяем без перезапуска приложения.

#### Scenario: регистрация на новую сессию

- **WHEN** пользователь открывает FREE root-сессию без активного подключения
- **THEN** клиент автоматически подключается и регистрируется с basePath по умолчанию и стандартным набором инструментов; активная сессия сохраняется для восстановления при старте

#### Scenario: повторное открытие той же сессии

- **WHEN** сессия уже зарегистрирована (или регистрация в процессе) и пользователь снова открывает её
- **THEN** повторный register не отправляется

#### Scenario: параллельная регистрация другой сессии

- **WHEN** согласование или регистрация сессии A ещё не завершены и приходит запрос на сессию B
- **THEN** запрос B отклоняется с кодом `register-in-progress`; согласование и регистрация A продолжаются без изменений

#### Scenario: отказ согласования отражается в статусе

- **WHEN** пользователь отклонил согласование первой регистрации
- **THEN** клиент эмитит статус (registered=false, причина отказа), UI показывает причину, а не «подключён»

#### Scenario: долгое раздумье над согласованием

- **WHEN** пользователь отвечает на согласование позже таймаута регистрации
- **THEN** регистрация продолжается штатно (таймер регистрации стартует с отправкой фрейма, после ответа)

#### Scenario: таймаут регистрации виден и повторим

- **WHEN** сервер не подтвердил регистрацию за таймаут
- **THEN** в строке релея видна причина (`register-timeout`); повторная попытка доступна без перезапуска приложения

#### Scenario: сессия занята другим пользователем

- **WHEN** сервер отвечает `workspace-occupied`
- **THEN** показывается сообщение «сессия занята другим пользователем»; попыток takeover нет

#### Scenario: reconnect того же пользователя

- **WHEN** клиент переподключается после разрыва и шлёт register
- **THEN** сервер сам разруливает (idempotent/takeover/superseded) — клиент не ветвит логику

#### Scenario: STATE-сессия

- **WHEN** пользователь пытается зарегистрироваться на STATE-сессии
- **THEN** регистрация не отправляется; пользователю показывается, что релей доступен только для root-сессий
