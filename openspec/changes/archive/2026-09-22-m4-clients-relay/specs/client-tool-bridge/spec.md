# client-tool-bridge Specification

## Purpose

Клиент «приносит» свои инструменты (включая транслированные из внешних MCP-серверов клиента) — сервер регистрирует их как runtime-оверлей манифеста сессии и маршрутизирует вызовы обратно в релей. Видимость оверлея — по parent-цепочке сессии; гейт нативных файловых инструментов — на уровне резолвера.

## ADDED Requirements

### Requirement: Декларация клиентских инструментов

Клиент SHALL декларировать инструменты в фрейме `register`: `tools[]: { name, description, inputSchema, source }`. `name` — free-form, уникально в рамках декларации (дубликаты → `error duplicate-tool-name`, close 4409); `inputSchema` — JSON Schema (используется для валидации args на стороне сервера перед отправкой `tool.call`); `source` ∈ {`client`, `client.mcp:<server>`} — информативное поле для UI/аудита, на сервере не интерпретируется (D-82: мы не знаем и не ходим к MCP-серверам клиента). Пустая декларация валидна.

#### Scenario: декларация с MCP-источником

- **WHEN** клиент декларирует `jira.list_issues` с `source: "client.mcp:jira"`
- **THEN** инструмент появляется в манифесте сессии; вызов маршрутизируется клиенту; сервер к MCP-серверу jira не обращается

#### Scenario: дублирующее имя

- **WHEN** в одной декларации два инструмента с одним именем
- **THEN** регистрация отклоняется, close 4409 `duplicate-tool-name`

### Requirement: Видимость оверлея по parent-цепочке

Клиентский оверлей SHALL быть виден: root FREE-сессии, на которой зарегистрировано соединение, и её sub-сессиям, порождённым `spawn_subagent` (резолв по parent-цепочке до root). Сессии задач (`create_task` → собственный `session_id` с ролевым агентом) SHALL иметь toolset SERVER: в их parent-цепочке нет зарегистрированного соединения, оверлей не резолвится, нативные серверные инструменты работают как в M1–M3. Override для task-сессий невозможен.

#### Scenario: root-сессия с клиентом

- **WHEN** клиент зарегистрировался на root-сессии оркестратора
- **THEN** манифест root-сессии содержит клиентские инструменты; toolset = CLIENT

#### Scenario: sub-сессия наследует CLIENT

- **WHEN** оркестратор spawn'ит субагента из CLIENT-root-сессии
- **THEN** дочерняя сессия резолвит оверлей родителя и видит клиентские инструменты

#### Scenario: task-сессия всегда SERVER

- **WHEN** create_task/metaTools порождает задачу с ролевым агентом
- **THEN** её сессии имеют toolset SERVER: оверлей не резолвится, нативные серверные инструменты доступны

### Requirement: Гейт нативных файловых на уровне резолвера

В CLIENT-toolset нативные файловые инструменты (`bash`, `read_file`, `write_file`, `edit_file`, `glob`, `grep`) SHALL **не резолвиться** — гейт применяется не только к манифесту, но и к `AgentTurnEngine.executeToolCall`: серверный `NativeAgentTools` для них не вызывается. Порядок резолва: (1) серверные колбэки (metaTools, MCP — доступны всегда; нативные файловые — только в SERVER); (2) клиентский оверлей; (3) отсутствие резолва → `TOOL_RESULT ERROR tool-not-available`. Async-классификация применяется только к серверным колбэкам — клиентский инструмент (включая декларированный `bash`) никогда не уходит в `AsyncToolExecutor`. Манифест инструментов собирается на Turn; резолв оверлея — live на момент вызова.

#### Scenario: галлюцинированный bash в CLIENT-сессии

- **WHEN** модель в CLIENT-сессии вызывает `bash`, не декларированный клиентом
- **THEN** TOOL_RESULT ERROR tool-not-available; серверный контейнер не затрагивается

#### Scenario: клиентский bash исполняется клиентом

- **WHEN** модель в CLIENT-сессии вызывает `bash`, декларированный клиентом
- **THEN** вызов маршрутируется в релей, серверный NativeAgentTools не используется

#### Scenario: неизвестный инструмент

- **WHEN** модель вызывает `foo.bar`, которого нет ни в серверных колбэках, ни в клиентском оверлее
- **THEN** TOOL_RESULT ERROR tool-not-available

### Requirement: Оверлей — runtime-only, не персистится

Клиентские инструменты SHALL существовать только в in-memory оверлее на время активного WS-соединения (D-80). В БД они не пишутся; `permissions_jsonb`/`tools_jsonb` агента НЕ мутируются клиентской регистрацией. После отключения оверлей этой сессии очищается — вызовы клиентских инструментов становятся `tool-not-available` (авто-парковки нет, решение владельца), а нативные серверные инструменты снова доступны (toolset = наличие connection, D-84); повторное подключение восстанавливает оверлей из новой декларации. Очистка действует на следующие собираемые манифесты (Turn'ы) — манифест текущего Turn'а остаётся неизменным до его конца (stale-риск принят).

#### Scenario: disconnect очищает оверлей

- **WHEN** клиент отключился
- **THEN** клиентские инструменты пропадают из следующих манифестов затронутых сессий (до reconnect); БД неизменна

#### Scenario: reconnect восстанавливает

- **WHEN** клиент переподключается и декларирует инструменты снова
- **THEN** манифесты сессий снова содержат их; состав может отличаться от предыдущего

### Requirement: Валидация args перед маршрутизацией

Перед отправкой `tool.call` клиенту сервер SHALL валидировать `args` против `inputSchema` декларации (JSON Schema валидатор, используемый для MCP/native-инструментов). Невалидные args → `TOOL_RESULT ERROR params-schema` — клиент не дёргается.

#### Scenario: кривые args

- **WHEN** модель вызывает клиентский инструмент с args, не подходящими под inputSchema
- **THEN** TOOL_RESULT ERROR params-schema; `tool.call` клиенту не отправляется

#### Scenario: валидные args

- **WHEN** args проходят валидацию
- **THEN** клиенту отправляется `tool.call` с этими args
