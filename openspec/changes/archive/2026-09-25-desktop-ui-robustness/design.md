## Context

Предыдущий change (`relay-connect-consent-confirm`, 9976660) закрыл три дыры tool-цикла, но ревью и живой стенд показали три хвоста: не-терминальная очистка регистрации в `disconnect()`, немое проглатывание ошибки каталога агентов и два задокументированных крайних случая (очистка prompt-состояния до IPC; временные каталоги e2e). Все три — клиентские, backend не затрагивается.

## Goals / Non-Goals

**Goals:**
- `disconnect()` делает регистрацию in-flight терминальной за конечное время; повторная регистрация работает сразу.
- Пользователь отличает «агентов нет» от «каталог не загрузился»; восстановление — через существующую кнопку обновления.
- Ответ диалога не теряет состояние при падении IPC.
- e2e не оставляет мусора в `%TEMP%`.

**Non-Goals:** ретраи-поллинги каталога; новая UI-подача ошибок; чистка чужих старых каталогов.

## Decisions

### D-1 (A): disconnect терминирует регистрацию через abort-хук и исход `disconnected`

**Решение**: `sendRegister` регистрирует `registerAbort`-хук (clearTimer + removeListener + resolve), `disconnect()` вызывает его с `{ok:false, message:'relay disconnected'}`. Consent-резолверы получают тип `(approved: boolean | 'disconnected') => void`; `disconnect()` разрешает все ожидающие согласования исходом `'disconnected'` и очищает `pendingConsent`/`openConsent`; `register()` возвращает `{ok:false, code:'disconnected', ...}` без эмита статуса (статус disconnected уже эмитит сам `disconnect()`).

**Альтернативы**: резолвить consent `false` — врёт («User declined»); оставлять promise висеть до таймаута — исходное поведение, «ничего не происходит»; бросать исключение из disconnect — ломает fire-and-forget вызовы.

**Почему**: единственная точка терминальной очистки; повторный `register` сразу идёт полным путём (дедуп `registering` снят), renderer-`autoInFlight` освобождается `finally`.

### D-2 (B): каталог агентов — отдельная загрузка с явным исходом ошибки

**Решение**: `loadAgents()` в `useSessions`: успех → `agents`+`agentsError=null`; пусто → `agents=[]`, `agentsError=null`; сбой → `agentsError=текст` (список не перезаписывается). Вызывается при монтировании и в `refresh()` (кнопка «↻» уже есть). UI: существующий параграф `.error` в `SessionList` (`data-testid="agents-error"`).

**Альтернативы**: заглушка-кнопка «повторить» внутри ошибки — дублирует «↻»; поллинг — вне задачи; выводить ошибку только в форме создания — пользователь без открытой формы её не увидит.

**Почему**: «пусто» и «не загрузилось» — разные состояния с разными действиями пользователя; восстановление после рестарта бэкенда — существующим контролом, без нового визуального языка.

### D-3 (C1): ответ диалога — сначала IPC, потом очистка; at-most-once без буферизации

**Решение**: `respondConsent`/`respondToolConfirm` захватывают текущий объект, `await` IPC и очищают состояние только при успехе и только если оно не было заменено более новым prompt. Доставка at-most-once: флаги занятости в `useRelay` (повторный вызов во время доставки — no-op) и `disabled`-кнопки в `RelayDialogs` на время доставки. В main ответ при отсутствии открытого запроса — идемпотентный no-op: буфер `pendingConsent` удалён, т.к. отложенный ответ позволял следующей регистрации той же сессии миновать диалог (тихий обход D-93). Окна гонки между показом prompt и постановкой резолвера нет (резолвер ставится синхронно до `emit`), поэтому явное состояние не нужно — единственный «потребитель» буфера был именно обход согласования. При падении invoke исключение уходит в обработчик клика, диалог остаётся — ответ можно повторить.

**Альтернативы**: try/catch с молчаливым проглатыванием — против духа бага B (немые сбои); сохранение буфера «на всякий случай» — критический обход per-session consent.

**Почему**: падение invoke возможно только на разрушенном канале (закрытие приложения); корректность не должна держаться на timing'е microtask-патча Vue, а D-93 не должен обходиться порядком доставки ответов.

### D-4 (C2): e2e убирает за собой

**Решение**: electron-smoke удаляет `--user-data-dir` после `app.close()` и save-target после ассертов; `StubHandle.close()` удаляет workspace-каталог стаба. Удаление — с `maxRetries` (флейк на Windows: занятый файл EBUSY/EPERM после `app.close()`).

**Альтернативы**: общий afterAll-скан `%TEMP%` — хрупко (затронет чужие каталоги); ничего не делать — накопление мусора при каждом прогоне.

**Почему**: точечная чистка известных путей, созданных самим прогоном.

## Фикс-раунд (решение судьи по кросс-чеку ревьюеров, 2026-09-25)

### F1: at-most-once на prompt согласия; main не буферизует ответы без открытого запроса

**Решение**: (1) буфер `pendingConsent` удалён — `resolveRegistrationConsent` без открытого prompt (нет резолвера) — идемпотентный no-op; инвариант: следующая регистрация той же сессии всегда показывает диалог (D-93 не обходится порядком доставки). Окна гонки «prompt показан, резолвер не поставлен» в main нет (резолвер ставится синхронно до emit), поэтому буфер не имел легитимного потребителя. (2) Renderer: флаги занятости в `useRelay.respondConsent/respondToolConfirm` (повторный вызов во время доставки — no-op, «ровно один ответ») + `disabled`-кнопки в `RelayDialogs` на время доставки. Регрессионный тест: два ответа на один prompt → ровно один вызов IPC; ответ без открытого prompt игнорируется; следующая регистрация той же сессии показывает диалог.

### Дополнительно (то же семейство отказов, не блокеры)

- `disconnect()` разрешает `confirmWaiters` отказом («command rejected by user», без запуска процесса) — залипших диалогов подтверждения нет; исход отказа виден renderer'у через `toolResult`; renderer при статусе disconnected/fatal закрывает prompt-диалоги.
- `rmSync` в electron-smoke — с `maxRetries` (флейк EBUSY/EPERM на Windows после `app.close()`).
