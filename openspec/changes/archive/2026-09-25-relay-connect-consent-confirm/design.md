## Context

M5 поставил WS-клиент релея, локальные инструменты и оба гейта D-93 в main-процессе, но UI-потребители гейтов не были смонтированы, а подключение к релею оставалось ручным. Итог на живом стенде: релей не подключается (ноль relay-событий в main.log), tool-call не может завершиться. Диагноз по трём точкам: (1) `useRelay.connect/register` вызывается только кнопкой; (2) `consent`/`toolConfirm` из `useRelay` не рендерятся и их `respond*` не вызываются; (3) событие `registrationConsent`, отправленное main до монтирования renderer (стартовая авторегистрация `relayActiveSessionId`), теряется безвозвратно.

Дополнительная находка: e2e `electron-smoke.spec.ts` зелёный, но пустой — селекторы не из реального DOM, stub-сервер не отправляет WS `tool.call` (tool-цикл не идёт), «save-as» не пишет файл, а ассерт проверяет файл, созданный самим stub'ом при старте.

## Goals / Non-Goals

**Goals:**
- Открытие FREE root-сессии в UI → автоматические connect + register с дефолтным `basePath` (D-88); активная сессия сохраняется и восстанавливается при старте.
- Consent первой регистрации и подтверждение команды (D-93) показываются пользователю поверх любого view; без ответа регистрация/исполнение не продолжаются.
- Запрос consent, отправленный до монтирования renderer, не теряется (pending re-fetch).
- e2e-спека становится реальным стражем: реальный DOM, полный tool-цикл через WS, оба диалога, настоящий save-as.

**Non-Goals:**
- Серверные изменения; выбор basePath пользователем; локализация сообщений; новые числовые параметры (все таймауты уже в конфиге).

## Decisions

### D-1: Состояние релея в renderer — module-синглтон

**Решение**: `useRelay()` переводится на module-scoped refs с однократной подпиской на `window.harness` события (guard-флаг). `RelayDialogs.vue` (глобальный) и `ChatView` видят одно состояние.

**Альтернативы**: оставить per-instance состояние — диалоги в App.vue и ChatView получили бы разные копии `consent`/`toolConfirm`; ответ из одной копии не очищал бы другую. Pinia-store — тяжелее, чем нужно для одного источника событий main.

**Почему**: события идут из одного main-процесса, состояние глобально по определению; подписка живёт весь срок жизни приложения, teardown per-component не нужен и был источником потери событий.

### D-2: Диалоги — глобальный оверлей в App.vue, не в ChatView

**Решение**: `RelayDialogs.vue` монтируется в `App.vue`; показывает consent и tool-confirm поверх любого view.

**Альтернативы**: диалоги внутри ChatView — consent при стартовой авторегистрации приходит, пока пользователь может находиться не в чате; tool-confirm может прийти при переключении view. Локальные диалоги в этих случаях терялись бы визуально.

**Почему**: оба гейта блокируют продвижение серверной стороны (register-обещание / исполнение вызова), поэтому должны быть видны всегда; маршрут ответа уже сводится в main через IPC (`RELAY_CONFIRM_REGISTRATION`, `TOOL_RESPOND_CONFIRM`).

### D-3: Pending-consent re-fetch (новый IPC `relay:pending-consent`)

**Решение**: `RelayClient` хранит текущий незакрытый consent-запрос (`getPendingConsent()`), очищает его при ответе; renderer при монтировании диалогов запрашивает его по IPC и показывает. Новая команда `RelayClient.getPendingConsent()` + IPC-канал `RELAY_PENDING_CONSENT` + preload-метод `relay.pendingConsent()`.

**Альтернативы**: повторная отправка события из main по готовности окна (нужен новый lifecycle-сигнал renderer→main — больше движущихся частей); буферизация событий в preload — скрывает семантику «один активный запрос».

**Почему**: гонка «стартовая авторегистрация vs монтирование Vue» реальна (loadURL резолвится до mount); без re-fetch register-обещание в main висит вечно — это второй механизм зависания из найденных на стенде.

### D-4: Авто-подключение из ChatView c дедупликацией

**Решение**: `watch(activeSession)` в ChatView → `relay.ensureConnected(sessionId, kind)`: пропускает STATE-сессии, уже зарегистрированную ту же сессию и повторный вызов для той же сессии, пока предыдущий не завершился; дальше `connect()` + `register()` (канал `RELAY_REGISTER` — он сохраняет `relayActiveSessionId` в конфиге; канал `RELAY_SET_SESSION` не сохраняет и потому не используется). Ошибки не пробрасываются — статус виден в статус-баре.

**Альтернативы**: триггер из useChat.openSession — примешивает релей к чату; main-side авто-connect на REST-запросах — скрытая магия вне UI-слоя.

**Почему**: спека desktop-relay-client прямо описывает сценарий «WHEN пользователь открывает FREE root-сессию»; сохранение активной сессии и рестарт-восстановление уже реализованы в main — достаточно вызвать правильный канал.

### D-5: e2e — stub дорабатывается до WS `tool.call`, спека — под реальный DOM

**Решение**: stub-сервер после `register` хранит соединение по sessionId и отправляет `{type:'tool.call'...}` (ретраи до регистрации), `toolCount` считает из `client.tools[]`; сценарная bash-команда меняется на кроссплатформенную (`node -e`). Спека: селекторы `li.session-item` / `data-testid` / `data-kind`, два сценария (confirmCommands=never — полный цикл с consent; confirmCommands=always — отклонение и разрешение команды), save-as — через подмену `dialog.showSaveDialog` в main (`app.evaluate`) с ассертом файла на диске.

**Альтернативы**: держать «auto-confirm» и не покрывать диалоги — оставляет дыру D-93 без e2e; ассертить файл stub'а — прежний ложный позитив.

**Почему**: задача спеки — ловить регрессии клиентского tool-цикла, включая оба UI-гейта и реальную запись артефакта.

## Ревью-фиксы (консенсус ревьюеров, 2026-09-24)

### F1: отказ согласования — статус с причиной, «подключён» только для registered

**Решение**: `relay-client.register()` при `!allowed` эмитит `{connected:true, registered:false, phase:'connected', code:'consent-declined', reason:'User declined local execution.'}`. Логика подписи статуса вынесена в чистую функцию `lib/relay-label.ts`: ветка `if (s.connected) return 'подключён'` удалена — «подключён» показывается только при `registered`; незарегистрированный релей показывает `reason`, фазу («релей: ожидание регистрации…») или «не подключён». Guard-тесты: unit `relay-label` (формулировки, включая decline-статус), unit `relay-client` (факт эмита статуса при decline), e2e-шаг «Отклонить → в строке релея причина, кнопка Подключить».

**Альтернативы**: показывать decline только в диалоге/уведомлении — противоречит строке-спеке «в строке релея видна причина»; toast — временный, теряется.

**Почему**: delta-сценарий desktop-chat «отказ в согласовании виден» и desktop-relay-client «причина видна в UI» требуют именно строку статуса; прежний UI был противоречив («подключён» + кнопка «Подключить»).

### F2: STATE-сессия — явный индикатор

**Решение**: `relayLabel(status, sessionKind)` — для `kind==='STATE'` возвращает «релей доступен только для root-сессий» независимо от статуса релея (перекрывает и статус предыдущей FREE-сессии). Кнопка релея для STATE по-прежнему disabled.

**Альтернативы**: сбрасывать статус релея при открытии STATE-сессии — дороже (событие main-стороны) и не нужно: индикатор определяется активной сессией.

**Почему**: требование базовой спеки desktop-relay-client (сценарий «STATE-сессия») не имело UI-выражения; строка статуса от чужой FREE-сессии вводила в заблуждение.

### F3: параллельные регистрации — явная политика

**Решение**: в `relay-client.register()` до любых побочных эффектов (mkdir/connect/consent): запрос на другую сессию, пока та регистрируется или ждёт согласования, отклоняется `{ok:false, code:'register-in-progress'}`; повторный запрос той же сессии при ожидании её согласования — `{ok:false, code:'consent-pending'}` (без перезаписи резолвера); `sendRegister` привязан к сессии (`registeringSession`), дедуп валиден только для той же сессии. Renderer: дедуп `ensureConnected` — per-session `Set` вместо одиночного флага.

**Альтернативы**: очередь регистраций — скрытая очередь диалогов согласования плоха для UX; «последний выигрывает» с молчаливой отменой первой — теряет осиротевший promise.

**Почему**: прежнее поведение возвращало чужой promise/перезаписывало резолверы — неявно и с зависанием; модальный оверлей смягчал, но не устранял.
