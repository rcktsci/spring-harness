## Context

`refreshIfNeeded` при истёкшем access-токене выполняет сетевой refresh немедленно и без координации: на старте приложения пять+ потребителей (список сессий, каталог агентов, SSE-подписка, relay auto-register, артефакты) проходят через него параллельно. Keycloak по умолчанию отзывает refresh-токен при использовании (ротация), поэтому второй параллельный вызов с тем же токеном получает `invalid_grant` (400). Плюс любой сбой обновления (включая сеть и 5xx) трактуется как «сессия мертва» → `clearTokens()` → пользователь на `/login`.

## Goals / Non-Goals

**Goals:**
- Один сетевой refresh на пачку параллельных запросов; одинаковый результат для всех ожидающих; очистка токенов — не более одного раза на пачку.
- Терминальный исход только при отказе гранта от Keycloak (4xx token endpoint, кроме retry-later кодов 408/429 — они временные); сеть/5xx — токены сохраняются, повтор на следующем запросе.
- Причина отказа от Keycloak (тело ответа) в логах — санитизированно: секретные поля маскируются, длина тела ограничена.
- Результат refresh, завершившийся после явной смены сессии (logout, смена issuer), отбрасывается — сессия не «воскрешается».

**Non-Goals:** proactive refresh, retry с backoff, изменение конфигурации Keycloak.

## Decisions

### D-1: Single-flight через модульное in-flight обещание

**Решение**: `refreshIfNeeded` проверяет свежесть токена; при необходимости обновления — если `refreshInFlight` (переменная уровня модуля `auth.ts`) не создана, создаёт `doRefresh(cfg, refreshToken)` и сохраняет обещание; все параллельные вызовы ожидают одно и то же обещание. `finally` сбрасывает `refreshInFlight = null` — следующая пачка снова может обновиться (в том числе после ошибки).

**Альтернативы**: мьютекс/очередь вызовов — избыточно: вызывающим нужен только результат; кэш результата с TTL — усложнение и отдельный источник гонок; координация на уровне rest-client — расползание ответственности (refresh живёт в auth, D-91).

**Почему**: минимальная координация в единственной точке владения токенами; семантика для вызывающих не меняется (`string | null`), ошибка как результат «нет токена» доходит до всех одинаково.

### D-2: Исходы refresh — терминальный только при отказе гранта

**Решение**: сетевой вызов инкапсулируется так, что ошибки делятся на два класса: (1) `RefreshGrantError` — HTTP-ответ token endpoint со статусом 4xx, **кроме retry-later кодов 408/429** (грант недействителен/отозван/истёк) → `clearTokens()` один раз на пачку, лог с телом ответа Keycloak; (2) всё остальное — сетевые исключения, 5xx, **408/429**, аномальный 2xx без `access_token` → токены сохраняются, вызов возвращает `null`, следующий запрос инициирует новый refresh (in-flight уже сброшен). `SafeStorageUnavailableError` при чтении хранилища сохраняет прежнее поведение (null без очистки); ошибки чтения/парсинга хранилища — как раньше, вне refresh-семантики.

**Альтернативы**: считать терминальным только `invalid_grant` по телу — парсинг формата ошибок Keycloak делает клиент хрупким; 4xx-класс достаточен и стабилен (400/401 на grant endpoint = грант не принят). 408/429 — это «повторите позже» (перегрузка/таймаут шлюза), а не отказ гранта: логинить пользователя заново по ним нельзя.

**Почему**: сетевой сбой и недоступность бэкенда не должны логинить пользователя заново; реальный отзыв гранта обязан завершать сессию — гейт `isSessionUsable` при сохранённых токенах работает как раньше.

### D-3: Диагностика — тело ответа в ошибке, санитизированно

**Решение**: при `!res.ok` текст исключения включает статус **и тело ответа** (`refresh endpoint 400: {"error":"invalid_grant",...}`); тело читается одним `text()`. Аномальный 2xx (не-JSON или JSON без `access_token`) тоже несёт тело в тексте ошибки. Тело перед попаданием в текст/лог санитизируется (`sanitizeBody`): под ключом, чьё имя содержит `token`/`secret`/`password`/`credential` (без учета регистра), маскируется **значение целиком на любой глубине и любого типа** (объект/массив под секретным ключом-контейнером скрывается весь, `[masked]`) — имена полей сохраняются для диагностики; JWT-подобные подстроки в не-JSON телах заменяются на `[jwt-like]` (три base64url-сегмента по 8+ символов через точки); итоговая строка ограничена лимитом (`BODY_LOG_LIMIT_CHARS`). Та же санитизация применяется к телу ошибки обмена кода (`exchangeCode`, ветка `!res.ok`) — сырое тело token endpoint не логируется нигде. Лог терминального исхода — `log.error` с ошибкой, временного — `log.warn`; оба содержат причину без секретов.

**Альтернативы**: парсить JSON и вытаскивать `error_description` — красиво, но хрупко к не-JSON телам; не логировать не-JSON тело целиком — слепит диагностику (маскирование JWT-подобных подстрок сохраняет форму ответа); сырого тела достаточно для диагностики, но оно может содержать секреты (проект запрещает логировать секреты).

**Почему**: инцидент 2026-09-25 диагностировался по косвенным признакам — причина от Keycloak должна быть в main.log сразу; при этом аномальный ответ token endpoint теоретически может содержать токены, и попадание их в лог недопустимо.

## Фикс-раунд (решение судьи, 2026-09-25)

### F1 (major): logout/смена конфигурации во время in-flight refresh «воскрешал» сессию

**Решение**: эпоха сессии — модульный счётчик в `auth.ts`. `invalidateSession()` (экспорт) инкрементит её; вызывается из `logout()` и из `index.ts` при смене issuer (вместе с `clearTokens`). Внутренние терминальные очистки (`terminateSession`: нет refresh-токена, отказ гранта, нечитаемое хранилище) тоже инкрементят. `doRefresh` захватывает эпоху до сетевого вызова; при settle с изменившейся эпохой — результат отбрасывается: токены не сохраняются, ожидающие получают «нет токена» (reject в `requireAccessToken`), сессия остаётся завершённой. В catch-ветке при смене эпохи — тоже выход без побочных эффектов (no повторный clear поверх logout).

**Альтернативы**: AbortController для отмены сетевого вызова — не отменяет уже отправленный POST и усложняет refreshTokens; проверка «токены ещё на месте» через повторный loadTokens — гонка с новым логином.

**Почему**: явный Sign out должен работать детерминированно: результат refresh, начатый в предыдущей сессии, не имеет права её «воскрешать».

### F2 (minor): 408/429 — временные ошибки

**Решение**: грант-отказ — 4xx **кроме** 408/429; оба кода отнесены к транзиентным (токены сохраняются). Формулировки delta-спеки и D-2 синхронизированы с фактическим поведением. Тест: `it.each([408, 429])` → clear не вызывается.

### F3 (minor): тело ответа в ошибке аномального 2xx

**Решение**: `parseTokenResponse`-отказ в `refreshTokens` оборачивается в `RefreshTransientError` с сообщением парсинга и телом ответа. Тест: 2xx `{"foo":"bar"}` → null, без очистки, warn-лог содержит тело.

### F4 (minor): детерминированность тестов

**Решение**: `afterEach(() => { vi.unstubAllGlobals(); })` в `auth-refresh.test.ts`.
