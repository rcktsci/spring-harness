## Context

`silent-refresh-single-flight` разделил исходы refresh и в терминальном случае чистит токены в main (`terminateSession`). Но renderer узнаёт о состоянии только через явные вызовы (`loginState`) — при непроизвольной потере сессии никто не дёргает стор: `loggedIn` остаётся `true`, гвард пускает, каждый запрос падает «Not signed in. Open Settings → Sign in and retry». Восстановление — перезапуск.

## Goals / Non-Goals

**Goals:** main сообщает renderer о терминальной потере сессии по типизированному мосту; guard приводит UI к `/login` из любого view; одна потеря — один переход; транзиентные исходы не уведомляют; интерактивный Sign out не дублируется.

**Non-Goals:** вотчер состояния; ретраи/автологин; события в relay/SSE-подсистемах.

## Decisions

### D-1: Событие из main, а не опрос состояния

**Решение**: `terminateSession()` — единственная точка терминальной потери (грант-отказ, нет refresh-токена, нечитаемое хранилище) — дополнительно broadcast'ит `auth:session-lost` через `broadcastToRenderer` (новая функция `renderer-bridge`: отправка всем живым окнам, единая точка main→renderer push'ей). Renderer: `installAuthGuard` подписывается (`auth.onSessionLost`) → `auth.refresh()` (стор становится `loggedIn:false`, если токены действительно удалены) → если сессия не восстановилась и текущий маршрут не `/login`, — `router.push('/login')`.

**Альтернативы**: (1) опрос `loginState` по таймеру/на каждую навигацию — латентность и лишние IPC; после этого инцидента «навигация есть, состояния нет» всё равно ловится только в момент навигации; (2) дергать стор из main — main не знает renderer-состояние, только факт потери; (3) обрабатывать в каждом view — рассинхронизация (дефект возник из-за одного пропущенного места). Broadcast по факту — мгновенно и из единственного источника истины.

**Почему**: у main монополия на момент потери (он же чистит токены); IPC-мост для main→renderer push'ей уже существует (relay:status, sse:event) — это тот же паттерн.

### D-2: Одна потеря — один переход

**Решение**: переход выполняется только при `router.currentRoute.value.path !== '/login'`; повторные события при уже открытой `/login` ограничиваются `refresh()` стора (без push) — vue-router дубликат-навигацию не создаёт. Лавина параллельных 401 ограничена на стороне main: single-flight refresh вызывает `terminateSession` один раз на пачку; плюс дедуп по текущему маршруту на стороне renderer.

**Альтернативы**: флаг «уже обработали» с ручным сбросом — лишнее состояние; debounce по времени — зашитый интервал.

**Почему**: идемпотентность через проверку фактического маршрута — без нового состояния и без таймеров.

**D-3: Интерактивный Sign out не уведомляет**

**Решение**: `logout()` шлёт только `clearTokens()` (без broadcast) — у него есть собственный UI-переход (`SettingsView` → `/login`, change `login-navigation-after-auth`). Broadcast только на непроизвольную потерю.

**Альтернативы**: уведомлять и на logout, убрать push из SettingsView — размывает ответственность и меняет уже работающий протестированный путь.

**Почему**: различие семантик: интерактивный выход — пользователю известно; потеря — неожиданна и требует приведения UI в согласованное состояние.

**Почему**: смена issuer/client id делает сохранённую сессию невалидной — это терминальная потеря по инициативе main; обработчик события идемпотентен по маршруту, «интерактивность» сценария на результат не влияет. Чистый классификатор даёт прямое unit-покрытие матрицей (issuer/clientId → true; theme/limits/window → false), что исключает и константу `true`, и константу `false`.

### D-4: Смена Keycloak-параметров — та же доставка события (результат идентичен потере)

**Решение**: классификатор `sessionInvalidatingChange(prev, next)` (чистая функция в `shared/config-invalidation.ts`) определяет, инвалидирует ли смена настроек сохранённую сессию: `true` для `keycloakIssuer`/`keycloakClientId`, `false` для всего остального. `onServerConfigChanged` вызывает его и при `true` чистит токены, инкрементит эпоху и рассылает `auth:session-lost` — тот же канал и тот же идемпотентный renderer-обработчик. Renderer-мок `config.set` в тестах использует ту же функцию, поэтому покрытие привязано к реальному правилу.

**Альтернативы**: считать смену issuer «интерактивной» потерей без события, а переход делать в SettingsView — размножает знание «какие параметры ключевые» в renderer; новый отдельный канал — дублирует семантику (результат для пользователя одинаков: экран логина); условие инлайн в `onServerConfigChanged` — нетестируемо (главная претензия ревью: регресс «main не шлёт событие» не ловился).

**Почему**: смена issuer/client id делает сохранённую сессию невалидной — это терминальная потеря по инициативе main; обработчик события идемпотентен по маршруту, «интерактивность» сценария на результат не влияет. Чистый классификатор даёт прямое unit-покрытие матрицей (issuer/clientId → true; theme/limits/window → false), что исключает и константу `true`, и константу `false`.

### D-5: Побочные эффекты смены конфигурации — декларативный план

**Решение**: `planEndpointChange(prev, next)` (`shared/config-invalidation.ts`) возвращает декларативный план: `invalidateSession` (issuer/clientId), `sseResubscribe` (baseUrl || sessionInvalidated — отписка SSE/релей для чистой переподписки), `clientsRebuild` (только baseUrl — клиенты захватывают cfg в конструкторе), `notifyConfigChanged` (baseUrl || sessionInvalidated). `onServerConfigChanged` исполняет план; отписка SSE и рассылка `config:changed` возвращены под гарнд смены endpoint — неключевые настройки (тема/лимиты/`confirmCommands`/`showTray`) план со всеми `false` и не дёргают ни подписки, ни уведомления.

**Альтернативы**: инлайн-условия в `onServerConfigChanged` — нетестируемы (ревью-находка: перенесённый блок потерял гард, а регресс «условие убрали» не ловился); три отдельных булевых функции — избыточно.

**Почему**: план — чистая функция с матричным unit-покрытием (baseUrl → rebuild+resubscribe+notify; issuer/clientId → invalidate+resubscribe+notify; showTray/theme → всё false), а `index.ts` исполняет готовое решение. Ревью-замечание: SSE-отписка и `config:changed` относятся к смене endpoint'а, но не к теме/лимитам; `clientId` включён в смена-эндпоинт как смена «бэкенда авторизации».
