# desktop-relay-client Specification

## Purpose
WebSocket-клиент релея в Web Desktop (живёт в **main**-процессе, D-91): подключение к `/api/v1/relay`, регистрация на сессии с декларацией локальных инструментов, локальное исполнение `tool.call`, heartbeat, переподключение и takeover. Контракт — api-contracts §5 (M4).

## Requirements

### Requirement: Подключение и handshake

Клиент SHALL подключаться к `{baseUrl}/api/v1/relay` с Bearer-JWT из safeStorage; при 4401 — триггер silent-refresh/relogin. После соединения SHALL отправлять `hello { protocol: 1 }` и ждать `welcome`; таймаут handshake — конфиг (дефолт 10 с), при превышении — reconnect с backoff. Close 4403 (protocol-mismatch / фрейм до hello) — фатальный: клиент показывает сообщение «несовместимая версия протокола/ошибка handshake» и НЕ реконнектится.

#### Scenario: штатное подключение

- **WHEN** пользователь открывает сессию (или приложение стартует с активной сессией)
- **THEN** клиент подключается, отправляет hello, получает welcome

#### Scenario: истёк токен

- **WHEN** сервер закрывает соединение с 4401
- **THEN** клиент делает silent refresh и переподключается

### Requirement: Регистрация на сессии с декларацией

Клиент SHALL отправлять `register { sessionId, basePath, client: { version, tools[] } }` для активной FREE root-сессии (STATE-сессии не регистрируются). `basePath` — локальный корень (по умолчанию `~/harness-workspaces/{sessionId}` или каталог, выбранный пользователем); main-process SHALL создавать его (`fs.mkdir recursive`) при обработке register, до отправки фрейма. `tools[]` — стандартный файловый набор (см. «Локальные инструменты»). Обработка ответов: `registered` — подтверждение; `error workspace-occupied` — сообщение «сессия занята другим пользователем» (кнопки «забрать» нет — takeover работает только для того же principal); `error superseded` (при reconnect) — прежнее подключение того же principal закрыто; `error session-not-found`/`wrong-session-kind`/`duplicate-tool-name` — соответствующие сообщения пользователю. При старте приложения с сохранённой активной сессией клиент SHALL автоматически connect + register. Renderer SHALL инициировать connect + register автоматически при открытии FREE root-сессии (без ручной кнопки), используя канал регистрации, сохраняющий активную сессию (`relayActiveSessionId`); повторный триггер для той же сессии, пока регистрация в процессе или уже выполнена, SHALL дедуплицироваться (per-session, без блокировки других сессий). Пока регистрация одной сессии не завершена (согласование ожидается или `register` в полёте), регистрация другой сессии SHALL отклоняться с явным кодом (`register-in-progress`) без побочных эффектов для первой; повторный запрос той же сессии, пока ожидается её согласование, отклоняется с кодом `consent-pending`; после отказа согласования клиент SHALL эмитить статус с причиной отказа для показа пользователю. Ожидание ответа пользователя на согласование SHALL НЕ расходовать таймаут регистрации: таймер регистрации стартует с отправкой register-фрейма (после ответа). Срыв регистрации по таймауту SHALL быть виден пользователю (статус с причиной `register-timeout`) и повторяем без перезапуска приложения.

#### Scenario: регистрация на новую сессию

- **WHEN** пользователь открывает FREE root-сессию без активного подключения
- **THEN** клиент автоматически подключается и регистрируется с basePath по умолчанию и стандартным набором инструментов; активная сессия сохраняется для восстановления при старте

#### Scenario: повторное открытие той же сессии

- **WHEN** сессия уже зарегистрирована (или регистрация в процессе) и пользователь снова открывает её
- **THEN** повторный register не отправляется

#### Scenario: параллельная регистрация другой сессии

- **WHEN** согласование или регистрация сессии A ещё не завершены и приходит запрос на сессию B
- **THEN** запрос B отклоняется с кодом `register-in-progress`; согласование и регистрация A продолжаются без изменений

#### Scenario: отказ согласования отражается в статусе

- **WHEN** пользователь отклонил согласование первой регистрации
- **THEN** клиент эмитит статус (registered=false, причина отказа), UI показывает причину, а не «подключён»

#### Scenario: долгое раздумье над согласованием

- **WHEN** пользователь отвечает на согласование позже таймаута регистрации
- **THEN** регистрация продолжается штатно (таймер регистрации стартует с отправкой фрейма, после ответа)

#### Scenario: таймаут регистрации виден и повторим

- **WHEN** сервер не подтвердил регистрацию за таймаут
- **THEN** в строке релея видна причина (`register-timeout`); повторная попытка доступна без перезапуска приложения

#### Scenario: сессия занята другим пользователем

- **WHEN** сервер отвечает `workspace-occupied`
- **THEN** показывается сообщение «сессия занята другим пользователем»; попыток takeover нет

#### Scenario: reconnect того же пользователя

- **WHEN** клиент переподключается после разрыва и шлёт register
- **THEN** сервер сам разруливает (idempotent/takeover/superseded) — клиент не ветвит логику

#### Scenario: STATE-сессия

- **WHEN** пользователь пытается зарегистрироваться на STATE-сессии
- **THEN** регистрация не отправляется; пользователю показывается, что релей доступен только для root-сессий

### Requirement: Локальное исполнение tool.call

Получив `tool.call { callId, sessionId, tool, args }`, клиент SHALL определять рабочий каталог **строго по `call.sessionId`** через соответствие `sessionId → basePath`, поддерживаемое успешными регистрациями; вызов для сессии без записи в соответствии SHALL завершаться явным отказом («no registration for session …») без запуска процесса и без использования каталога другой сессии. Запись добавляется при `registered`; записи сессий, регистрировавшихся ранее на соединении, сохраняются до `disconnect()` (вызов «в полёте» после переключения активной сессии исполняется в своём каталоге); `disconnect()` и терминальные закрытия соединения (4409 `superseded`, 4403 protocol-mismatch) очищают соответствие целиком (reconnect восстанавливает записи повторными регистрациями). Закрытие соединения с последующим реконнектом не SHALL оставлять исполнение в устаревшем каталоге: повторная регистрация восстанавливает соответствие, в том числе при смене basePath. Исполнение — как прежде: `bash` — через `child_process.spawn` в `basePath` (shell ОС, таймаут из args/конфига, stdout+stderr объединены, non-zero exit = OK с exitCode); `read_file`/`write_file`/`edit_file` — через `fs` с лимитами вывода (конфиг); `glob` — поиск в `basePath`; `grep` — поиск по содержимому. Результат SHALL отправляться фреймом `tool.result { callId, output, exitCode }`; длинный вывод — через опциональные `tool.progress { callId, chunk }` (streaming) с финальным `tool.result`. `tool.cancel { callId }` SHALL прерывать исполняемый процесс (SIGTERM → SIGKILL по таймауту) и отменять незавершённый `tool.result`; cancel для неизвестного `callId` — игнорируется клиентом. Конкурентные регистрации разных сессий запрещены (см. «Регистрация на сессии с декларацией»); вызовы последовательно регистрировавшихся сессий исполняются каждая в своём каталоге.

#### Scenario: bash-вызов

- **WHEN** оркестратор вызывает клиентский `bash`
- **THEN** команда исполняется локально в basePath, соответствующем `call.sessionId`; клиент отправляет tool.result с output и exitCode

#### Scenario: вызов для незарегистрированной сессии

- **WHEN** приходит `tool.call` с `sessionId`, отсутствующим в соответствии (никогда не регистрировалась на этом клиенте)
- **THEN** явный отказ «no registration for session …» без запуска процесса; чужой каталог не используется

#### Scenario: последовательные регистрации A→B

- **WHEN** сессия A была зарегистрирована, затем активной стала B ( basePath B отличается)
- **THEN** вызовы B исполняются в каталоге B; вызов A «в полёте» исполняется в каталоге A

#### Scenario: реконнект не меняет каталог

- **WHEN** соединение разорвано и та же сессия перерегистрирована (в том числе с иным basePath)
- **THEN** следующий вызов исполняется в актуальном каталоге этой сессии, а не в каталоге прошлой регистрации

#### Scenario: длинный вывод

- **WHEN** вывод bash превышает лимит
- **THEN** клиент стримит его через tool.progress и завершает tool.result с маркером truncated

#### Scenario: отмена

- **WHEN** приходит `tool.cancel` во время исполнения bash
- **THEN** процесс убивается; `tool.result` для этого `callId` НЕ отправляется (если процесс успел завершиться до cancel — отправляется, сервер игнорирует дубль по идемпотентности callId)

#### Scenario: отмена неизвестного вызова

- **WHEN** приходит `tool.cancel` с `callId`, которого нет в выполняемых вызовах (гонка stop с публикацией вызова)
- **THEN** фрейм игнорируется, ошибка пользователю не показывается

#### Scenario: клиентский таймаут меньше серверного

- **WHEN** локальный bash превышает клиентский таймаут (конфиг; обязан быть < серверного `tool-call-timeout` 5 мин, §5.4)
- **THEN** процесс убивается, шлётся `tool.result` с ошибкой timeout; `tool.progress` потолок НЕ продлевает (известное ограничение контракта)

### Requirement: Heartbeat и переподключение

Клиент SHALL отвечать `pong` на серверный `ping`; клиентский ping-watchdog: отсутствие серверного `ping` дольше 2× ожидаемого интервала (конфиг) → ранний reconnect (спящий/ half-open хост). При потере соединения (network down / close без 4409) SHALL реконнектиться с backoff (конфиг: начальная 1 с, максимум 30 с, экспонента) и повторно отправлять `register` с теми же параметрами — сервер сам решает idempotent/takeover/error, клиент не ветвит. При 4409 `superseded` (подключение забрал другой клиент) — прекратить reconnect-попытки, показать уведомление «сессия открыта в другом месте». При 4403 `protocol`/`protocol-mismatch` — fatal: без retry, сообщение «сервер требует другую версию протокола».

#### Scenario: сеть пропала

- **WHEN** соединение разрывается по причине сети
- **THEN** клиент реконнектится с backoff и перерегистрируется

#### Scenario: takeover с другого устройства

- **WHEN** сервер закрывает соединение с 4409 `superseded`
- **THEN** клиент прекращает reconnect-попытки и показывает уведомление

#### Scenario: протокол не подошёл

- **WHEN** сервер закрывает соединение с 4403 `protocol-mismatch`
- **THEN** reconnect не выполняется; показывается сообщение о несовместимости версии протокола

#### Scenario: half-open соединение

- **WHEN** сервер молчит (спящий ноут, обрыв без FIN) — ping-watchdog сработал
- **THEN** клиент досрочно закрывает соединение и реконнектится

### Requirement: Lifecycle при переключении сессий

При переключении активной сессии клиент SHALL: на новой FREE root-сессии отправить новый `register` на том же WS-соединении (сервер отвязывает прежнюю); на STATE-сессии — регистрацию не отправлять (индикатор: «релей доступен только для root-сессий»). При выходе из приложения — корректно закрывать соединение (без orphan-регистраций; сервер всё равно очистит по heartbeat/разрыву).

#### Scenario: переключение

- **WHEN** пользователь переключается на другую root-сессию
- **THEN** клиент перерегистрируется на новую сессию (basePath по умолчанию новой сессии); UI показывает новый статус релея

### Requirement: Pending-consent переопрос

Main SHALL хранить текущий незакрытый запрос согласования первой регистрации и отдавать его renderer'у по явному запросу (IPC `relay:pending-consent`); запрос снимается с хранения при получении ответа пользователя. Renderer SHALL при монтировании диалогов запрашивать незакрытый consent, чтобы запрос, отправленный main до монтирования (стартовая авторегистрация сохранённой сессии), не терялся.

#### Scenario: consent отправлен до монтирования renderer

- **WHEN** main начал стартовую авторегистрацию и запросил consent до того, как Vue-приложение смонтировалось
- **THEN** renderer при монтировании получает запрос по `relay:pending-consent` и показывает диалог; ответ завершает регистрацию

### Requirement: UI согласования первой регистрации

Renderer SHALL показывать диалог согласования первой регистрации на сессии (sessionId, basePath, список инструментов) с выбором «разрешить/отклонить» и доставлять ответ в main (IPC `RELAY_CONFIRM_REGISTRATION`). Пока ответ не дан, регистрация не отправляется. Диалог SHALL быть доступен из любого view (глобальный оверлей).

#### Scenario: первая регистрация на сессии

- **WHEN** авто-подключение открыло consent-запрос
- **THEN** пользователь видит каталог basePath и набор инструментов; после «разрешить» регистрация отправляется, после «отклонить» — регистрация не отправляется и причина видна в UI

### Requirement: UI подтверждения команды (D-93)

При `confirmCommands=always` renderer SHALL показывать диалог подтверждения каждого `tool.call` (инструмент, args, basePath) с выбором «разрешить/отклонить» и доставлять ответ в main (IPC `TOOL_RESPOND_CONFIRM`). До ответа исполнение не начинается; отклонение завершает вызов результатом «command rejected by user» без запуска процесса.

#### Scenario: разрешение команды

- **WHEN** оркестратор вызвал клиентский инструмент в режиме `always`
- **THEN** команда исполняется и результат попадает в ленту только после «разрешить»

#### Scenario: отклонение команды

- **WHEN** пользователь выбрал «отклонить»
- **THEN** процесс не запускается; агент получает результат «command rejected by user»

### Requirement: Очистка регистрации при разрыве

`disconnect()` SHALL делать любую регистрацию in-flight терминальной за конечное время: ожидающий `register`-promise разрешается с ошибкой «relay disconnected», ожидающие согласования первой регистрации — исходом `disconnected` (не «отказ пользователя»), ожидающие подтверждения команд — отказом, незакрытый consent-запрос очищается. После этого повторная регистрация SHALL проходить полный путь (connect → handshake → согласование → register) без ожидания истечения таймаутов. Программный дедуп (`registering`) валиден только пока регистрация активна.

#### Scenario: разрыв во время ожидания согласования

- **WHEN** соединение/приложение уходит из регистрации, пока пользователь не ответил на согласование
- **THEN** регистрация завершается явной ошибкой разрыва немедленно; запрос согласования снимается с пере-опроса; повторная регистрация той же сессии проходит полный путь

#### Scenario: разрыв после согласования, до ответа сервера

- **WHEN** `disconnect()` приходит после согласования, но до `registered`/`error`
- **THEN** регистрация завершается ошибкой «relay disconnected», а не таймаутом регистрации

#### Scenario: разрыв во время ожидания подтверждения команды

- **WHEN** `disconnect()` приходит, пока пользователь не ответил на подтверждение команды
- **THEN** ожидающее подтверждение разрешается отказом («command rejected by user») без запуска процесса, и вызов получает терминальный результат

### Requirement: Устойчивость ответов диалогов

Renderer SHALL доставлять ответ диалога (согласование регистрации, подтверждение команды) в main до очистки prompt-состояния: при успешной доставке состояние очищается (если не было заменено новым запросом), при сбое доставки состояние сохраняется и ответ может быть повторён. На один prompt SHALL быть доставлен не более одного ответа (at-most-once: повторная доставка на доставляемый prompt — no-op, кнопки диалога неактивны во время доставки). Ответ в main при отсутствии открытого запроса SHALL быть идемпотентным no-op и SHALL НЕ буферизоваться: отложенное решение недопустимо, иначе следующая регистрация той же сессии обошла бы согласование (D-93) — следующая регистрация той же сессии всегда показывает диалог заново.

#### Scenario: сбой доставки ответа

- **WHEN** IPC-вызов доставки ответа завершается ошибкой
- **THEN** диалог остаётся открытым и ответ может быть отправлен повторно; main-резолвер не теряется молча

#### Scenario: успешная доставка

- **WHEN** ответ доставлен в main
- **THEN** prompt-состояние очищается

#### Scenario: двойной ответ на один prompt

- **WHEN** доставка ответа ещё идёт и приходит повторный ответ на тот же prompt
- **THEN** в main доставляется ровно один ответ; после него следующая регистрация той же сессии показывает диалог согласования заново

#### Scenario: ответ без открытого запроса

- **WHEN** в main приходит ответ, для которого нет открытого prompt согласования
- **THEN** это no-op без исключения; ответ не запоминается и не применяется к следующей регистрации той же сессии

### Requirement: Безопасность локального исполнения

Локальное исполнение SHALL происходить с ведома пользователя: первая регистрация на сессию — подтверждение «разрешить оркестратору выполнять команды на этом компьютере в каталоге X»; режим подтверждения `confirmCommands` (always/never, **дефолт always** — пользователь подтверждает каждую команду до исполнения; выключается в Settings после доверия). Путями по умолчанию остаётся `basePath` (chdir); выход за пределы не блокируется (это машина пользователя — D-88). Таймаут локальной команды SHALL быть `min(таймаут из args, harness.relay.tool-call-timeout сервера)` — превышение серверного потолка (5 мин) всё равно даст серверный `tool-timeout`.

#### Scenario: первый раз на сессии

- **WHEN** пользователь регистрируется на сессию впервые
- **THEN** показывается подтверждение с путём basePath и набором инструментов

#### Scenario: режим подтверждения команд

- **WHEN** включён confirmCommands и оркестратор вызывает bash
- **THEN** команда показывается пользователю; исполняется только после confirm
