# desktop-chat Specification

## Purpose
Чат-интерфейс Web Desktop: список сессий, лента сообщений со всеми MessageKind, отправка сообщений, команды compact/stop, SSE-подписка на события сессии через fetch-stream.

## Requirements

### Requirement: Список сессий

UI SHALL показывать список FREE-сессий (`GET /api/v1/sessions?mine=true`): заголовок, агент, `runtimeStatus`-бейдж (IDLE / TURN_RUNNING / PARKED_ASYNC; `PARKED_CLIENT` — зарезервирован и не присваивается, D-84 — UI его не обрабатывает), время активности (превью последнего сообщения НЕ показывается — SessionDto его не содержит, отдельный запрос на каждую сессию — несоразмерно); сортировка по `lastActivityAt`; поле поиска в шапке списка (debounce 300 мс → `q=`); пагинация курсором. Создание новой сессии (`POST /api/v1/sessions`) — выбор агента из каталога (`GET /api/v1/agents`), заголовок. Каталог агентов SHALL загружаться при монтировании и перезагружаться при обновлении списка; сбой загрузки каталога SHALL отличаться от реально пустого каталога: показывается сообщение об ошибке (в стиле ошибок списка), а пустой каталог не выдаётся за «агентов нет».

#### Scenario: открытие приложения

- **WHEN** пользователь залогинился
- **THEN** показывается список его сессий с актуальными runtimeStatus

#### Scenario: создание сессии

- **WHEN** пользователь нажимает «Новая сессия» и выбирает агента
- **THEN** создаётся FREE-сессия, открывается пустой чат

#### Scenario: сбой каталога виден

- **WHEN** `GET /api/v1/agents` не удался (401, рестарт бэкенда, сеть)
- **THEN** показывается сообщение об ошибке; «не загрузилось» не изображается как пустой каталог

#### Scenario: обновление перезагружает каталог

- **WHEN** пользователь обновляет список после восстановления бэкенда
- **THEN** каталог агентов загружается заново и ошибка исчезает

### Requirement: Лента сообщений

UI SHALL отображать сообщения (`GET /api/v1/sessions/{id}/messages`) в хронологическом порядке: USER (справа, автор), ASSISTANT (слева, markdown-рендер), SYSTEM (центр, приглушённый), TOOL_CALL (сворачиваемый: инструмент + args), TOOL_RESULT (сворачиваемый: статус `OK|ERROR|ASYNC_ACCEPTED|CANCELLED|LOST`, output, exitCode, `truncated`-маркер; плейсхолдер «ожидает результат» рендерится, если результат ещё не пришёл или его статус `ASYNC_ACCEPTED`), COMPACT (граница раунда). Поздние результаты — с `late`-маркером. Начальная загрузка: пейджинг `since=0&limit=N` по `nextCursor` до хвоста (история ограничена compact-политикой); новые сообщения приходят через SSE — подгрузка «раньше» скроллом вверх не нужна.

#### Scenario: ассистент ответил

- **WHEN** оркестратор отвечает текстом
- **THEN** сообщение рендерится слева с markdown

#### Scenario: инструмент вызван

- **WHEN** в ленте TOOL_CALL + TOOL_RESULT
- **THEN** отображается сворачиваемый блок с инструментом, args и результатом

#### Scenario: async-плейсхолдер

- **WHEN** TOOL_CALL исполнен, а TOOL_RESULT ещё не пришёл (или пришёл со статусом ASYNC_ACCEPTED)
- **THEN** показывается плейсхолдер «ожидает результат»; поздний TOOL_RESULT заменяет его на результат с late-маркером

### Requirement: Отправка и команды

UI SHALL отправлять сообщения (`POST /api/v1/sessions/{id}/messages`) с атрибуцией автора; команды реализованы кнопками в строке состояния чата (не slash-парсинг): «Compact» → `POST .../compact` (кнопка скрыта для STATE-сессий — compact на них даёт 409 `wrong-session-kind`, §2), «Stop» (с подтверждением «остановить Turn?» при активном TURN_RUNNING; индикатор «агент работает…» в строке состояния рядом с полем ввода). Ввод во время TURN_RUNNING разрешён (событие подхватится доп. раундом).

#### Scenario: отправка сообщения

- **WHEN** пользователь пишет текст и нажимает Enter
- **THEN** сообщение отправляется, появляется в ленте

#### Scenario: остановка

- **WHEN** пользователь нажимает Stop во время TURN_RUNNING
- **THEN** отправляется stop-команда, лента показывает CANCELLED-результаты по завершении

### Requirement: SSE-подписка через fetch-stream

UI SHALL подписываться на события сессии через `fetch` + `ReadableStream` (EventSource не поддерживает Bearer-заголовок — D-87); запрос идёт через main (D-91 — renderer не держит токен). Семантика по контракту §3.1: при коннекте/реконнекте первым приходит снапшот `session.status`, далее `message.created` (SSE `id:` = seq), `ping` (комментарий `: ping`); клиент хранит последний seq и при реконнекте передаёт его в `?since=` (Last-Event-ID приоритетен); `retry: 5000` — пауза реконнекта. При переключении сессии — отписка старой, подписка новой.

#### Scenario: новое сообщение в фоне

- **WHEN** сессия активна и пришёл message.created
- **THEN** сообщение добавляется в ленту без перезагрузки

#### Scenario: статус сменился

- **WHEN** приходит session.status с TURN_RUNNING
- **THEN** бейдж сессии и индикатор ввода обновляются

#### Scenario: реконнект

- **WHEN** stream-соединение рвётся
- **THEN** клиент переподключается с Last-Event-ID без пропусков и дублей

### Requirement: Активная сессия и релей-статус

UI SHALL показывать статус подключения релея к активной сессии: «не подключён» / «подключён (N инструментов)» / «сессия открыта в другом месте» (4409 superseded); текст «подключён» SHALL показываться только для зарегистрированного релея — незарегистрированный релей показывает причину (отказ согласования, отказ сервера) или фазу. Кнопка «Подключить»/«Отключить» управляет регистрацией (desktop-relay-client). При открытии FREE root-сессии UI SHALL запускать авто-подключение релея (desktop-relay-client: connect + register с basePath по умолчанию) без нажатия кнопки; для STATE-сессий авто-подключение не выполняется, а строка релея показывает «релей доступен только для root-сессий» (не статус предыдущей FREE-сессии). Причина последней неудачи регистрации (отказ согласования, `workspace-occupied` и пр.) SHALL быть видна в строке релея. Диалоги согласования регистрации и подтверждения команды (D-93) SHALL быть доступны из любого view как глобальный оверлей.

#### Scenario: индикация подключения

- **WHEN** регистрация на активную сессию прошла успешно
- **THEN** показывается «подключён (N инструментов)»

#### Scenario: авто-подключение при открытии сессии

- **WHEN** пользователь открывает FREE root-сессию
- **THEN** релей автоматически подключается и регистрируется; статус в строке релея обновляется без нажатия «Подключить»

#### Scenario: отказ в согласовании виден

- **WHEN** пользователь отклонил согласование первой регистрации (или сервер отклонил регистрацию)
- **THEN** в строке релея видна причина, а не безликое «подключён»; кнопка остаётся в состоянии «Подключить»

#### Scenario: STATE-сессия показывает индикатор

- **WHEN** пользователь открывает STATE-сессию (в том числе сразу после зарегистрированной FREE-сессии)
- **THEN** строка релея показывает «релей доступен только для root-сессий», а не статус другой сессии

#### Scenario: диалог поверх любого view

- **WHEN** приходит запрос согласования или подтверждения команды, пока пользователь находится не в чате
- **THEN** диалог показывается поверх текущего view
