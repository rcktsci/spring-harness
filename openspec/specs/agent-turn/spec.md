# agent-turn Specification

## Purpose
Пробуждение и жизненный цикл Turn'а: два контура wake (EVENT+POLL), взаимоисключение по сессии на ShedLock-блокировках, агентный цикл с синхронными инструментами, отмена и одноразовые сканы при старте процесса (D-40).

## Requirements

### Requirement: Wake-контур EVENT

Источник, добавивший сессии работу (в M1 — сообщение пользователя; поздние результаты инструментов — с M3), SHALL немедленно инициировать попытку запуска Turn'а для этой сессии, не дожидаясь опроса.

#### Scenario: сообщение запускает Turn сразу

- **WHEN** пользователь отправил сообщение в IDLE-сессию
- **THEN** Turn стартует без ожидания интервала опроса

### Requirement: Wake-контур POLL как страховка

Системная джоба опроса (интервал — конфиг, единственность гарантируется локом джобы) SHALL подбирать сессии с непотреблёнными событиями (`last_seq > last_consumed_seq`), пропущенные контуром EVENT (падение процесса, гонка).

#### Scenario: сессия пропущена из-за рестарта

- **WHEN** процесс перезапущен между дописью сообщения и запуском Turn'а
- **THEN** POLL-джоба в пределах одного-двух интервалов запускает Turn

### Requirement: Взаимоисключение Turn'ов по сессии

Для каждой сессии SHALL действовать блокировка `sess-{sessionId}` (TTL — конфиг `harness.lock.session-ttl`, заведомо больше максимальной длины Turn'а). Попытка запуска при занятой блокировке — no-op. Активный Turn продлевает блокировку heartbeat'ом (интервал — конфиг) и освобождает её по завершении. При нормальной работе исполняется не более одной активной попытки Turn'а на сессии (на любом числе инстансов); патологически замороженный владелец поверх истёкшего TTL допускает повторный запуск — риск принят осознанно (D-40, без fencing-токенов). Блокировка — взаимоисключение Turn'ов; допись событий в журнал его не требует (монотонность seq — транзакционно на уровне БД).

#### Scenario: конкурентный запуск

- **WHEN** сообщение и POLL-джоба одновременно пытаются запустить Turn одной сессии
- **THEN** ровно одна попытка получает блокировку и исполняет Turn, вторая завершается без эффекта

#### Scenario: зависший процесс не блокирует навсегда

- **WHEN** процесс-владелец блокировки умер без её освобождения
- **THEN** блокировка истекает по TTL, сессия подбирается повторно

### Requirement: Агентный цикл Turn'а (sync + async-capable)

Turn SHALL исполнять раунды: рендер видимого контекста → вызов модели → фиксация ответа и tool-calls в журнал → исполнение синхронных инструментов → допись результатов → следующий раунд. Модель «закончила» ⟺ в ответе нет tool-calls; тогда Turn завершается со статусом COMPLETED, `last_consumed_seq` доводится до `last_seq`. События, пришедшие во время хода (новое сообщение), SHALL подхватываться дополнительным раундом. При ошибке LLM, исчерпавшей ретраи, Turn завершается статусом FAILED: в журнал дописывается SYSTEM-событие с причиной ошибки и `last_consumed_seq` доводится до `last_seq` (потребление батча — защита от повторного POLL-запуска); автоматических повторов Turn'а нет — повторная попытка только новой пользовательской записью.

С флагом `cancel_requested` в M3 (mini-amendment R-1, supersede M1-требование «сбрасывается при завершении Turn'а (любой исход) и на старте нового Turn'а»): после `requestStop` (включая каскад SubtreeCanceller по поддереву) флаг SHALL быть персистентным — он НЕ сбрасывается автоматически ни при завершении Turn'а, ни при старте нового; `tryStart` при поднятом флаге — no-op (POLL, поздний результат async-инструмента и рестарт-скан не поднимают остановленную сессию). Флаг сбрасывается только явным resume: USER-сообщение (сброс атомарно с дописью, `SessionStore.appendEvent`) или вход/resume задачи (`AgentStateBootstrapper.bootstrap`).

#### Scenario: сообщение после stop возобновляет сессию

- **WHEN** сессия остановлена (cancel_requested = true) и пользователь дописывает USER-сообщение
- **THEN** флаг сбрасывается атомарно с дописью; wake поднимает Turn; модель видит CANCELLED-результаты и новое сообщение

#### Scenario: stop держится против фоновых wake

- **WHEN** сессия остановленного поддерева становится eligible (например, SubtreeCanceller дописал CANCELLED-результат parked-вызову)
- **THEN** POLL/поздний результат/рестарт-скан не поднимают Turn (tryStart — no-op при cancel_requested); сессия возобновляется только явным resume

Turn SHALL поддерживать async-capable инструменты: если в раунде модель вернула инструмент(ы) с `async-capable=true` и хотя бы один из них не уложился в `harness.async.window.default-ms` (конфиг, дефолт 30 с), ход завершает раунд с записью в журнал `TOOL_CALL(callId) + ASYNC_ACCEPTED(callId)` для каждого (`ASYNC_ACCEPTED` — допустимое значение `MessageKind`; enum расширяется миграцией 018). Sync-результаты раунда фиксируются в этом же раунде; модель видит плейсхолдер ASYNC_ACCEPTED в рендере нового Turn'а, поднятого поздним результатом. Turn с не уложившимися в окно async-вызовами завершается, сессия переходит в `session.runtimeStatus = PARKED_ASYNC` (состояние сессии, значение зарезервировано в api-contracts §2; исход раунда `last_turn_outcome = COMPLETED` при `pending_tool_calls > 0`; enum TurnOutcome НЕ расширяется), wake придёт позже через сессионный канал `message.created` (поздний TOOL_RESULT).

Поздний TOOL_RESULT SHALL идти через сессионный канал `message.created`/`session_message.seq` (M1 `InMemorySessionEventBroadcaster`), инкрементируя `last_seq` сессии, и вызывает wake существующим `TurnManager.tryStart`-путём: после парковки (штатный случай — Turn с async завершён) поздний результат поднимает новый Turn с `instructionSource=TOOL_RESULT`; если Turn по какой-то причине ещё активен, результат подхватывается дополнительным раундом (M1-семантика). Маркер `late=true` в `MessageDto` для поздних. Правило «первый финальный результат выигрывает» — финальные статусы `OK|ERROR|CANCELLED|LOST`; синтетические LOST/CANCELLED из рестарт-скана тоже считаются финальными; `ASYNC_ACCEPTED` — placeholder «в полёте», финальным не считается.

#### Scenario: полный цикл с инструментом

- **WHEN** модель в ответе вызывает инструмент и после получения результата отвечает финальным текстом
- **THEN** в журнале последовательно фиксируются ASSISTANT+TOOL_CALL, TOOL_RESULT, финальный ASSISTANT; Turn — COMPLETED

#### Scenario: сообщение пришло во время хода

- **WHEN** пользователь дописывает сообщение, пока Turn активен
- **THEN** после текущего раунда исполняется дополнительный раунд, видящий новое сообщение

#### Scenario: bash превысил окно в активном Turn'е

- **WHEN** модель вызвала bash и окно превышено
- **THEN** журнал: TOOL_CALL + ASYNC_ACCEPTED; session.runtimeStatus = PARKED_ASYNC (last_turn_outcome = COMPLETED, pending>0); на поздний TOOL_RESULT → wake → новый Turn

#### Scenario: bash превысил окно, Turn уже COMPLETED

- **WHEN** bash вернулся после COMPLETED
- **THEN** финальный TOOL_RESULT (late=true) → message.created → новый Turn видит результат

#### Scenario: смешанный раунд (sync + async)

- **WHEN** модель в одном раунде вызвала sync-инструмент и async-capable инструмент, превысивший окно
- **THEN** sync TOOL_RESULT пишется в этом же раунде; async — TOOL_CALL + ASYNC_ACCEPTED; session.runtimeStatus = PARKED_ASYNC (pending>0); поздний результат поднимает новый Turn

#### Scenario: рестарт во время async

- **WHEN** процесс упал, сессия имеет ASYNC_ACCEPTED(callId) без результата
- **THEN** рестарт-скан (M1 + M3 расширение) записывает синтетический TOOL_RESULT LOST

### Requirement: Write-ahead раунда

Стрим модели завершён → система SHALL сначала записать ответ ассистента и tool-calls в журнал, и только потом исполнять инструменты. Рестарт между записью и исполнением закрывается рестарт-сканом (синтетический LOST) — повторной генерации и двойного расхода нет. Применение мета-инструмента `transition` (M2) SHALL исполняться транзакционно в момент исполнения tool-call (CAS `current_state` + INSERT `task_transition_history` атомарны с исполнением инструмента), а не откладываться до turn-finish: рестарт между tool-call и turn-finish не повторяет и не теряет переход.

#### Scenario: рестарт между записью и исполнением

- **WHEN** процесс упал после записи TOOL_CALL, но до результата
- **THEN** рестарт-скан дописывает синтетический TOOL_RESULT LOST «операция потеряна при перезапуске»

#### Scenario: рестарт после transition tool-call

- **WHEN** процесс упал после исполнения tool-call `transition`, но до завершения Turn'а
- **THEN** переход уже записан транзакционно (история не дублируется), рестарт-скан его не повторяет

### Requirement: Отмена Turn'а (stop)

Команда stop SHALL устанавливать `cancel_requested`; активный Turn проверяет флаг между вызовами модели/инструментов и завершается статусом CANCELLED. Длительная синхронная операция (bash) прерывается убийством процесса в контейнере; её результат — синтетический CANCELLED. Повторный stop идемпотентен. Флаг `cancel_requested` SHALL сбрасываться при завершении Turn'а (любой исход) и на старте нового Turn'а; stop по сессии без активного Turn'а не имеет последующего эффекта.

#### Scenario: stop во время bash

- **WHEN** stop приходит во время исполнения bash в контейнере
- **THEN** процесс в контейнере убивается, в журнал дописывается TOOL_RESULT CANCELLED, Turn — CANCELLED

#### Scenario: stop на IDLE-сессии

- **WHEN** stop приходит на сессию без активного Turn'а
- **THEN** операция безвредна (идемпотентна), ответ `202`

#### Scenario: сообщение после отмены

- **WHEN** Turn завершён со статусом CANCELLED, после чего пользователь отправляет новое сообщение
- **THEN** новый Turn стартует и отрабатывает штатно (флаг cancel_requested не гасит его)

### Requirement: Рестарт-скан и осиротевшие контейнеры

При старте процесса система SHALL: (1) для сессий без живой блокировки `sess-{id}` закрыть TOOL_CALL без финального результата синтетическим TOOL_RESULT LOST (залоченные не трогаются — Turn жив); (2) удалить helper-контейнеры без живой сессии.

#### Scenario: зависший TOOL_CALL закрыт

- **WHEN** после падения процесса сессия имеет TOOL_CALL без результата и свободный лок
- **THEN** при старте дописывается синтетический TOOL_RESULT LOST, сессия пробуждается

#### Scenario: живой Turn не тронут

- **WHEN** TOOL_CALL без результата у сессии с живой блокировкой другого инстанса
- **THEN** рестарт-скан её пропускает

### Requirement: Мета-инструмент transition (гейт metaTools)

В STATE-сессии агенту SHALL быть доступен инструмент `transition(toState, kind, reason)`: `toState` — код исходящего ребра текущего состояния задачи; `kind` — `NEXT|ERROR` (определяется ребром, по умолчанию `NEXT`); `reason` — обязательный непустой текст-обоснование. На уровне реестра `taskId` обязателен (task-engine); инструменту он передаётся адаптером неявно — резолвится из STATE-сессии, в которой исполняется Turn. Гейт metaTools (D-52/D-59): инструмент SHALL быть доступен только при `instructionSource = USER`; в M2 единственная точка входа — USER-сообщение прямо в сессию состояния (`POST /api/v1/sessions/{id}/messages`); агентские сообщения (TOOL_RESULT, внутренние апдейты) metaTools не порождают. Запрещённый гейтом вызов — ошибка инструмента, переход не происходит.

#### Scenario: USER-сообщение разрешает transition

- **WHEN** пользователь отправляет сообщение в сессию состояния и агент вызывает `transition`
- **THEN** инструмент исполняется, переход записывается (семантика — task-engine)

#### Scenario: TOOL_RESULT не порождает metaTools

- **WHEN** ход порождён результатом инструмента (не USER) и агент пытается вызвать `transition`
- **THEN** вызов отклоняется гейтом, переход не происходит

### Requirement: `spawn_subagent` в Turn'е

Агенту-оркестратору SHALL быть доступен `spawn_subagent` в каждом Turn'е (мета-инструмент, см. `subagent-lifecycle`). Вызов строго синхронный — блокирующий: родительский виртуальный поток ждёт завершения субагента (условие завершения — `subagent-lifecycle`); окно `harness.async.window` на spawn НЕ распространяется. Результат (`TOOL_RESULT` с output субагента) фиксируется только на ходу родителя, где spawn вызван. Если родительский Turn всё же завершился до возврата (отмена/рестарт) — поздний TOOL_RESULT идёт через `message.created` и поднимает новый Turn.

#### Scenario: оркестратор spawn'ит в активном Turn'е

- **WHEN** `spawn_subagent` вызван в активном раунде
- **THEN** дочерняя сессия стартует синхронно; родительский поток блокируется до завершения субагента; spawn возвращает TOOL_RESULT на этом же ходу

#### Scenario: родительский Turn завершён до возврата spawn (отмена/рестарт)

- **WHEN** родительский Turn COMPLETED, spawn-результат не успел вернуться
- **THEN** message.created с late TOOL_RESULT поднимает новый Turn родителя

### Requirement: `read_compacted` доступен агенту

В manifest инструментов агента SHALL входить `read_compacted(compact_message_id)` (см. `subagent-lifecycle`). Резолв `id → seq` — по `session_message.id`, только в пределах текущей сессии; cross-session-чтение в M3 не поддерживается. Ответ — оригинальные записи, скрытые COMPACT-покрытием.

#### Scenario: агент читает скрытое

- **WHEN** агент вызывает `read_compacted(id)` где id указывает на покрытое сообщение
- **THEN** TOOL_RESULT с оригиналом (лимит по `harness.compact.read-max-bytes`)

#### Scenario: id вне сессии

- **WHEN** `read_compacted(id)` где id не из текущей сессии
- **THEN** TOOL_RESULT not-found (cross-session-чтение в M3 не поддерживается)
